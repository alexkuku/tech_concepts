1. 为什么需要 AI 沙箱

当 LLM 开始「写代码并执行代码」时，执行环境就变成了一个不可信代码的运行边界。模型可能被提示注入、可能生成死循环、可能尝试读取宿主机文件或内网服务。沙箱要回答的，本质是一个安全工程问题：如何在几百毫秒内，为一段来路不明的代码准备好一台可丢弃的计算机？

2. 五分钟心智模型

E2B 与 CubeSandbox 虽然实现不同，但抽象层次高度一致：它们都把「运行一段代码」拆成了控制面（决定在哪跑）、数据面（真正跑起来）和边缘面（流量怎么进出）。先建立这张映射表，后面看任何组件都不会迷路。

控制流（创建/销毁）与数据流（HTTP 访问沙箱端口）是分离的两条路径：前者经过控制面，后者从边缘代理直达节点。这是两者共同的设计，也是高并发场景的关键。

一句话记住两个项目

E2B 是「AI 代码执行沙箱」这一品类的开源原厂实现，生态与 SDK 最完整；CubeSandbox 是腾讯开源的、E2B API 兼容的自托管替代品，重点优化冷启动、密度与 eBPF 网络。

3. E2B 全景

E2B（Apache-2.0 Runtime）提供「安全隔离的云沙箱」来运行 AI 生成的代码，既提供 E2B Cloud，也开源了可自托管的 runtime。它的核心抽象非常克制：Sandbox（一台按需 Linux VM）+ Template（环境定义）+ SDK（Python/JS）。

E2B 的四类 SDK 与能力边界

# 最小示例：创建沙箱并在其中执行 shell 命令
from e2b import Sandbox

with Sandbox.create() as sbx:
    result = sbx.commands.run("python3 -c 'print(6 * 7)'")
    print(result.stdout)          # 42

    sbx.files.write("/tmp/hello.txt", "hi from agent")
    print(sbx.files.read("/tmp/hello.txt"))
# Code Interpreter：变量在同一内核中跨调用保留
from e2b_code_interpreter import Sandbox

with Sandbox.create() as sbx:
    sbx.run_code("x = 41")
    execution = sbx.run_code("x + 1")
    print(execution.text)         # 42
    # execution 还可以带出 stdout、stderr、图表、错误等结果
关键区别

e2b 的 commands.run 每次都是独立进程；e2b-code-interpreter 则维护一个有状态的 Jupyter 内核，因此变量、导入的模块、内存中的 DataFrame 都能跨调用保留——这正是「代码解释器」与「执行 shell」的本质差异。

3.2 创建沙箱的完整流程

一次 Sandbox.create() 对 SDK 而言是一个同步调用，内部却横跨边缘、控制面、调度与节点四层，可拆成 12 个阶段。下面按「谁负责、读写什么状态、失败怎么办」逐段展开——这既是理解「控制流 / 数据流分离」的入口，也是排查创建变慢与创建失败的坐标。

图 3 · E2B 创建沙箱时序（12 阶段）：①–③ 准入与放置，④–⑦ 模板解析与沙箱准备，⑧–⑨ 快照恢复与 envd 就绪，⑩–⑫ 网络接入、落库与返回
  1. SDK 序列化并签名请求

    把模板 ID、资源规格（vCPU / 内存）、超时时间、环境变量、metadata 与 secure 标记组装成请求体，经 E2B_API_KEY 鉴权后发往 POST /sandboxes。sandboxId 不在客户端预分配，一切以服务端返回为准。

  2. Client Proxy 做边缘接入

    终止 TLS、做基础限流并注入请求 ID，再按 API 域名把请求转发到控制面集群。这一层不保留沙箱状态，因此它挂掉只会让请求失败，不会留下「半创建」的沙箱。

  3. API 做鉴权与准入

    依次校验 API Key 所属 team、模板可见性（公共 / 私有）、并发沙箱配额、速率限制与参数上限（CPU / 内存 / 超时）。任何一项不通过都直接返回 4xx，不进入调度，也不占用节点资源。

  4. Template Manager 解析模板

    确认该模板在集群中已有可用构建；目标节点没有缓存时，从对象存储拉取 rootfs 层并分发到节点；若模板从未构建过且允许即时构建，则先跑构建步骤生成 rootfs 与内存快照。命中缓存时，这一步退化为一次元数据查询。

  5. API 选择节点并落初始状态

    按「模板已缓存 → 资源余量 → 亲和 / 打散」的优先级选出节点，把 sandboxId、模板、节点与超时写入 PostgreSQL，状态置为 starting。这条记录既是幂等依据，也是失败时回收资源的凭据。

  6. Orchestrator 领取任务并准备沙箱目录

    节点侧 Orchestrator 收到创建指令后，为沙箱建立独立目录（rootfs 层、配置、日志），把环境变量、超时与 metadata 写入本地配置，并预留 cgroup 与网络资源。

  7. CoW 克隆 rootfs

    对模板的只读 rootfs 做 reflink 克隆（FICLONE），只改元数据、不复制数据；沙箱内的写入全部落在新层，模板本身始终保持只读。

  8. Firecracker 恢复快照

    按规格创建 Firecracker 进程，恢复包含内核与 envd 的预启动内存快照；virtio 块设备指向第 7 步的 CoW 层，网络设备先完成占位。内存页通过 userfaultfd 惰性加载，只有真正访问到的页才从快照中取。

  9. envd 就绪并健康检查

    VM 内 envd 开始监听，Orchestrator 通过健康检查确认它可以接受 RPC。从这一刻起，shell、文件、PTY、代码执行全部经由 envd，不再经过控制面。

  10. 网络接入与路由登记

    创建 TAP 设备并加入沙箱的 network namespace，下发 nftables 规则（出口策略、端口转发），再把 <port>-<sandboxId>.<domain> 的路由登记到 Client Proxy，同时生成访问 token，避免端口被随意枚举。

  11. 状态更新与事件发布

    控制面把状态从 starting 改为 running，并把创建耗时、节点、模板等生命周期事件写入 ClickHouse 等分析管道，供计费、监控与自动暂停策略消费。

  12. 返回 sandboxId 与访问信息

    API 返回 HTTP 201，包含 sandboxId、域名与 envd 凭据；SDK 缓存 envd 客户端，后续命令与文件操作直接走「Client Proxy → envd」，控制面不再参与数据流。

创建链路的责任边界与失败处理

模板解析与构建Template Manager对象存储中的模板构建状态返回构建错误，不产生沙箱记录

为什么能快

等待时间被三个优化压缩：预启动快照（第 8 步跳过内核引导与用户态初始化）+ CoW 根文件系统（第 7 步跳过镜像解压）+ 惰性内存加载（第 8 步只拉取真正访问到的页）。这也是所有 MicroVM 沙箱的通用公式。

排障视角

创建变慢时按顺序看三个指标：模板是否命中节点缓存（未命中会退化为跨节点拉取，对应第 4 步）、节点内存压力（缺页变多，userfaultfd 拉取变慢，对应第 8 步）、边缘到节点的 RTT（跨可用区放置，对应第 5 步）。三者分别指向放置策略、超卖比例与网络拓扑问题。

3.3 隔离与资源模型

E2B 的隔离不是单一机制，而是「VM 边界 + 内核资源控制 + 网络命名空间」的叠加。理解每一层各防什么，是安全评审的基础。

1Firecracker MicroVM独立内核，硬件虚拟化边界，防内核逃逸
2cgroupsCPU / 内存 / I/O 限额，防资源耗尽（noisy neighbor）
3Network Namespace每沙箱独立网络栈，配合 nftables 做出口域名策略
4Rootfs CoW只读镜像 + 写时复制，沙箱间不共享可写数据
5Secrets 控制面隔离密钥只存在于控制面元数据；工作负载用短期身份令牌
E2B 隔离层次与威胁模型
层隔离对象防御的威胁失效后果
MicroVM内核、地址空间、设备内核漏洞提权、容器逃逸跨租户代码执行
cgroupsCPU / 内存 / I/Ofork 炸弹、内存耗尽、磁盘打满同节点其他沙箱被拖垮
netns + nftables网络栈与出口内网探测、数据外泄、C2 回连横向移动

Secrets 隔离凭据模型上下文泄露密钥云资源被滥用
安全评审要点

评审沙箱平台时，不要只看「是否用了 Firecracker」。要同时确认：设备模型是否最小化（virtio 越少越好）、seccomp 是否收紧、出口是否默认拒绝、密钥是否进入 VM。任何一项缺失，VM 边界都可能被绕过。

3.4 状态、暂停与持久化

E2B 把沙箱的生命周期做成了「暂停 / 恢复」的一等公民：暂停会同时保存内存与磁盘的差异，恢复时优先选择缓存了这些数据的节点。这意味着 Agent 可以「挂起」一个长任务，稍后继续，而不用重新初始化环境。

E2B 生命周期操作与语义
操作保存内容资源占用典型用途
create新建 VM + CoW rootfs运行态资源每轮工具调用
pause内存 + 磁盘 diff快照存储，释放计算长任务挂起、降本
resume恢复内存与文件系统重新占用计算继续任务；优先有缓存的节点
kill销毁 VM 与临时数据释放全部资源任务结束、回收
持久卷独立于沙箱生命周期的存储按卷计费跨沙箱共享代码/数据

内存快照为什么能「懒加载」

图 4 · 基于 userfaultfd 的惰性内存恢复：恢复快、首访慢，适合「创建后很快只用一小部分内存」的 Agent 负载
与 CubeSandbox 的差异

CubeSandbox 同样采用「内存快照 + 恢复」，但额外强调增量脏页跟踪：暂停时只持久化被修改的匿名页，未修改页通过 reflink 共享，从而降低写放大与快照体积。两者的目标一致，实现路径不同。

3.5 网络与访问模型

沙箱里的服务（Jupyter、Web 应用、数据库）需要能被外部访问。E2B 采用「端口子域名」模型：每个沙箱的每个监听端口都映射为一个 HTTPS 子域。

# 沙箱内监听 3000 端口后，外部可直接访问：
https://3000-<sandboxId>.<your-domain>

# 访问链路（数据面）：
Client → Client Proxy（边缘） → Orchestrator Proxy（节点） → envd → 沙箱内进程
E2B 网络设计要点
维度做法效果
入站寻址<port>-<sandboxId>.domain无需为每端口分配公网 IP；通配 DNS + TLS
访问控制每沙箱访问令牌URL 泄露不等于可访问

常见坑

「沙箱能访问外网」不等于「出口安全」。仅靠安全组或出站 IP 白名单，无法阻止域名前置（domain fronting）与SNI 伪装。生产环境应使用 L7 出口代理做基于域名的允许列表，并对 TLS 做可控检查。

3.6 部署形态与自托管

E2B 提供从托管云到单机、再到多云 Terraform 的完整光谱。选型时先明确「数据能否出域」与「是否需要 KVM」两个约束。

全链路 OpenTelemetry；生命周期事件、宿主机统计与指标写入 ClickHouse，可对接现有监控体系。

Secrets

密钥只作为控制面元数据存在；VM 内工作负载通过 workload identity 获取短期令牌，避免长期凭据落盘。

控制面与节点代理以 Go 为主，适合与现有云原生栈集成；Firecracker 本身为 Rust。

小结

E2B 的设计哲学可以概括为：「VM 边界 + 快照恢复 + 边缘路由 + 托管优先」。它把复杂性留给平台，把极简的 SDK 留给应用开发者。

4. CubeSandbox 全景

CubeSandbox 是腾讯开源的 AI Agent 基础设施（Apache-2.0），基于 RustVMM + KVM 启动硬件隔离的 MicroVM，官方宣称冷启动 60 ms 以内、单机可承载数千沙箱，并提供 E2B 兼容的 REST API。它的定位不是「简单工具执行」，而是长生命周期、有状态的 Agent 与服务工作负载（持久开发环境、Web 服务、数据库）。

4.2 请求生命周期（11 步）

下面是官方文档描述的 Sandbox.create() 完整链路。注意第 5 步的 CoW 克隆与第 7 步的 快照恢复——这是「毫秒级」与「高密度」的两个支点。

  1. Client → CubeAPI

    SDK 发送 E2B 兼容的 POST /sandboxes 请求。

  2. CubeAPI → CubeMaster

    通过 gRPC 转发内部请求，完成鉴权与参数转换。

  3. CubeMaster 选择节点

    基于资源可用性（CPU / 内存 / 模板本地缓存）做放置。

  4. CubeMaster → Cubelet

    发送 RunCubeSandbox gRPC 指令到目标节点。

  5. Cubelet 准备 rootfs

    通过 CubeCoW 从模板做 O(1) 克隆，不复制数据。

  6. Cubelet → CubeShim

    经 containerd Shim v2 接口创建并启动 task。

  7. CubeShim → CubeHypervisor

    启动 VMM，创建 VM，并从内存快照恢复。

  8. VM 就绪

    CubeHypervisor 报告 ready，vsock 开始监听。

  9. 网络接入

    Cubelet 通过 CubeVS 挂载 TAP 设备与过滤器（策略、NAT）。

  10. 发布事件

    CubeMaster 将生命周期事件写入 Redis，供路由与自动暂停使用。

  11. 返回结果

    CubeAPI 返回 sandbox ID 与元数据（HTTP 201）。

观察点

整条链路中，只有 CoW 元数据操作与 内存快照恢复是「重活」。这也是为什么「模板预热」比「镜像拉取」重要：模板一旦在节点上预热，后续创建几乎只剩元数据操作。

为什么不用 iptables

iptables 的规则是线性链式匹配，规则数一多（数千沙箱 × 每沙箱多条规则）就会显著退化；且每次变更都要重建链。eBPF 用 hash/LPM map 查找，天然支持热更新与 per-sandbox 隔离，还能在同一程序里做 DNS 检查、会话跟踪与 ARP 代理。

4.5 安全体系与出口控制

CubeSandbox 的安全是「六层纵深」：从硬件虚拟化一直到 L7 出口代理。任何单层被绕过，仍有多层兜底。

1硬件隔离KVM MicroVM，每沙箱独立内核
2网络隔离CubeVS 默认拒绝私网/链路本地，per-sandbox 策略
3出口控制CubeEgress L7 代理 + 域名允许列表
4凭据保险箱Header 重写注入，密钥不进入沙箱与模型上下文
5SeccompCubeHypervisor 仅保留最小系统调用白名单

5.1 逐项解读

① 同源异构的 VMM

E2B 用 AWS 的 Firecracker；CubeSandbox 用 RustVMM（Firecracker 同源技术栈的通用 VMM 库）。两者都基于 KVM、都只暴露最少 virtio 设备，因此安全边界与启动性能在同一量级。

② 控制面的「厚度」

E2B 的 Orchestrator 直接管进程，链路短；CubeSandbox 多了 CubeMaster（集群调度）与 CubeShim（Shim v2）两层，换来更好的多节点扩展性与容器生态复用。

③ 网络哲学

E2B 偏「成熟内核组件」：nftables + netns + 代理。CubeSandbox 偏「可编程数据面」：eBPF 自建 NAT/连接跟踪/策略，规则规模与热更新更友好，但调试门槛更高。

④ 出口安全深度

CubeEgress 是完整的 L7 MITM 代理，支持按 SNI/Host/Method/Path 过滤、凭据注入与审计；E2B 主要依赖 nftables 域名规则，L7 能力较弱但部署更简单。

⑤ 状态与数据

E2B 的持久卷与暂停语义更面向「应用开发者」；CubeSandbox 的 CoW 快照/克隆/回滚更面向「平台运维」，适合做开发环境、数据库等有状态服务。

⑥ 迁移成本

由于 API 兼容，从 E2B 迁到 CubeSandbox 主要是改 endpoint 与密钥；反向迁移同样容易。这降低了两者的锁定风险，也让「本地开发 + 云上生产」可以混用。

如何客观评价「谁更好」

不存在绝对优劣：E2B 胜在生态成熟、SDK 完善、托管省心；CubeSandbox 胜在自托管密度、冷启动数字与 eBPF/L7 安全深度。真正的选型变量是「数据能否出域」「是否需要 KVM」「团队能否维护内核级组件」。

6.3 CoW 与 reflink 的本质

传统复制是「复制数据块」；reflink 是「复制块的引用」。写时复制（CoW）则在此基础上，只有当某一方修改某个块时，才为该方分配新块。因此：

  • 创建沙箱：克隆模板 rootfs 的元数据，O(1)。
  • 快照：记录当前元数据映射，O(1)。
  • 写入：只复制被修改的块，空间随写入量增长。
  • 删除：释放该快照独占的块；共享块由引用计数管理。
工程陷阱

reflink 的「O(1)」只在支持 reflink 的文件系统上成立。若数据盘是 ext4 或未开启 reflink 的 XFS，克隆会退化为全量复制，冷启动与密度优势瞬间消失。这是自托管最常见的性能事故。

10. 常见问题 FAQ

Q1：E2B 和 CubeSandbox 是竞品吗？

可以视为同一品类的两种实现。CubeSandbox 明确以 E2B 兼容 API 为卖点，定位是「开源、可自托管的替代」。E2B 生态更成熟（官方 SDK、Cloud、Desktop、企业支持），CubeSandbox 更强调自托管密度、冷启动与 eBPF/L7 安全。两者可以混用：本地开发用 E2B，生产用 CubeSandbox，或反之。

Q2：为什么不用 Docker 容器，而要用 MicroVM？

容器共享宿主内核，任何内核漏洞都可能导致跨租户逃逸；且容器无法提供「独立内核」级别的强隔离。MicroVM 每沙箱一个内核，攻击面小得多，代价是启动与内存开销。对于「执行来路不明的 AI 代码」这一场景，MicroVM 是更合适的默认选择。

Q3：为什么能 <60ms 冷启动？

不是「从零启动 Linux」，而是「恢复预启动快照」：模板阶段已完成内核引导与用户态初始化并生成内存快照；创建沙箱时只做 CoW 克隆 rootfs + 恢复内存快照，内存页还可惰性加载。三个优化叠加，才有官方数字。

Q4：内存和磁盘怎么省？

磁盘靠 reflink/CoW 共享只读镜像，只有写入才产生新块；内存靠页共享（相同只读页）、惰性加载与脏页增量快照。密度越高，共享收益越大。

Q5：沙箱里的服务怎么被外部访问？

E2B 用 https://<port>-<sandboxId>.domain 的子域模型；CubeSandbox 的 CubeProxy 同时支持 Host 模式与 Path 模式（/sandbox/<id>/<port>/...），后者适合无法配置通配 DNS/TLS 的环境。

Q6：出口安全到底防什么？

防三件事：内网探测（访问私网/元数据服务）、数据外泄（把密钥/数据发到未授权域名）、供应链回连（C2）。手段是默认拒绝 + 域名允许列表 + L7 审计 + 凭据不进沙箱。

Q7：能不能跑浏览器和桌面？

E2B 提供官方 Desktop SDK（鼠标、键盘、截图、应用启动、桌面流）；CubeSandbox 仓库也提供浏览器自动化示例。两者都基于同一个 MicroVM 隔离模型，桌面只是更重的模板。

Q8：自托管需要什么？

最低：x86_64 Linux + KVM + 支持 reflink 的数据盘 + Docker/容器运行时。生产还需要多节点调度、Redis、对象存储、监控与出口代理。E2B 有 Embed/Terraform/K8s 路径；CubeSandbox 有 PVM/裸机/Terraform/K8s 预览。

Q9：迁移成本高吗？

由于 API 兼容，主要是改 endpoint 与密钥，业务代码基本不动。但要注意 SDK 版本差异（E2B_API_URL vs E2B_DOMAIN）、模板格式、以及各自特有的能力（如 E2B Desktop、CubeEgress 策略）。

Q10：如何评估性能？

至少测四个指标：冷启动 P50/P99、单机密度（内存超卖下的稳定并发）、恢复延迟（暂停后首次请求）、出口代理开销（RTT 增量）。压测时用真实模板与真实负载，不要用空镜像。
