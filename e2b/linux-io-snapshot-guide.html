1. 为什么做快照必须先懂 IO 栈

「快照」听起来只是「把当前状态存一份」，但在内核里它至少涉及三个独立的问题：内存里的页是什么状态、文件系统是否处于一致点、块设备上的写缓存是否已落盘。任何一层没对齐，快照要么不一致，要么恢复后数据错乱，要么性能完全不可用。

一句话原则

快照的一致性上限，由你最不了解的那一层决定。只懂 cp 的人做出来的是「文件副本」；懂页缓存与 writeback 的人做出来的是「崩溃一致快照」；懂 freeze 与设备 flush 的人才能做出「应用一致快照」。

常见误区

「快照 = 复制磁盘」是错的。对运行中的沙箱，磁盘只是状态的一部分：内存里的脏页、CPU 寄存器、设备队列、vsock 连接同样是状态。CubeSandbox 的模板之所以包含「冷启动后的内存快照」，正是因为只克隆 rootfs 无法恢复一个「已经跑起来」的环境。

3. 内存管理（一）：虚拟内存与物理页

Linux 的每个进程都活在自己的虚拟地址空间里。CPU 通过 MMU 查页表，把虚拟地址翻译成物理地址；内核则用 struct page 管理每一个物理页。理解「虚拟 → 页表 → 物理页」这条链，是理解页缓存、mmap、userfaultfd 的前提。

3.1 缺页：虚拟地址第一次被访问时发生什么

  1. CPU 访问虚拟地址，MMU 查页表发现 PTE 无效

    触发 #PF 异常，进入内核 do_user_addr_fault。

  2. 内核找到对应 VMA

    检查地址是否落在合法区间、权限是否允许（读/写/执行）。

  3. 分类处理

    匿名页 → 分配零页或从 swap 读入；文件页 → 查 page cache，未命中则文件系统发起读 IO。

  4. 填充 PTE

    把物理页帧号写入页表，设置权限位与脏位；更新 RSS 统计。

  5. 返回用户态重试

    指令重新执行，这次 MMU 命中。

缺页的两种类型（性能分析的关键区分）
类型触发条件是否需要 IO典型场景观测
Minor fault（次缺页）页已在页缓存/已分配，只是 PTE 未建立通常否首次访问已缓存文件、CoW 复制、UFFD 惰性恢复/proc/vmstat 的 pgfault
Major fault（主缺页）页不在内存，需要从磁盘/swap 读入是冷启动读文件、swap 换入、快照首次拉页pgmajfault；perf 可追踪
CubeSandbox 落地 ①

模板恢复时，如果内存快照按需加载（userfaultfd），那么「第一次访问某个页」就是一次 minor 或 major fault。这解释了为什么沙箱刚恢复时会有延迟毛刺：热页越多，毛刺越少。优化手段是恢复后主动 MADV_WILLNEED 预取，或对热点页做预热。

4. 内存管理（二）：Page Cache 与 address_space

页缓存是 Linux 性能的基石：读写文件本质上是在读写内存页，磁盘只是页的后端。页缓存按「inode + 文件偏移」索引，而这个索引的载体就是 address_space。

图 3 · file / dentry / inode / address_space 四者关系：inode 是磁盘元数据的内存表示，address_space 是它的页缓存视图

关键细节：reflink 不共享页缓存

XFS 的 reflink 共享的是磁盘 extent，不是内存页。克隆出来的文件是新的 inode，拥有独立的 address_space 与页缓存。所以：克隆是 O(1) 的磁盘操作，但冷读仍会打盘。CubeSandbox 做克隆/恢复时，如果希望低延迟，需要额外做页缓存预热（vmtouch、MADV_WILLNEED、或共享内存快照）。这是很多人第一次做 reflink 快照时踩的坑。

5. 内存管理（三）：回收与回写

内存不是无限的。当空闲页低于水位线，内核开始回收；当脏页超过阈值，内核开始回写。快照的性能与一致性，几乎都绕不开这两个机制。

5.1 页面回收（reclaim）

回收机制与水位线
机制触发行为对快照的影响
kswapd（后台回收）空闲页低于 low 水位异步扫描 LRU，回收干净页/回写脏页后台抖动，可能拖慢快照
直接回收（direct reclaim）分配时低于 min 水位分配者自己同步回收，延迟尖刺快照期间分配内存会变慢
LRU 双链表—active/inactive 分级，二次机会热页更可能留在内存，利于恢复
swap匿名页被回收换出到 swap 设备内存快照可能包含已换出页的引用
OOM killer无法回收且超过 memory.max按 oom_score 杀进程快照进程被误杀 → 快照失败

水位线：min（保留）< low（唤醒 kswapd）< high（停止回收）。可通过 /proc/sys/vm/watermark_scale_factor 调整。

做快照前，正确顺序是：让客户机应用 fsync（或 fsfreeze）→ 暂停 vCPU → 刷宿主机页缓存 → 刷设备写缓存 → 再做 reflink/内存快照。少了任何一步，恢复出来的沙箱都可能「看起来正常，但文件断了半截」。

6. 内存管理（四）：memcg 与 userfaultfd

6.1 memcg：给沙箱划内存红线

cgroup v2 的 memory 控制器负责统计与限制一组进程的内存。对沙箱平台而言，它是「单沙箱内存配额 + 超卖 + OOM 隔离」的基础。

cgroup v2 memory 关键接口
文件含义用法
memory.current当前使用量（anon + file + kernel）监控、利用率
memory.max硬上限，超过触发回收，最终 OOM单沙箱配额
memory.high软上限，超过后限流回收避免硬杀，平滑降速
memory.stat细分统计：anon、file、dirty、writeback、slab定位「谁占用了内存」
memory.eventshigh/max/oom 事件计数告警
memory.reclaim主动回收指定字节数快照前主动腾内存
memory.oom.groupOOM 时整组杀避免只杀子进程留下残局
容易忽略的点

memory.current 包含 page cache。一个沙箱读了很多文件，current 会上升，但这部分是可回收的。做容量规划时，真正要限制的是 anon；page cache 应该「能收就收」，而不是直接算进硬配额。

6.2 userfaultfd：把缺页交给用户态

userfaultfd 允许用户态程序注册一段内存，并在缺页时接管处理。它让「按需加载」从内核策略变成用户策略，是 VM 内存快照、CRIU、QEMU 热迁移的核心机制。

userfaultfd 的三种模式
模式触发的缺页支持的内存类型典型用途
UFFDIO_REGISTER_MODE_MISSING页从未存在（匿名页/空洞）匿名、shmem、hugetlbfs懒分配、按需从快照拉页

/* 极简骨架：注册一段匿名内存，缺页时从快照文件填充 */
int uffd = syscall(SYS_userfaultfd, O_CLOEXEC | O_NONBLOCK);
struct uffdio_api api = { .api = UFFD_API };
ioctl(uffd, UFFDIO_API, &api);

void *addr = mmap(NULL, len, PROT_READ | PROT_WRITE,
                  MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);

struct uffdio_register reg = {
    .range = { .start = (unsigned long)addr, .len = len },
    .mode  = UFFDIO_REGISTER_MODE_MISSING,
};
ioctl(uffd, UFFDIO_REGISTER, &reg);

/* 事件循环 */
struct uffd_msg msg;
read(uffd, &msg, sizeof(msg));           /* 发生缺页 */
off_t off = msg.arg.pagefault.address - (unsigned long)addr;
pread(snap_fd, buf, PAGE_SIZE, off);      /* 从快照文件读页 */

struct uffdio_copy copy = {
    .dst = msg.arg.pagefault.address & ~(PAGE_SIZE - 1),
    .src = (unsigned long)buf,
    .len = PAGE_SIZE,
};
ioctl(uffd, UFFDIO_COPY, &copy);          /* 填充并唤醒缺页线程 */

生产实现还要处理 UFFDIO_ZEROPAGE（零页）、UFFDIO_CONTINUE（minor 模式）、UFFDIO_WRITEPROTECT（写保护跟踪）、fork 事件与并发。内核 tools/testing/selftests/mm/uffd-* 有完整示例。

7.1 路径解析：一次 open("/a/b/c") 经过什么

  1. 从根或 cwd 开始

    link_path_walk 逐段解析，优先走 RCU-walk（无锁读 dcache）。

  2. 查 dcache

    命中则直接拿 inode；未命中调 i_op->lookup 从磁盘读目录项。

  3. 权限与挂载检查

    每段做 inode_permission，并处理挂载点跨越（mount namespace）。

  4. 打开文件

    分配 struct file，调 f_op->open，返回 fd。

与快照相关的两个细节

① dcache 与 inode 缓存是内存状态，快照恢复后如果底层文件被替换（例如回滚到旧 reflink 克隆），必须让缓存失效，否则会读到旧 inode 的数据。② 挂载命名空间决定沙箱看到哪些文件系统；跨节点恢复时，挂载点与设备名可能变化，需要重新绑定。

8.1 日志（journaling）到底保证什么

日志解决的是崩溃一致性：如果系统在写数据的中途掉电，重启后通过重放日志，让文件系统回到「某个一致状态」。注意——它不保证你的数据不丢，只保证元数据不自相矛盾。

ext4 的三种数据日志模式
模式数据是否写日志一致性性能典型场景
data=ordered（默认）否，但保证数据先于元数据落盘不会出现「元数据指向未写数据」中通用服务器
data=writeback否，无顺序保证可能读到旧数据/垃圾高对一致性要求低的场景
data=journal是，数据也写日志最强低（写放大）数据库元数据、小文件

XFS 采用元数据日志 + 延迟分配：数据块先写，日志提交确保元数据指向已写入的数据。XFS 的日志是一个环形缓冲区，通过 CIL（Committed Item List）批量提交，因此高并发下日志开销被摊薄。

「崩溃一致」不等于「应用一致」

文件系统日志只能保证结构一致。数据库还需要 WAL/redo log，应用还需要自己的事务语义。做 VM 快照时，如果客户机里跑着数据库，默认快照只是崩溃一致；要应用一致，必须在客户机内 fsfreeze 或调用数据库的快照钩子。

9. 文件系统（三）：reflink 与写时复制

这是 CubeSandbox 快照最关键的一节。XFS 的 reflink 允许两个文件共享同一批磁盘 extent；只有某一方写入时，才为它分配新块。它把「复制一个 GB 级 rootfs」从 O(数据量) 降到 O(元数据)。

9.2 FICLONE 系统调用

#include <sys/ioctl.h>
#include <linux/fs.h>
#include <fcntl.h>

int clone_file(const char *src, const char *dst) {
    int sfd = open(src, O_RDONLY);
    int dfd = open(dst, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (sfd < 0 || dfd < 0) return -1;

    /* 整个文件克隆；FICLONERANGE 可只克隆一段 */
    if (ioctl(dfd, FICLONE, sfd) < 0) {
        perror("FICLONE");           /* EOPNOTSUPP：文件系统不支持 */
        return -1;                   /* EXDEV：跨文件系统 */
    }
    close(sfd); close(dfd);
    return 0;
}
生产环境必须处理的边界
  • EOPNOTSUPP：数据盘不是 XFS/Btrfs，或 XFS 未开 reflink → 必须回退到全量复制，并告警。
  • EXDEV：源和目标不在同一文件系统 → 不能克隆。
  • ENOSPC：CoW 写入时空间不足 → 写入失败，沙箱可能损坏；需要预留空间与告警。
  • extent 碎片：极端碎片化时，克隆的元数据操作不再是严格 O(1)，但仍远小于数据复制。
  • 页缓存不共享：克隆后第一次读仍打盘，需要预热策略。
  • 快照平面模型：CubeSandbox 的快照之间相互独立，删除一个不影响另一个；GC 必须基于引用计数。

10. 文件系统（四）：一致性与 freeze

拍快照的前提是「静止点」。但 Linux 的文件系统一直在动：应用在写、页缓存在回写、日志在提交。要得到一个可用的快照，必须先把文件系统冻结，或者用写时复制机制保证时间点一致。

10.1 三种一致性级别

快照一致性的三个级别
级别保证实现手段适用

10.2 freeze 的层次

内核的 FIFREEZE ioctl 会调用 freeze_super()，把文件系统推进三个逐步加深的状态：

1SB_FREEZE_WRITE阻止新的写操作，等待进行中的写完成
2SB_FREEZE_TRANS等待日志事务提交完成（XFS 刷 log，ext4 刷 JBD2）
3SB_FREEZE_FREEZE完全冻结，允许安全读取/克隆；此时拍快照
# 冻结 / 解冻（需要 root）

# ... 在此拍快照 / reflink 克隆 / 备份 ...
fsfreeze -u /var/lib/cube          # FITHAW

# 查看是否冻结

# 或用 xfs_io 查询

freeze 的代价

冻结期间，客户机内所有写操作都会阻塞。对长事务或高写入负载，freeze 可能持续数百毫秒甚至更久，直接表现为业务卡顿。因此生产实现通常会给 freeze 设置超时，并在超时后放弃本次快照（而不是无限等待）。CubeSandbox 的自动暂停/恢复机制同样需要这个超时保护。

14.1 写缓存与持久化保证

很多设备（尤其是 SSD、云盘、RAID 控制器）有易失写缓存：write 返回时数据可能只在缓存里。要保证持久化，必须使用 flush 或 FUA 语义。

FALLOC_FL_ZERO_RANGE系统调用零填充区间（可保留块）安全擦除快照中的敏感区
discard 的两个陷阱

① 异步且可能丢：discard 不保证完成，不能作为「数据已擦除」的安全保证；敏感数据应显式覆写或加密。② 性能抖动：大量 discard 会触发 SSD GC，造成延迟尖刺；生产上通常用 fstrim.timer 在低峰期运行。

18. 一致性设计：把「静止点」工程化

前面讲了一致性的原理，这一章讲怎么在系统里实现它。核心是「两阶段协议 + 超时回滚 + 幂等」。

18.1 快照协议

  1. Pre-check

    检查目标节点资源、数据盘剩余空间、reflink 支持、快照 ID 是否已存在（幂等）。

  2. Quiesce

    通知沙箱内应用/文件系统进入静默：fsfreeze 或等效钩子；记录超时。

  3. Pause vCPU

    通过 VMM API 暂停所有 vCPU，确保内存与设备状态不再变化。

  4. Flush

    刷宿主机页缓存（syncfs）、刷设备写缓存（blkdev_issue_flush）。

  5. Capture

    并行执行：CubeCoW 克隆 rootfs（reflink）+ 导出内存（full/diff）+ 保存设备状态；记录时间戳与版本。

  6. Commit

    写元数据（原子 rename / 事务），标记快照可用；更新引用计数。

  7. Resume

    恢复 vCPU、thaw 文件系统；任何一步失败都走回滚。

  8. GC / Verify

    异步校验（checksum、可挂载性），并按引用计数回收过期快照。

快照创建接口必须接受客户端幂等键；服务端用 Redis 分布式锁（CubeSandbox 已有）按 sandbox_id 串行化，避免同一沙箱并发快照；元数据写入用「临时文件 + fsync + rename」保证原子性；引用计数用数据库事务或 Redis Lua 脚本。

22.2 控制器骨架（Go 伪代码）

func (c *Controller) CreateSnapshot(ctx context.Context, req SnapshotRequest) (*Snapshot, error) {
    // 1. 幂等：同一 idempotency_key 直接返回已有快照
    if s, err := c.store.GetByIdempotencyKey(ctx, req.IdempotencyKey); err == nil {
        return s, nil
    }

    // 2. 同一沙箱串行化（Redis 分布式锁）
    unlock, err := c.locks.Acquire(ctx, "snapshot:"+req.SandboxID)
    if err != nil { return nil, err }
    defer unlock()

    // 3. 预检：reflink 支持、剩余空间、节点资源
    if err := c.precheck(ctx, req.SandboxID); err != nil { return nil, err }

    s := &Snapshot{ID: newID(), SandboxID: req.SandboxID, State: StateCreating}
    if err := c.store.Create(ctx, s); err != nil { return nil, err }

    // 4. 冻结 + 暂停（任一失败都回滚）
    if err := c.shim.Freeze(ctx, req.SandboxID, req.Timeout); err != nil {
        return c.fail(ctx, s, err)
    }
    defer c.shim.Thaw(ctx, req.SandboxID)

    if err := c.shim.Pause(ctx, req.SandboxID); err != nil {
        return c.fail(ctx, s, err)
    }
    defer c.shim.Resume(ctx, req.SandboxID)

    // 5. 刷页缓存 + 设备缓存
    if err := c.node.Flush(ctx, req.SandboxID); err != nil {
        return c.fail(ctx, s, err)
    }

    // 6. 并行：磁盘 reflink + 内存导出
    if err := c.cow.Clone(ctx, req.SandboxID, s.ID); err != nil {
        return c.fail(ctx, s, err)
    }
    if err := c.vmm.ExportMemory(ctx, req.SandboxID, s.ID, req.Type); err != nil {
        return c.fail(ctx, s, err)
    }

    // 7. 原子提交 + 校验和
    s.State = StateReady
    s.Checksum = c.checksum(s)
    return s, c.store.Commit(ctx, s)
}
实现要点

① defer 顺序：先 defer thaw 再 defer resume，保证退出时「先恢复 vCPU 再解冻」还是反过来要按你的 VMM 语义确认（通常先 resume 再 thaw）。② 失败回滚：fail() 必须清理临时文件并释放 refcount。③ 超时：所有 gRPC 调用都要带 context deadline，避免级联卡死。④ 校验和：至少对快照元数据做 checksum，内存文件按块做可选校验。
