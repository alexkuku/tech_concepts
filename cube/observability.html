可观测性部署、日志与追踪

这一页把 CubeSandbox 的「可观测性」讲透：指标（Prometheus）、日志（Loki / Elasticsearch）、追踪（OTel / Tempo / Jaeger）三类信号如何从 Cubelet 与沙箱采集，经 OTel Collector 汇聚到后端与 Grafana；以及 one-click、Helm、对接外部平台、独立安装四种落地方式，和沙箱日志、分布式追踪、性能基准入口。指标口径细节见第 14 章，故障定位手法见第 15 章。

1可观测性总体架构

CubeObservability 为 CubeSandbox 提供开箱即用的沙箱资源指标与沙箱日志可观测性方案。它在 one-click（CVM / 裸金属）与 Kubernetes Helm 安装流程中默认关闭，用一个环境变量或一个 Helm Value 即可按需开启，并且同时支持两条路径：

  • 内置全栈：Prometheus + Loki（或 Elasticsearch）+ Grafana 一次部署到位；
  • 对接外部平台：团队已有监控 / 日志平台时，只部署节点侧 Collector，把数据推过去。

整体是「节点侧轻量采集 + 中心侧集中存储与展示」的三层架构：不改动 Cubelet 自身逻辑，并保持后端可替换——换掉 Prometheus / Loki / ES 不影响采集侧。

📊

指标 Metrics

抓取本机 Cubelet 127.0.0.1:9998/v1/metrics/resource，覆盖沙箱 CPU、内存及节点沙箱计数共 24 个指标族，自动带 cluster / node 标签，存入 Prometheus（:9092）。

📜

日志 Logs

用 filelog 实时 tail 沙箱目录 /data/cubelet/log/<sandbox-id>/{stdout,stderr}，自动解析 sandbox_id 与 stdout/stderr，存入 Loki（:3100）或 Elasticsearch（:9200）。

🧵

追踪 Traces

沙箱生命周期操作以 W3C Trace Context 贯穿五个服务，经 OTLP/gRPC 上报到外部 Collector 或 Tempo 接收端；Grafana 侧 3 张指标看板 + 1 张日志看板。

数据流：从采集到看板

每个计算节点上的 OTel Collector 用独立管道分别上报指标和日志，并把文件读取游标与 OTLP 发送队列持久化到本机磁盘（systemd 为 /var/lib/cube-sandbox/otelcol/storage，Helm 为 /var/lib/cube-sandbox/otelcol-k8s），进程重启或后端短暂抖动时可续传。

3安装前自检

如果节点已经安装 Cubelet，可先确认指标接口和日志路径就绪；全新 one-click 安装可直接跳到第 4 节。自检三件事：Cubelet 版本、资源指标接口、沙箱日志路径。

节点自检 
# 1. 检查 Cubelet 版本与运行状态
/usr/local/services/cubetoolbox/Cubelet/bin/cubecli version
sudo systemctl is-active cube-sandbox-cubelet.service

# 2. 检查沙箱资源指标接口
curl -fsS http://127.0.0.1:9998/v1/metrics/resource | \
  grep -E '^cubesandbox_(host_sandbox|guest_workload|node_sandbox_)'

# 3. 如有运行中的沙箱，检查其 stdout/stderr 日志路径
SANDBOX_ID=<替换为实际沙箱ID>
ls -l "/data/cubelet/log/${SANDBOX_ID}"/{stdout,stderr}
判读口径：没有活跃沙箱时，逐沙箱指标与日志可以为空，但 cubesandbox_node_sandbox_count 和 cubesandbox_node_sandbox_available_count 应返回 0——它们代表节点级计数，与是否有沙箱运行无关。

one-click 部署（CVM / 裸金属）

步骤 1：部署第一台 all-in-one 节点

进入 deploy/one-click（或解压后的发布包根目录），首次安装时创建 .env：

cd deploy/one-click
[[ -f .env ]] || cp env.example .env
chmod 600 .env

在 .env 中填入可被计算节点访问的内网 IP 和可观测性参数（如需 Elasticsearch，将 CUBE_LOGS_BACKEND 改为 elasticsearch）：

CUBE_SANDBOX_NODE_IP=10.0.0.10
ONE_CLICK_ENABLE_OBSERVABILITY=1
CUBE_OBSERVABILITY_CLUSTER_ID=cube-prod
CUBE_LOGS_BACKEND=loki
CUBE_GRAFANA_ADMIN_PASSWORD='<随机且至少16字符的密码>'

执行常规安装命令，并确认最终生效的内网 IP（供后续计算节点使用）：

sudo ./install.sh
grep '^CUBE_SANDBOX_NODE_IP=' /usr/local/services/cubetoolbox/.one-click.env

步骤 2：部署后续计算节点

在每台计算节点准备同版本发布包与 .env，填写第一台节点内网 IP（保持集群 ID 和日志后端一致），然后执行 install-compute.sh：

# .env
ONE_CLICK_CONTROL_PLANE_IP=10.0.0.10
ONE_CLICK_ENABLE_OBSERVABILITY=1
CUBE_OBSERVABILITY_CLUSTER_ID=cube-prod
CUBE_LOGS_BACKEND=loki
sudo ./install-compute.sh

install-compute.sh 会自动识别计算节点角色，仅安装本机 OTel Collector，并自动推导第一台节点的 Prometheus（:9092）与日志后端（:3100 或 :9200）地址。

步骤 3：在存量 one-click 集群中启用或关闭

保留原安装目录中的 .env（不要用 env.example 覆盖，也不要直接编辑 /usr/local/services/cubetoolbox/.one-click.env）：

  1. 在第一台节点的 .env 中添加上述可观测性变量，执行升级：sudo ./install.sh --mode=upgrade --yes
  2. 第一台节点验收通过后，在各计算节点的 .env 中添加对应变量，执行升级：sudo ./install-compute.sh --mode=upgrade --yes
sudo ./install.sh --mode=upgrade --yes
sudo ./install-compute.sh --mode=upgrade --yes
不会误关：升级时默认配置中的 ONE_CLICK_ENABLE_OBSERVABILITY=0 不会关掉已启用的监控；如需明确关闭，执行 sudo env ONE_CLICK_ENABLE_OBSERVABILITY=0 ./install.sh --mode=upgrade --yes（计算节点用 ./install-compute.sh）。

补充：在线一键安装（online-install.sh）

如需直接通过在线脚本安装，可通过 env 透传相同变量。涉及外部鉴权 Token 等敏感信息时，建议下载 release 包并写入 0600 权限的 .env，避免残留在 shell 历史中。

# 第一台 all-in-one 节点
GRAFANA_ADMIN_PASSWORD="$(openssl rand -hex 16)"
echo "Grafana admin password: ${GRAFANA_ADMIN_PASSWORD}"
curl -fsSL https://raw.githubusercontent.com/tencentcloud/CubeSandbox/master/deploy/one-click/online-install.sh \
  | sudo env ONE_CLICK_ENABLE_OBSERVABILITY=1 \
      CUBE_OBSERVABILITY_CLUSTER_ID=cube-prod \
      CUBE_LOGS_BACKEND=loki \
      CUBE_GRAFANA_ADMIN_PASSWORD="${GRAFANA_ADMIN_PASSWORD}" \
      bash

# 后续计算节点
curl -fsSL https://raw.githubusercontent.com/tencentcloud/CubeSandbox/master/deploy/one-click/online-install.sh \
  | sudo env ONE_CLICK_DEPLOY_ROLE=compute \
      ONE_CLICK_CONTROL_PLANE_IP=10.0.0.10 \
      ONE_CLICK_ENABLE_OBSERVABILITY=1 \
      CUBE_OBSERVABILITY_CLUSTER_ID=cube-prod \
      CUBE_LOGS_BACKEND=loki \
      bash

Kubernetes Helm 部署

在现有 runtime-values.yaml（含数据库、Redis 凭据及节点调度配置）基础上，追加 observability.* 参数即可。以下为使用内置后端的快速部署：

helm upgrade --install cube ./deploy/kubernetes/chart \
  -n cube-system --create-namespace \
  -f /path/to/runtime-values.yaml \
  --set observability.enabled=true \
  --set observability.clusterId=k8s-prod \
  --set observability.logs.backend=loki

获取 Grafana 密码：Chart 默认生成 release 级随机密码 Secret 并在升级时复用，通过以下命令读取（生产环境建议提前创建 Secret 并配置 observability.backend.grafana.existingSecret）：

kubectl get secret -n cube-system \
  -l app.kubernetes.io/component=grafana-admin \
  -o jsonpath='{.items[0].data.admin-password}' | base64 --decode; echo
  • 切换为 Elasticsearch：将 --set observability.logs.backend=loki 改为 --set observability.logs.backend=elasticsearch。
  • 开启组件容器日志采集（可选）：追加 --set observability.logs.components.enabled=true。这会启动第二个只读 DaemonSet，仅采集当前 namespace 下白名单容器（默认 cube-master、cube-api、cube-ops、cube-templatecenter、cubelet、cube-proxy、cube-lifecycle-manager）在 /var/log/pods 中的新增日志。开启前请确认组件日志不含明文密钥。
  • 所有内置监控 Pod 均配置了 readiness / liveness probe 用于健康检查和自动重启（不包含 Alertmanager 告警规则）。

对接外部监控与日志平台（含鉴权）

如果团队已有 Prometheus / VictoriaMetrics / Loki / Elasticsearch 或托管可观测性平台，可以只部署节点 Collector，将数据推送到外部后端。

互斥与安全约束：
  • 指标输出端（OTLP/HTTP 与 Remote Write）只能二选一；日志输出端（Loki OTLP 与 Elasticsearch）同样只能二选一。
  • 鉴权配置仅用于 Collector 与 Grafana 客户端请求头，不会给内置后端开启服务端认证。
  • HTTPS 端点默认校验证书（使用系统 / 容器 CA）；私有 CA 场景请挂载信任链，勿长期关闭 TLS 校验。

方式 A：one-click / systemd 对接外部后端

在 .env 中显式配置外部地址后，ONE_CLICK_OBSERVABILITY_ROLE=auto 会自动跳过本地后端，仅安装节点 Collector：

ONE_CLICK_ENABLE_OBSERVABILITY=1
ONE_CLICK_OBSERVABILITY_ROLE=auto
CUBE_OBSERVABILITY_CLUSTER_ID=cube-prod
CUBE_LOGS_BACKEND=loki

# 外部指标与日志地址（OTLP 填基础路径，不要附加 /v1/metrics 或 /v1/logs）
CUBE_METRICS_OTLP_HTTP_ENDPOINT=https://prometheus.example.com/api/v1/otlp
CUBE_LOGS_OTLP_HTTP_ENDPOINT=https://loki.example.com/otlp

# 外部后端鉴权（可选；*_AUTHORIZATION 填完整 Header，*_TOKEN 填裸 Token，二者不可同时设置）
CUBE_METRICS_AUTHORIZATION='Bearer <metrics-token>'
CUBE_METRICS_TENANT_ID=cube-prod

建议监控告警表达式（PromQL）

安装器默认不部署 Alertmanager 或告警规则。以下 PromQL 可作为告警起点（CPU、节流、内存占比和采样不可用建议加 for: 5m；内存限制失败建议立即触发；占比类表达式仅适用于配置了有限配额的沙箱）：

# 沙箱 CPU 使用率超过 80%
100 * rate(cubesandbox_host_sandbox_cpu_usage_seconds_total[5m])
  / clamp_min(cubesandbox_host_sandbox_cpu_limit_cores, 0.001) > 80

# CPU 节流周期占比超过 20%
100 * rate(cubesandbox_host_sandbox_cpu_throttled_periods_total[5m])
  / clamp_min(rate(cubesandbox_host_sandbox_cpu_periods_total[5m]), 0.001) > 20

# 沙箱内存使用率超过 85%
100 * cubesandbox_host_sandbox_memory_current_bytes
  / clamp_min(cubesandbox_host_sandbox_memory_limit_bytes, 1) > 85

# 最近 5 分钟内出现内存限制失败
increase(cubesandbox_host_sandbox_memory_failures_total[5m]) > 0

# 存在沙箱但当前无可用资源采样
cubesandbox_node_sandbox_count - cubesandbox_node_sandbox_available_count > 0

6沙箱日志

功能迭代中：日志能力目前仍在持续迭代，cubecli logs 命令是临时使用版本——后续版本可能对接口及底层存储结构进行调整。

CubeSandbox 提供两个互补的日志层，不要混淆：

层级记录内容获取方式
沙箱日志容器 init 进程（主入口）的 stdout/stderrcubecli logs（本节）
envd 任务日志在沙箱内通过 exec 接口启动的子任务的 stdout/stderrE2B SDK（on_stdout / on_stderr 回调）

前置条件

cubecli 随 Cubelet 一同构建，并在一键部署时自动安装。logs 子命令访问的日志文件位于 Cubelet 挂载命名空间内，因此必须直接在计算节点上执行，无法通过 API 或非节点主机远程调用。

读取沙箱日志

# 最后 100 行 stdout（默认）
cubecli logs <sandbox-id>

# 最后 100 行 stderr
cubecli logs --stderr <sandbox-id>

# 完整日志（全部行）
cubecli logs --all <sandbox-id>

# 最后 N 行
cubecli logs --tail 50 <sandbox-id>
# 简写
cubecli logs -t 50 <sandbox-id>

# 前 N 行
cubecli logs --head 20 <sandbox-id>
# 简写
cubecli logs -H 20 <sandbox-id>
参数简写说明
--stderr-e读取 stderr，默认读取 stdout
--all-a输出全部行；不可与 --tail 或 --head 同时使用
--tail N-t N输出最后 N 行（未指定其他标志时默认为 100）
--head N-H N输出前 N 行

读取模板构建日志

模板构建过程中，容器的 stdout/stderr 会写入宿主机文件系统 /data/log/template/<templateID>_0/。这些文件无需进入 Cubelet 挂载命名空间，使用 --tpl 标志可跳过命名空间切换：

# 最后 100 行模板构建 stdout
cubecli logs --tpl <template-id>

# 完整模板构建 stderr
cubecli logs --tpl --all --stderr <template-id>

日志文件路径

场景路径
沙箱 stdout/data/cubelet/state/io.containerd.runtime.v2.task/default/<sandbox-id>/stdout（Cubelet 挂载命名空间内）
沙箱 stderr/data/cubelet/state/io.containerd.runtime.v2.task/default/<sandbox-id>/stderr（Cubelet 挂载命名空间内）
模板 stdout/data/log/template/<template-id>_0/stdout（宿主机文件系统）
模板 stderr/data/log/template/<template-id>_0/stderr（宿主机文件系统）
为什么需要挂载命名空间？沙箱日志文件由 CubeShim 写入 bundle 目录，该目录仅在 Cubelet 的私有挂载命名空间内可见。cubecli logs 会在读取前自动重新进入该命名空间——你无需任何额外操作，只需在节点上直接运行该命令即可。

范围与限制

  • 这些日志仅记录 init 进程（容器内 PID 1）的输出。通过 exec 接口启动的进程输出需通过 E2B SDK 的 on_stdout / on_stderr 回调获取。
  • 日志转发需要 v0.4.0 及以上版本的 CubeShim。在更旧的部署上，日志文件将不存在。
  • 日志目前不支持实时流式读取，暂无 --follow 标志。如需查看最新输出，请重新执行命令。
  • 沙箱删除后，对应的日志文件会一并清除。

7分布式链路追踪

日志和指标能告诉你某次沙箱操作慢或失败了，却很少告诉你卡在哪一步。分布式链路追踪为每次操作记录一条 trace，经过的每个组件、每个已插桩的阶段各有一个 span。创建沙箱、从镜像构建模板、暂停与恢复沙箱都要依次经过多个组件，追踪能展示时间花在这些阶段的哪些地方。

被追踪的工作流

工作流入口trace 展示的内容
创建沙箱（含从快照创建）POST /sandboxes入队与调度、节点选择、创建容器，恢复场景下还有快照准备与 VM 恢复
镜像转模板POST /templates镜像构建、rootfs/ext4、产物发布、分发
沙箱转模板（commit）POST /cube/sandbox/commit横跨 CubeMaster 与 Cubelet 的大致阶段：Master 上的提交、运行、快照与注册，Cubelet 上的抓取与发布
创建快照POST /sandboxes/:sandboxID/snapshots准备、抓取、注册
回滚POST /sandboxes/:sandboxID/rollback准备、恢复、注册
暂停 / 恢复POST /sandboxes/:sandboxID/pause、.../resume准备、抓取或运行时、收尾

Span 来自五个上报服务，各以各自的服务名上报：

服务在 trace 中的角色
cube-api经 CubeAPI 发起的请求的 HTTP 入口 span
cubemaster编排：调度、派发、异步任务生命周期
cubetemplatecenter模板镜像构建与产物处理
cubelet单节点运行时工作流与生命周期锁
cube-shim单沙箱 VMM 启动、引导或恢复、容器启动

containerd 插桩还会记录 Task、RPC 和传输等 span，并使用调用方服务的身份上报。

一次沙箱创建的 span 树

下面是一次创建沙箱的 span 层级示意（左侧时间线标签为上报服务，仅展示主干；官方试点中一次创建产生 52 个 span，实际层级与耗时以真实 trace 为准）。

POST /sandboxes（入口 span）

cube-apiHTTP 入口，携带 W3C traceparent，是整条 trace 的根。

入队与调度

cubemaster接收创建请求，进入调度队列。

节点选择

cubemaster按资源与策略挑选目标计算节点。

派发创建

cubemaster把创建任务下发到目标 Cubelet。

创建容器 + 生命周期锁

容器启动

cube-shim容器进程启动，完成后向上返回。

（恢复场景）快照准备 + VM 恢复

master / cubelet从快照创建时，在创建链路上额外出现快照准备与 VM 恢复 span。

启用追踪

追踪默认关闭。把各组件各自的 OTEL_EXPORTER_OTLP_ENDPOINT 指向外部自备的 OTLP/gRPC 接收端——OpenTelemetry Collector 或 Tempo 的 OTLP/gRPC 接收端——取值为 http://<receiver-host>:<OTLP-gRPC-port>。

  • 也可以设置 OTEL_EXPORTER_OTLP_TRACES_ENDPOINT；同时设置时 traces 专用地址优先。仅当两个值都为空时关闭追踪。
  • 启用后使用 SDK 默认的基于父级、始终采样策略：根请求和本地启动的生命周期 Trace 以 100% 采样，已采样的父级会跨服务继续采样。尚不支持配置采样率，请据此规划 Collector 和后端容量。
  • 试点中一次沙箱创建产生了 52 个 Span；按相似流程估算，1,000 次创建约产生 52,000 个 Span，尚未计入暂停、恢复、快照和模板流量。实际数量取决于流程与部署。
  • 接收端和查询后端需要单独部署。各组件以各自的服务名上报，因此不要设置共享的 OTEL_SERVICE_NAME。

安装方式配置位置说明

Kubernetes加到各组件的 env 数组中参见 Helm 安装中的「8.4 链路追踪配置」

Cubelet 为每个沙箱启动一个全新的 CubeShim 进程；该进程在启动时继承 Cubelet 的环境变量，因此已在运行的 shim 会保留旧设置。Cubelet 在 task.Start 前注册 containerd 的 task.Wait：任务启动后等待会有意持续到任务退出，创建请求取消或超时不会丢失退出事件；等待上下文只保留 containerd 命名空间，不继承请求取消、日志字段或已结束的创建 Span；若任务启动失败，则取消等待。

Rust envd REST 追踪

要启用 Rust envd 追踪，请在 envd 启动时读取的沙箱环境中设置 CUBE_ENVD_OTEL_ENDPOINT。取值是沙箱内可访问的完整 OTLP/HTTP protobuf 追踪地址，例如 http://<receiver>:4318/v1/traces。控制面的 OTLP 地址变量不会启用 envd 追踪。

携带已采样 W3C traceparent 的 REST 请求会生成 envd Server Span，并接在对应的父 Span 下。父上下文可以由 CubeProxy 传入。后台上报失败会写入 envd 日志，REST 请求照常处理。

查询与解读耗时

可以按 trace ID 查询，也可以用接口返回的某个 ID。响应里的标识与 span 属性并不总是同一个字符串，而且它们都不是 trace ID：

你手上的标识span 属性
创建沙箱响应中的 clientID（该次创建的业务请求 ID）cube.request_id（仅创建场景）
沙箱 IDcube.sandbox_id
模板 IDcube.template_id
快照 IDcube.snapshot_id
异步任务 ID（jobID / job_id）cube.job_id
只有创建响应是这样映射的：详情或列表响应里的 clientID 可能是宿主机 ID，不要一概而论。HTTP 请求头 x-request-id 是另一回事——它对应 CubeAPI 入口 span 上的 cube.http_request_id。

属性只需存在于部分 span 上就能找到整条 trace：只要任一个 span 匹配，整条 trace 就会被返回。下面示例使用 Tempo 的 TraceQL，其他后端有各自的查询语言。

{ span.cube.request_id = "<creation-client-id>" }
{ span.cube.sandbox_id = "<sandbox-id>" }
{ span.cube.job_id = "<job-id>" }

同一个沙箱 ID 可能对应保留期内的多次操作，可按操作发生时间缩小查询范围。查不到时，先确认查询时间范围覆盖了操作时间。失败请求可能尚未生成沙箱或快照 ID，这时可用已有的 cube.request_id 查询。

如何解读耗时

  • 父 span 的耗时一般包含其嵌套工作，因此不要在它之上再累加嵌套耗时。脱离请求生命周期的异步子 span 可能超出父 span；父子重叠属于正常的嵌套——只有时间上重叠的兄弟任务才提示存在并行。
  • 子 span 的耗时之和不一定等于父 span 的耗时；阶段间的空隙可能包含等待或尚未单独埋点的工作。
  • 异步模板任务的存活时间超过提交它的 API span。提交 span 只度量提交动作，构建与运行的 span 记录后台执行，但整个「提交到就绪」的任务未必是单个 span——是否成功要以任务状态为准，不能只看 span。
  • 业务失败仍可能返回 HTTP 200。要一并检查 span 状态与业务属性（cube.ret_code）以及 HTTP 状态码，而不是只相信后者。
追踪回答的是「卡在哪一步」，不是「为什么」。当某个偏慢或失败的 span 指向某个组件的某个阶段后，原因通常就在该组件的日志里——参见本页第 6 节的沙箱日志，以及第 12 章的服务管理与日志。

9易错点与最佳实践

下面这些点几乎覆盖了可观测性落地时最常见的「踩坑」，按主题分组记忆。

端口与网络

  • Prometheus 用 9092 不是 9090：9090 已被 cube-proxy 占用，配置里出现 9090 多半是抄错了。
  • 内置后端无服务端鉴权：Prometheus / Loki / ES 只对计算节点内网放通 9092、3100、9200，切勿暴露公网；跨网段请前置认证网关。
  • OTLP 填基础路径：外部地址不要附加 /v1/metrics 或 /v1/logs，例如 https://prometheus.example.com/api/v1/otlp、https://loki.example.com/otlp。

互斥关系

  • 指标输出端 OTLP/HTTP 与 Remote Write 二选一；日志输出端 Loki OTLP 与 Elasticsearch 二选一；同一部署只启用一个日志后端，不会双写。
  • *_AUTHORIZATION（完整 Header）与 *_TOKEN（裸 Token）不可同时设置；ES 的 CUBE_LOGS_ES_API_KEY 与 Basic Auth 也二选一。

安装与升级

  • 不要用 env.example 覆盖现有 .env，也不要直接编辑 /usr/local/services/cubetoolbox/.one-click.env；升级用 --mode=upgrade --yes。
  • 升级不会误关已启用的监控（默认 ONE_CLICK_ENABLE_OBSERVABILITY=0 不生效）；要关闭需显式传 ONE_CLICK_ENABLE_OBSERVABILITY=0。
  • Grafana 密码至少 16 个字符且首尾不含空白；生产环境用 existingSecret 管理，别把密码写进 --set 历史。
  • 别手改运行态配置：/etc/cube-sandbox/otelcol/otelcol.yaml 与 ConfigMap 会被重装 / 升级覆盖，改配置请改生成器，并用 install.sh render cvm / helm template ... -s templates/observability.yaml 预览。
  • Helm 抓取周期不得小于 10s 超时；大规模建议保持默认 15s。Helm 形态需保持 cubeNode.hostNetwork=true，否则同节点 Collector 访问不到 127.0.0.1:9998。

日志与追踪

  • 沙箱销毁即删日志目录：必须在沙箱存活期间持续上报，否则日志随沙箱一起丢失。
  • cubecli logs 必须在计算节点执行；只覆盖 init 进程（PID 1）；没有 --follow；日志转发需 CubeShim ≥ v0.4.0。
  • 追踪不要设共享 OTEL_SERVICE_NAME：五个服务各用自己的服务名上报；采样率当前不可配，容量按 100% 采样规划。
  • 业务失败可能返回 HTTP 200：排障时同时看 span 状态、cube.ret_code 与 HTTP 状态码。
  • 组件容器日志从文件末尾开始采集、不回放历史；开启前确认组件日志不含明文密钥。one-click 暂不支持组件日志采集。
最容易被忽略的一条：「指标看板数值加起来等于整机」是错的——内存限额是已导出有限限额之和，Host Sandbox 与 Guest Workload 记账口径不同、不可直接相加；缺样本也不等于 0。解读看板前先确认口径。

自测（3 题）

1. 你发现指标看板没有数据，但 curl 127.0.0.1:9998/v1/metrics/resource 有输出。先怀疑哪几件事？

先查三层链路：① Collector 是否在跑（systemctl status cube-sandbox-otelcol 或 rollout status daemonset/cube-node-otelcol）；② 是否连到了正确的 :9092（注意不是 9090）；③ 外部场景下 OTLP 基础路径是否被误加了 /v1/metrics；④ Helm 形态是否保持 cubeNode.hostNetwork=true。沙箱维度为空是正常的，需看节点级 node_sandbox_count。

2. 为什么 cubecli logs <sandbox-id> 在 CI 机器上执行失败，在计算节点上却正常？

因为沙箱日志文件位于 Cubelet 的私有挂载命名空间内（/data/cubelet/state/io.containerd.runtime.v2.task/default/<sandbox-id>/{stdout,stderr}），cubecli logs 必须在计算节点本机执行、由它自动重入该命名空间；无法通过 API 或非节点主机远程调用。此外还要求 CubeShim ≥ v0.4.0。

3. 一条创建沙箱的 trace 里，子 span 耗时加起来小于父 span，是不是丢了数据？业务失败但 HTTP 200，该怎么判断？

不是丢数据。父 span 的耗时包含嵌套工作，子 span 之和不一定等于父 span；阶段间的空隙可能包含等待或尚未单独埋点的工作，父子重叠也是正常嵌套。业务失败可能返回 HTTP 200，必须同时检查 span 状态、业务属性 cube.ret_code 与 HTTP 状态码；「为什么失败」往往要去对应组件的日志里找。
