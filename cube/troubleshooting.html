1排障方法论：先分层，再定位信号

一次沙箱创建会穿过 CubeAPI、CubeMaster、Cubelet、CubeShim、VMM、网络与存储等多个环节。遇到故障时不要一上来就翻日志，而是按「先分层 → 再定位信号 → 最后验证」的顺序，把「全链路都挂了」收敛成「某一层的某一个组件」。

先分层：判断问题出在控制面、计算面、网络、存储、模板还是沙箱内部。
↓
再定位信号：用日志、指标、状态三类信号，锁定最小可疑组件。
↓
最后验证：复现一次、修复一次、观察一次，确认根因而非掩盖症状。

1.2 症状 → 先查什么

下面把高频故障的「第一跳」固化下来：看到这条症状，先执行这一条命令，再决定是否深入。

创建 500 / 超时

先看路由与探测

context deadline exceeded 或 PortBindingFailed：先 ip route 再 rg PortBindingFailed /data/log/Cubelet/Cubelet-req.log，多为 CIDR 冲突（§5）。

预检 not bpf

先确认 bpffs

报「不是 bpf 文件系统」时，先 grep -w bpf /proc/filesystems；有输出就挂载，无输出则内核不支持 eBPF（§3）。

预检 not XFS

先确认文件系统

one-click 报 not XFS：df -T /data/cubelet 查看是否 ext4 根盘，需要 XFS 的 reflink（§3）。

模板卡住

先看磁盘余量

卡在 UNPACKING / BUILDING_EXT4：df -h /tmp /data/cubelet /usr/local/services/cubetoolbox（§4）。

DISTRIBUTING 超时

先分 job phase

DISTRIBUTING 看 create_image_timeout_insec，CREATING_TEMPLATE 看 app_snapshot_timeout_insec；先查节点健康再动超时（§4）。

Host Mount 拒绝写

先对齐 UID

写 /mnt/rw 报 Permission denied：先在容器内 id，再在宿主机 stat -c 'owner=%u:%g mode=%a' 对比（§6）。

3部署问题：bpffs、XFS 与 cgroup

one-click 部署会在修改系统之前做前置检查，检查不通过时直接退出——这是「不把机器改坏」的保护。遇到预检失败，先按下面三项逐一对齐，再重新执行安装。

3.1 bpffs 未挂载

Cubelet 内嵌的网络运行时依赖 /sys/fs/bpf 挂载 bpffs（bpf 文件系统），用于固定（pin）eBPF 程序与 Map。若该目录不是 bpf 文件系统（WSL2 或部分极简 Linux 默认未挂载），安装器会在修改系统前退出。

步骤命令期望结果
1. 确认内核支持 grep -w bpf /proc/filesystems 有 bpf 输出则继续；无输出说明内核未启用 eBPF（缺 CONFIG_BPF_SYSCALL）
2. 挂载 bpffs mkdir -p /sys/fs/bpf
mount -t bpf bpf /sys/fs/bpf		 无报错，/sys/fs/bpf 可写
3. 持久化（可选） 在 /etc/fstab 添加 bpf /sys/fs/bpf bpf defaults 0 0 重启后仍保持挂载 
# 1) 确认内核是否支持 bpf 文件系统
grep -w bpf /proc/filesystems

# 2) 若支持，创建目录并挂载（需要 root）
mkdir -p /sys/fs/bpf
mount -t bpf bpf /sys/fs/bpf
持久化写法：把下面这一行加入 /etc/fstab，可让 bpffs 在重启后自动挂载。 
bpf /sys/fs/bpf bpf defaults 0 0
内核不支持时不要硬装：若 grep -w bpf /proc/filesystems 无任何输出，说明当前内核缺少 CONFIG_BPF_SYSCALL，需升级或更换支持 eBPF 的内核后再试，挂载命令本身不会成功。

3.2 /data/cubelet 必须是 XFS（reflink）

cubelet 把 /data/cubelet 作为容器可写层的存储目录，依赖 XFS 的 reflink 特性。在 Ubuntu / Debian / WSL 等 ext4 根盘的环境上部署，one-click 前置检查会以 not XFS 报错退出。

项目要求 / 做法
文件系统挂载到 /data/cubelet 的分区必须是 XFS，并启用 reflink
自查命令df -T /data/cubelet
临时 Workaround用 loopback .img 格式化为 XFS 后挂到 /data/cubelet
生产建议挂独立 XFS 数据盘（100–300 GiB）
新装机推荐OpenCloudOS 9 / RHEL 系
 
# 确认 /data/cubelet 当前的文件系统类型
df -T /data/cubelet

3.3 Ubuntu 上 cgroup v2 未启用 cpu controller

现象是 cubelet 的 CPU quota 不生效。根因有两层：Ubuntu / Debian 云镜像默认不会把 cgroup v2 的 cpu controller 委托到子 cgroup；同时 multipathd 的 RT 线程会让 +cpu 写入返回 Invalid argument。完整复现与修复步骤见官方 issue #366。

只写源文档确认的结论：该问题在源文档中仅给出「根因 + 指向 issue #366」，未给出可复制的一键修复命令。动手前请先阅读 issue 再操作，避免照搬过期方案。

4模板问题：构建失败、超时与磁盘

模板制作本质上是「拉取 OCI 镜像 → 解压 → 写成 ext4 磁盘文件 → 分发 → 创建快照」的流水线。卡住的阶段不同，根因与超时配置也不同，先看 job phase 再动手。

4.1 先认阶段，再找超时

模板制作因 RPC deadline 失败时，修改 timeout 前先检查 job phase：不同阶段由不同的超时配置限制，盲目调大会掩盖故障节点。

job phase / 现象在做什么对应的超时配置先查什么
UNPACKING解压 OCI 镜像受临时磁盘空间影响分区余量、inode 是否耗尽
BUILDING_EXT4把解压结果写成 ext4 磁盘文件受临时磁盘空间影响磁盘余量、mkfs.ext4 校验和/inode 报错
DISTRIBUTING分发镜像数据create_image_timeout_insec节点健康、网络连通性、Cubelet 日志
CREATING_TEMPLATE创建模板快照app_snapshot_timeout_insec节点健康、磁盘、Cubelet 日志
正确顺序：先检查节点健康、剩余磁盘空间、网络连通性和 Cubelet 日志；确认只是正常操作较慢后，再修改 CubeMaster cubelet_conf 中对应的 create_image_timeout_insec / app_snapshot_timeout_insec，并重启 CubeMaster。

4.2 磁盘空间不足导致制作失败

制作模板时需要把 OCI 镜像解压并写入磁盘文件，会占用大量临时空间。当 /tmp、/data/cubelet 或 /usr/local/services/cubetoolbox/ 所在分区空间不足时，模板可能卡在 UNPACKING / BUILDING_EXT4 阶段，或表现为 mkfs.ext4 校验和不匹配、inode 类型冲突等错误。

# 三个关键分区都要看，任意一个满都可能卡住构建
df -h /tmp /data/cubelet /usr/local/services/cubetoolbox

4.3 tpl create-from-image 总是超时

tpl create-from-image 超时通常有两类主因：

  • probe 服务未启动：自定义镜像没有启动 --probe / --probe-path 配置的 HTTP 服务（使用 envd 的镜像通常配置为 49983/health）。
  • 嵌套虚拟化：在 AWS EC2 等嵌套虚拟化环境部署，受 XSAVE 等指令集缺失影响，导致 MicroVM panic、嵌套页错误慢启动，撞上 VsockServerReady / probe budget。
主因验证方法解法
probe 未启动先在本地验证配置的 HTTP probe 是否可访问镜像需要 envd 时，按「bring-your-own-image」准备
嵌套虚拟化确认是否运行在 AWS EC2 等嵌套环境切换到 PVM 模式
 
# 验证镜像内 HTTP probe 是否可访问（envd 镜像通常暴露 49983/health）
curl -sS http://<host>:49983/health

4.4 沙箱网段冲突导致创建模板超时

若模板在 CREATING_TEMPLATE 阶段以 context deadline exceeded 失败，且宿主机局域网也使用 192.168.1.x，请直接跳到 §5 网络 CIDR 冲突：这不是模板本身的问题，而是沙箱 IP 与真实局域网重叠导致端口探测失败。

源文档边界：官方 troubleshooting 的 templates 页只覆盖 UNPACKING、BUILDING_EXT4、DISTRIBUTING、CREATING_TEMPLATE 等阶段，未给出更细的 PULLING / BUILDING 阶段名。排障时请以实际打印的 job phase 为准，不要套用不存在的阶段。

5网络 CIDR 冲突与残留 cube-dev

这是裸金属 / 本地物理机部署最常见的「创建模板超时」根因：Cube 默认给沙箱分配 192.168.0.0/18，一旦宿主机局域网也使用 192.168.1.x，两者重叠就会让探测流量走错网卡。

5.1 问题现象

创建模板在 CREATING_TEMPLATE 阶段失败：

cubemastercli run fail: template tpl-xx creation failed: context deadline exceeded

用 cube-bench 压测时，会看到大量 create 返回 500：

create HTTP 500: {"code":500,"message":"CubeMaster returned error code 130595: context deadline exceeded"}

5.2 环境信息

项目取值
Cube Sandbox 版本e29453
部署模式裸金属或本地物理机部署
宿主机 OS / 内核Ubuntu 22.04 / Linux 6.6
相关组件Cubelet、持久化 TAP 网卡

5.3 根因：更精确的路由抢走了流量

在本地物理机或裸金属部署时，Cube 会创建大量持久化 TAP 网卡，名称类似 z192.168.0.x 或 z192.168.1.x。其默认配置位于 Cubelet/config/config.toml，默认在 192.168.0.0/18 网段下创建 500 个 TAP 网卡：

[plugins]
  [plugins."io.cubelet.internal.v1.network"]
    object_dir = "/usr/local/services/cubetoolbox/cube-vs/network"
    eth_name = "eth0"
    tap_init_num = 500
    cidr = "192.168.0.0/18"

当宿主机同时存在两条相关路由时，192.168.1.0/24 比 /18 更精确，访问 192.168.1.40 会走真实物理网卡 enp56s0f0，而不是 Cube 的 cube-dev / TAP 路径，于是 Cubelet 探测沙箱端口时连不到真正的沙箱。

192.168.1.0/24enp56s0f0 · src 192.168.1.123
更精确 → 抢占/24 比 /18 更具体
192.168.0.0/18cube-dev · src 192.168.0.1

在 /data/log/Cubelet/Cubelet-req.log 里能看到对应证据：

5.4 解决方案：换一个不冲突的网段

把 Cubelet 的网络 CIDR 改成不和宿主机局域网冲突的网段（示例改为 172.31.64.0/18），并清理旧网卡后重启：

# 1) 先停止 Cube Sandbox 服务
sudo systemctl stop 'cube-sandbox-*.target'

# 2) 修改 Cubelet 网络 CIDR（示例：192.168.0.0/18 → 172.31.64.0/18）
sudo sed -i 's#cidr = "192.168.0.0/18"#cidr = "172.31.64.0/18"#' \
  /usr/local/services/cubetoolbox/Cubelet/config/config.toml

# 3) 删除旧的 cube-dev 与持久化 z* TAP 网卡
sudo ip link delete cube-dev 2>/dev/null || true
ip tuntap show | awk -F: '/^z[0-9]+\./{print $1}' \
  | xargs -r -n1 -I{} sudo ip tuntap del dev {} mode tap

# 4) 重启服务
sudo systemctl start 'cube-sandbox-*.target'

网段不再和宿主机局域网重叠后，重新创建模板即可成功。

5.5 残留 cube-dev：为什么 reboot 不够

停止 Cube Sandbox 服务不会删除 cube-dev dummy 网卡和持久化的 z<ip> TAP 设备，它们会一直残留，直到 reboot 或手动清理。用相同网段重装会自动复用现有 cube-dev，无需处理；但调整网段时，若新 CIDR 与残留的 cube-dev 网络重叠，预检会拦截：

[one-click] ERROR: CUBE_SANDBOX_NETWORK_CIDR '192.168.0.0/17' overlaps an existing cube-dev network (192.168.0.0/18).

  Changing the sandbox CIDR on a host that already has a cube network is
  disruptive: the old cube-dev and the persistent z* TAP devices are left
  stale. A reboot alone is NOT enough -- the systemd target is enabled and
  Cubelet 内置 network runtime 会在启动时按 config.toml 重建旧网络.

  To change the CIDR, fully reset the cube network first:
    sudo systemctl stop 'cube-sandbox-*.target'
    sudo ip link delete cube-dev 2>/dev/null || true
    ip tuntap show | awk -F: '/^z[0-9]+\./{print $1}' \
      | xargs -r -n1 -I{} sudo ip tuntap del dev {} mode tap
  then re-run install with the new CIDR.

  Or keep the existing CIDR (192.168.0.0/18) to reuse the current network.

  To bypass this check (not recommended), set:
    CUBE_SANDBOX_NETWORK_CIDR_SKIP_CONFLICT_CHECK=1
仅 reboot 并不够：systemd target 是 enabled 的，开机后 Cubelet 内置 network runtime 会按 config.toml 重建 cube-dev 和 TAP 设备。必须按报错中给出的步骤做确定性清理，再用新的 CUBE_SANDBOX_NETWORK_CIDR 重新安装。若新网段不与残留 cube-dev 重叠，预检放行，Cubelet 内置 network runtime 会把 cube-dev 协调到新网段。
不要用 bypass 硬闯：CUBE_SANDBOX_NETWORK_CIDR_SKIP_CONFLICT_CHECK=1 只是跳过检查，旧的 cube-dev 与 TAP 仍在，问题不会消失。

6Host Mount 写入 Permission Denied

Host mount 是「把 Cubelet 宿主机上的已有路径映射进沙箱」，它不会复制文件、不会创建工作区快照，也不会自动改写文件 owner。因此 Linux 权限照常生效，最常见的坑就是「能看见目录，却写不进去」。

6.1 问题现象

沙箱里可以看到 host mount 目录，但写入时报 Permission denied：

/bin/bash: line 1: /mnt/rw/1.txt: Permission denied

常见复现方式是创建一个可写 host mount：

import json
from cubesandbox import Sandbox

mounts = json.dumps([
    {
        "hostPath": "/tmp/rw",
        "mountPath": "/mnt/rw",
        "readOnly": False,
    },
])

with Sandbox.create(metadata={"host-mount": mounts}) as sandbox:
    sandbox.commands.run("echo hello > /mnt/rw/1.txt")

6.2 根因

  • hostPath 必须已经存在于运行该沙箱的 Cubelet 节点上。
  • 挂载目录会保留宿主机侧的 owner、group 和 mode bits。
  • 沙箱里的命令默认以沙箱用户身份运行。
  • 如果宿主机目录属于另一个 UID/GID，沙箱用户可能能读到目录，但不能写入。
关键结论：例如 /tmp/rw 在宿主机上属于 uid=1002，而沙箱命令以 uid=1000 运行，即使 readOnly 是 False，写 /mnt/rw 也可能失败。这是预期的 Linux 挂载行为——readOnly 只控制「只读还是读写挂载」，并不绕过宿主机文件系统权限。

6.3 先确认 host path 与 owner

sudo test -d /tmp/rw
sudo stat -c 'owner=%u:%g mode=%a path=%n' /tmp/rw

6.4 四种处理方案对比

方案适用场景关键命令 / 配置风险与注意
1. 只读挂载 agent 只需要读取和分析代码 "readOnly": True 最安全默认；无法写回宿主机
2. 对齐目录 owner 需要把结果写回宿主机目录 chown 1000:1000 /tmp/rw + chmod 0755 需先确认沙箱实际 UID/GID
3. 使用 ACL 宿主机 owner 不能改 setfacl -m u:1000:rwx /tmp/rw 保留原 owner，但增加 ACL 维护成本
4. 以 root 写入 管理类操作、可信 workload user="root" 可能生成 root-owned 文件，后续宿主机工具处理有权限差异

6.5 方案 1：代码工作区优先只读

import json
from cubesandbox import Sandbox

mounts = json.dumps([
    {
        "hostPath": "/srv/workspaces/my-repo",
        "mountPath": "/workspace",
        "readOnly": True,
    },
])

with Sandbox.create(metadata={"host-mount": mounts}) as sandbox:
    result = sandbox.commands.run("ls /workspace")
    print(result.stdout)

6.6 方案 2：读写挂载时对齐 owner

sudo mkdir -p /tmp/rw
sudo chown 1000:1000 /tmp/rw
sudo chmod 0755 /tmp/rw

如果沙箱镜像使用了不同用户，先在沙箱内确认实际 UID/GID，再用它去准备宿主机目录：

with Sandbox.create(metadata={"host-mount": mounts}) as sandbox:
    result = sandbox.commands.run("id && stat -c '%u:%g %a %n' /mnt/rw")
    print(result.stdout)

6.7 方案 3：宿主机 owner 不能改时用 ACL

sudo setfacl -m u:1000:rwx /tmp/rw
sudo setfacl -d -m u:1000:rwx /tmp/rw

这样可以保留原有宿主机 owner，同时允许沙箱用户写入新文件。

6.8 方案 4：仅在合适场景用 root 写入

with Sandbox.create(metadata={"host-mount": mounts}) as sandbox:
    sandbox.commands.run("echo hello > /mnt/rw/1.txt", user="root")
只建议在可信 workload 中使用 root：它可能在 host mount 中创建 root-owned 文件，后续宿主机工具处理这些文件时可能会遇到权限差异。

6.9 工作区映射注意事项

Host mount 是节点本地能力。在多机集群中，hostPath 必须存在于实际调度运行该沙箱的 Cubelet 节点上。如果希望沙箱使用和本地开发机一致的仓库，可以选择：

📦

同步到固定目录

先把仓库同步到每个 Cubelet 节点上的固定目录，再挂载该目录。

🗄️

共享存储

使用共享存储，并确保所有 Cubelet 节点上路径一致。

🧱

构建进镜像

如果沙箱只需要固定版本的代码快照，可以把仓库构建进 template image。

📥

运行时复制

如果工作区较小且不需要写回宿主机，可以在运行时把文件复制进沙箱。

不要这样用：不要只依赖 host-mount 把本地笔记本上的文件传到远端 Cubelet 节点——host mount 只映射「本节点已存在的路径」，不会替你同步。

7组件日志位置与 cubecli logs

CubeSandbox 由多个组件组成，排障时最常问的是「这条报错该去哪个日志文件里找」。关键认知是：日志分为三类，来源和查看方式完全不同。

7.1 三类日志

  • 业务行为日志：请求、调度、审计、VMM 创建过程等，各组件直接写文件到 /data/log/<Module>/，不会进 journalctl。
  • 启动期日志：进程被 systemd 拉起到稳定运行（或失败退出）期间的 stdout/stderr，只能用 journalctl -u <unit> 查看。
  • 容器沙箱 / 模板日志：沙箱内 init 进程（容器 PID 1）的 stdout/stderr，由 CubeShim 写入 Cubelet 的私有挂载命名空间内，必须用 cubecli logs 读取；模板构建日志则落在宿主机文件系统，无需进命名空间。

7.3 用 cubecli logs 查看沙箱 / 模板日志

cubecli 随 Cubelet 一同构建，一键部署时自动安装。沙箱日志文件位于 Cubelet 的私有挂载命名空间内，因此 cubecli logs 必须直接在计算节点上执行，无法远程调用。

# 沙箱 stdout，最后 100 行（默认）
cubecli logs <sandbox-id>

# 沙箱 stderr，最后 100 行
cubecli logs --stderr <sandbox-id>

# 沙箱完整日志
cubecli logs --all <sandbox-id>

# 沙箱最后 N 行 / 前 N 行
cubecli logs --tail 50 <sandbox-id>
cubecli logs --head 20 <sandbox-id>

# 模板构建日志：直接读宿主机文件系统，跳过命名空间切换
cubecli logs --tpl <template-id>
cubecli logs --tpl --all --stderr <template-id>
参数简写说明
--tpl—把 id 当作模板 ID，从 /data/log/template/<id>_0/ 读取，无需进命名空间
--stderr-e读取 stderr，默认读取 stdout
--all-a输出全部行；不可与 --tail/--head 同时使用
--tail N-t N输出最后 N 行（默认 100）
--head N-H N输出前 N 行
作用范围：cubecli logs 只覆盖容器 init 进程（PID 1）的输出。通过 E2B exec 接口在沙箱内启动的子任务，其 stdout/stderr 需要用 E2B SDK 的 on_stdout / on_stderr 回调获取。沙箱删除后，对应日志文件会一并清除；日志转发需要 v0.4.0 及以上版本的 CubeShim。

7.4 Guest kernel 日志：直接在 CubeShim log 里看

CubeShim 在启动虚拟机时，通过内核参数 console=hvc0 把 guest 内核的控制台输出接管过来，和沙箱容器 init 进程日志一样，统一写进 CubeShim 的请求日志文件。所以 guest kernel log 直接 grep cube-shim-req.log 即可，不需要额外工具。

LC_ALL=C sudo grep -a -E "(<sandbox-id 或 InstanceId>|Linux version)" /data/log/CubeShim/cube-shim-req.log

cube-shim-req.log 是逐行 JSON，日志本体在 LogContent 字段里。典型的 guest 内核启动记录形如：

{"Module":"Shim","InstanceId":"<sandbox-id>","ContainerId":"<sandbox-id>","Timestamp":"...","LogContent":"[    0.000000] Linux version 6.12.33-cube.sandbox.pvm.guest-... #2 SMP PREEMPT_DYNAMIC ...","FunctionType":""}

按 InstanceId（即 sandbox ID）过滤，即可拿到对应沙箱完整的内核启动输出，包括设备探测、EXT4-fs、rootfs mount 等信息。

为什么在这里：console=hvc0 是虚拟机的串口控制台，内核所有 printk 输出都会走这条通路。CubeShim 把这条控制台流量直接转发进它自己的日志管道（和普通请求日志共用同一个 writer），所以查 guest kernel 日志不需要额外挂载或调试工具。

7.5 cube-proxy 宿主机日志

cube-proxy 是基于 OpenResty 的 nginx 容器。一键部署会将宿主机目录 /data/log/cube-proxy/ bind mount 到容器内同一路径，可以直接从宿主机读取：

tail -F /data/log/cube-proxy/error.log
tail -F /data/log/cube-proxy/access.log
文件内容
access.lognginx 访问日志
error.lognginx 错误日志

7.6 开启 Cubelet debug 级别日志

Cubelet 默认日志级别是 warn，排障时往往需要临时调高到 debug。有两种方式，二者都不需要重启 Cubelet 进程。

方式一：改动态配置文件（持久生效，热加载）。Cubelet 以 10 秒为周期轮询动态配置文件，检测到变化后自动热加载。在 common: 段落下加一行 log_level：

common:
  enable_pf_mode: false
  log_level: debug   # 新增这一行
  sandbox_exec_cmd_time_out: 5s
  ...

一键部署环境下该文件的默认路径是：

/usr/local/services/cubetoolbox/Cubelet/dynamicconf/conf.yaml

方式二：调试端口临时切换（不改文件，进程重启后失效）。Cubelet 内置 debug HTTP 端口（默认监听 :9966，对应 config.toml 里的 [debug] address），暴露 /debug/loglevel 接口：

# 切到 debug
curl -X POST 'http://127.0.0.1:9966/debug/loglevel?level=debug'

# 排障结束后切回 info
curl -X POST 'http://127.0.0.1:9966/debug/loglevel?level=info'
只对新启动的沙箱生效：无论用哪种方式切到 debug，已经处于运行中的沙箱不会补出更详细的日志。因此排障时建议的顺序是：先切到 debug，再复现问题（新建沙箱触发问题场景）。
安全提示：debug 端口下还挂载了 /debug/pprof/*（goroutine 栈、堆内存 profile、源码片段）。请确保 :9966 仅监听 localhost，不要通过反向代理暴露，也不要绑定到 0.0.0.0。开启 debug 会使单次请求日志量放大一个数量级，排障结束后记得改回 info/warn。

8一键诊断信息收集与命令速查

下面这段脚本只做只读采集，把 §3–§7 中确认过的路径与命令一次性落到一个目录里，方便随工单/issue 一起提交。

#!/usr/bin/env bash
# CubeSandbox 一键诊断信息收集（只读命令，路径来自本文档）
set -u
OUT="/tmp/cube-diag-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$OUT"

uname -a > "$OUT/uname.txt" 2>&1
grep -w bpf /proc/filesystems > "$OUT/bpffs.txt" 2>&1
df -T /data/cubelet > "$OUT/df-cubelet.txt" 2>&1
df -h /tmp /data/cubelet /usr/local/services/cubetoolbox > "$OUT/df-tmp.txt" 2>&1
ip route > "$OUT/ip-route.txt" 2>&1
ip tuntap show > "$OUT/ip-tuntap.txt" 2>&1
systemctl status 'cube-sandbox-*.target' --no-pager > "$OUT/systemd.txt" 2>&1
journalctl -u cube-sandbox-cubelet.service --no-pager -n 200 > "$OUT/cubelet-journal.txt" 2>&1

for f in CubeAPI/cube-api-$(date +%F).log \
         CubeMaster/cubemaster-req.log \
         Cubelet/Cubelet-req.log \
         CubeShim/cube-shim-req.log \
         CubeVmm/vmm.log; do
  tail -n 200 "/data/log/$f" > "$OUT/$(echo "$f" | tr '/' '_')" 2>&1
done

echo "诊断信息已收集到 $OUT"

9易错点、记忆卡片与自测

9.1 易错点

易错点 1：以为 reboot 能清掉 cube-dev。仅 reboot 不够——systemd target 是 enabled 的，开机后 Cubelet 内置 network runtime 会按 config.toml 重建旧网络。必须手动 ip link delete cube-dev 并清理 z* TAP。
易错点 2：把 readOnly 当成权限开关。readOnly: False 只表示「以读写方式挂载」，不会绕过宿主机 UID/GID 权限；写不进去先对齐 owner 或用 ACL。
易错点 3：对着运行中的沙箱开 debug 等日志变详细。已经运行中的沙箱不会补出更详细的日志，必须「先切 debug，再新建沙箱复现」。
易错点 4：模板超时就调大 timeout。DISTRIBUTING 与 CREATING_TEMPLATE 由不同配置限制；先查节点健康、磁盘、网络和 Cubelet 日志，确认只是慢再改 cubelet_conf 并重启 CubeMaster。
易错点 5：在别的机器上远程执行 cubecli logs。沙箱日志位于 Cubelet 私有挂载命名空间，cubecli logs 必须在计算节点本机执行。

9.2 记忆卡片

方法论先分层 → 再定位信号 → 最后验证，不要一上来就翻日志。
bpffsgrep -w bpf /proc/filesystems 有输出才挂载；持久化写进 /etc/fstab。
XFS/data/cubelet 必须 XFS + reflink，ext4 根盘会报 not XFS。
CIDR默认 192.168.0.0/18；/24 比 /18 精确，会抢走沙箱流量。
日志三类业务日志进 /data/log；启动日志进 journalctl；沙箱日志用 cubecli logs。
guest kernel通过 console=hvc0 转发进 cube-shim-req.log。

9.3 自测

自测

1. one-click 预检报「不是 bpf 文件系统」，正确的排查顺序是什么？

先 grep -w bpf /proc/filesystems 确认内核是否支持。有输出则 mkdir -p /sys/fs/bpf && mount -t bpf bpf /sys/fs/bpf，可选地在 /etc/fstab 加 bpf /sys/fs/bpf bpf defaults 0 0 持久化；无输出说明缺 CONFIG_BPF_SYSCALL，需升级或更换内核。

2. 为什么把默认网段改掉后，仅重启机器还不够？

因为 cube-dev 和 z* TAP 是持久化残留，systemd target 又是 enabled 的，开机会由 Cubelet 内置 network runtime 按 config.toml 重建。必须停服后手动 ip link delete cube-dev、清理 z* TAP，再用新 CIDR 重装。

3. 想看到沙箱 guest kernel 的启动日志，应该去哪看？

直接在 CubeShim 的请求日志里看：LC_ALL=C sudo grep -a -E "(<sandbox-id>|Linux version)" /data/log/CubeShim/cube-shim-req.log。guest kernel 通过 console=hvc0 的输出被 CubeShim 转发进 cube-shim-req.log 的 LogContent 字段，无需额外工具。
