1模板与镜像：是什么关系

一句话：模板不是镜像，而是「镜像 + 构建产物 + 就绪探针 + 分发」四件事的封装。镜像只是原料，模板是 CubeSandbox 真正用来创建沙箱的、可被调度到集群各节点的制品。记住这条公式，后面所有命令和排错都能挂上去。

镜像
OCI 镜像（基础 rootfs）公开 / 私有仓库
产物
rootfs ext4 artifactartifact_idartifact_sha256
探针
--probe 端口--probe-path 路径（返回 2xx）
分发
distribution N/M readytemplate_spec_fingerprint 复用

几个必须记住的关键字段

概念含义为什么要关心
OCI 镜像标准容器镜像，是模板的原料镜像拉不到就卡在 PULLING
rootfs artifact构建出的可写层文件系统，带稳定 artifact_id多模板可共享同一 artifact，删除不立即回收
就绪探针--probe 指定端口、--probe-path 指定路径，必须返回 HTTP 2xx探针不通，模板永远进不了 READY
distributionN/M ready，已收到 artifact 的节点数0/N 长时间不变多半是分发/网络问题
fingerprint决定能否复用 artifact 的确定性指纹只改 cpu/memory/env 等字段可复用同一 artifact
与快照的关系：模板的底层产物与「快照 / 跨机迁移」共享同一套 artifact 存储（xfs 或 s3 CoW 后端）。加上 --backend s3 后，模板及其派生的沙箱与快照会走集群共享 S3 后端，这是跨机 Pause / Resume / FromSnap 的前提。

2三种制作方式对比

制作模板有三条路：从 OCI 镜像构建、自定义镜像（BYOI，先把 envd 等塞进你的镜像再构建）、以及把运行中的沙箱直接提交成模板。先看结论，再决定用哪条。

方式核心流程关键命令适用场景主要限制
从 OCI 镜像 选镜像 → create-from-image → watch → 使用 tpl create-from-image 已有标准镜像；可复现的构建流水线 镜像须能被集群节点拉取；探针端口/路径必须对
自定义镜像 BYOI 写 Dockerfile（注入 envd）→ 构建推送 → create-from-image COPY --from= / --enable-inject-envd 现有镜像没有 envd、需要 SDK/命令/文件能力 入口契约必须满足；-isnotfc 不可省
运行中沙箱提交 进入沙箱装依赖 → tpl commit cubecli exec + tpl commit 不适合写 Dockerfile、环境已手工调好 会保存内存状态；--file 是整体替换而非合并
可复现优先

选「从 OCI 镜像」

能用 Dockerfile 描述的环境就用它，构建产物可审计、可重建、可纳入 CI。

镜像缺 envd

选「BYOI」

你的应用镜像要用 SDK 执行命令/读写文件，就先注入 envd 与入口脚本再构建。

环境调好不想重来

选「沙箱提交」

手工装好依赖、跑通服务后一键 commit，连内存状态一起保存成模板。

3从 OCI 镜像制作模板

这是最常用、最推荐纳入流水线的方式。下面按「前置 → 选镜像 → 创建 → 监控 → 使用 → 查询 → 迁移 → 删除 → 排错」完整走一遍。

前置条件

  • 已安装 cubemastercli，且能连接 CubeMaster。
  • OCI 镜像能被 CubeMaster 节点访问（公开仓库，或已配置认证的私有仓库）。
  • 明文 HTTP 仓库（未启用 TLS）须在镜像引用前加 http://，例如 http://harbor.internal:5000/ns/app:tag。不加前缀时 CubeMaster 默认走 HTTPS（localhost 与 RFC1918 地址除外）。

选择 OCI 镜像

create-from-image 接收一个已构建发布的标准 OCI 镜像。本教程用预装 envd 的官方基础镜像：

ghcr.io/tencentcloud/cubesandbox-base:latest

该镜像中的 envd 默认监听 49983，可直接用 GET /health 作为模板探针。

创建模板

cubemastercli tpl create-from-image \
  --image     ghcr.io/tencentcloud/cubesandbox-base:latest \
  --writable-layer-size 1G \
  --expose-port 49983 \
  --probe 49983 \
  --probe-path /health

也可以暴露多个端口、自定义探针路径，并传入环境变量：

cubemastercli tpl create-from-image \
  --image     cube-sandbox-cn.tencentcloudcr.com/cube-sandbox/sandbox-code:latest \
  --writable-layer-size 1G \
  --expose-port 49999 \
  --expose-port 49983 \
  --probe      49999 \
  --probe-path /health \
  --env        MY_ENV=production

--user 指定模板构建进程、以及之后从该模板创建沙箱的容器用户。写法是 uid、uid:gid、用户名 或 用户名:gid，组必须是数字；不传仍以 root 运行。模板构建仍保持 privileged（构建过程要准备设备），变的只是容器进程用户。

cubemastercli tpl create-from-image \
  --image     ghcr.io/tencentcloud/cubesandbox-base:latest \
  --writable-layer-size 1G \
  --user      1000:1000
需要跨机 Pause / Resume / FromSnap？加上 --backend s3，让模板及其派生的沙箱 / 快照走集群共享 S3 CoW 后端；省略则沿用历史 xfs 路径。

监控进度：watch 与 status

Watch（阻塞，推荐）：循环轮询任务，直到终态（READY 或 FAILED）才退出。

cubemastercli tpl watch --job-id <job_id>

完成时输出示例：

字段说明
status / template_status任务和模板的整体状态，READY 表示可用
phase流水线阶段：PULLING → BUILDING → DISTRIBUTING → READY
progress当前阶段完成百分比
distributionN/M ready，已收到 artifact 的节点数
artifact_id / artifact_sha256rootfs artifact 的稳定 ID 与完整性摘要
template_spec_fingerprint判断能否复用 artifact 的确定性指纹
指纹口径：不包含 --cpu/--memory、--cmd/--arg、--env、--probe、工作目录、volume 挂载、rlimit——仅这些字段不同的模板共享同一 artifact（相同 artifact_id）。而 --expose-port、--network-type、--dns、--writable-layer-size、--instance-type、--user 仍会改变指纹。

Status（单次查询）：只想看一次当前状态、不阻塞时使用。

cubemastercli tpl status --job-id <job_id>

使用模板

template_status: READY 后，通过 template_id 用 E2B SDK 创建沙箱：

export CUBE_TEMPLATE_ID=tpl-748094d2f2374b0a8a37e6ec
python CubeAPI/examples/create.py

查询模板

# 列出所有模板
cubemastercli tpl list

# 同时查看 VERSION 与 LAST_ERROR
cubemastercli tpl list -o wide

# 输出完整 JSON，便于脚本处理
cubemastercli tpl list --json | jq '.data[].template_id'

# 查看单个模板（模板 ID 可作位置参数，也可用 --template-id）
cubemastercli tpl info tpl-748094d2f2374b0a8a37e6ec

# 机器可读 + 查看保存的创建请求体
cubemastercli tpl info tpl-748094d2f2374b0a8a37e6ec --json --include-request

# 预览创建沙箱时最终生效的请求
cubemastercli tpl render --template-id tpl-748094d2f2374b0a8a37e6ec --json

列表中的 IMAGE_INFO 优先展示「镜像引用 + digest」（image@sha256:...），digest 不可用时降级为仅镜像引用；CREATED_AT 使用 UTC RFC3339。

（可选）把历史本地 artifact 迁入 TC 存储

大多数新建的 from-image 模板已沿当前数据面直接走 TC 构建，不一定需要手动 tpl merge。它主要用于：历史 rootfs ext4 还在 CubeMaster 本地盘；集群后来开启 s3Backed=true 想收敛旧模板；或想再次触发幂等检查并清理遗留本地文件。命令名 merge 对应 API 路径 /cube/template/migrate，默认阻塞到 migrate job 结束。

# 阻塞迁移
cubemastercli tpl merge tpl-748094d2f2374b0a8a37e6ec

# 只提交 migrate job 就返回
cubemastercli tpl merge tpl-748094d2f2374b0a8a37e6ec --detach

# 存量模板：先收敛存储，再重新分发 / 必要时重建
cubemastercli tpl merge tpl-748094d2f2374b0a8a37e6ec
cubemastercli tpl redo --template-id tpl-748094d2f2374b0a8a37e6ec
口径统一：tpl merge 解决历史 artifact 的存储收敛，tpl redo 解决节点侧重新分发 / 必要时重建。开启 s3Backed=true 后旧模板不会自动补做迁移；若本地 ext4 已丢失，再跑 merge 也修不回来，只能对可重建的 from-image 模板执行 tpl redo。

删除模板

cubemastercli tpl delete tpl-748094d2f2374b0a8a37e6ec

# 一次删除多个（失败项最后汇总返回）
cubemastercli tpl delete tpl-first tpl-second tpl-third

# 用 --force 清除卡住的构建工作
cubemastercli tpl delete --force tpl-748094d2f2374b0a8a37e6ec

成功后输出 template deleted: tpl-...。--force 只清除卡住的构建任务/定义，不覆盖使用中检查——只要仍有运行中的沙箱依赖该模板，后端就拒绝删除（包括带 --force 的请求）。

删除相关规则说明
共享 artifactrootfs 与其他模板共享时，最后一个引用它的模板删除后才回收
不可达节点超过 15 分钟未心跳的节点不阻塞删除，记为待清理，删除照常成功
清理时机节点恢复后后台完成清理，通常 10 分钟内；一直不恢复则记录保留
ID 复用待清理完成前不要复用已删除的模板 ID
日志关键字含义
unreachable past grace节点被跳过，已记为待清理
orphan replica cleanup still failing节点已恢复，但清理仍然失败
orphan replica cleanup converged该节点上的模板本地数据已删除
deferred placement cleanup converged该节点上的镜像文件已删除

现象可能原因处理方式

4自定义模板镜像（BYOI）

当你的应用镜像要接入 CubeSandbox、用 SDK 执行命令 / 读写文件 / 建 PTY 时，镜像里必须带 envd。本节讲清「什么时候需要、怎么塞进去、入口契约、本地怎么验证」。

我的镜像什么时候需要 envd

envd 是 CubeSandbox SDK 和 E2B SDK 执行命令、读写文件和建立 PTY 所使用的数据面服务。

能力沙箱内的 envd 接口没有 envd 会怎样
健康检查（可作模板 probe）GET :49983/health → 204该探活端点不可用
Sandbox.commands.run():49983 上的 Process API命令 API 不可用
Sandbox.files.read/write():49983 上的 Files API文件 API 不可用
创建时环境变量初始化POST :49983/init传入创建时环境变量时，沙箱创建失败

交互式开发 / 代码执行沙箱建议保留 envd 便于排障；仅提供自有业务服务、不用上述能力的镜像可省略，此时把模板 probe 配成应用自己的 HTTP 健康检查端点。

基于 cubesandbox-base 构建

cubesandbox-base 就是普通 ubuntu:22.04，在 /usr/bin/envd 预装了 envd，并附带通用入口脚本——后台拉起 envd、前台 exec 你提供的 CMD。三步走：写 Dockerfile → 构建推送 → 创建模板。

FROM ghcr.io/tencentcloud/cubesandbox-base:2026.16

# 安装你自己需要的工具链
RUN apt-get update \
    && apt-get install -y --no-install-recommends python3 python3-pip \
    && rm -rf /var/lib/apt/lists/*

RUN pip install --no-cache-dir pandas matplotlib numpy

# 应用若需作为前台进程运行，在这里设置 CMD 即可。
# envd 仍会作为后台进程持续运行。
# CMD ["python3", "/srv/app.py"]
docker build -t my-registry.example.com/my-team/my-sandbox:v1 .
docker push   my-registry.example.com/my-team/my-sandbox:v1

镜像仓库需能被 Cube 集群拉到；明文 HTTP 仓库须加 http:// 前缀。创建模板时暴露 49983（envd）外加应用端口：

cubemastercli tpl create-from-image \
  --image       my-registry.example.com/my-team/my-sandbox:v1 \
  --writable-layer-size 1G \
  --expose-port 49983 \
  --expose-port <your-custom-port> \
  --probe       49983 \
  --probe-path  /health

向现有镜像注入 envd 的两种方式

方式 A：在 Dockerfile 中 COPY --from=——从 cubesandbox-base 拷贝 envd 与入口脚本。

FROM e2bdev/code-interpreter:latest

USER root

# 从 cubesandbox-base 拉取 envd 与通用入口脚本
COPY --from=ghcr.io/tencentcloud/cubesandbox-base:2026.16 \
     /usr/bin/envd /usr/bin/envd
COPY --from=ghcr.io/tencentcloud/cubesandbox-base:2026.16 \
     /usr/local/bin/cube-entrypoint.sh /usr/local/bin/cube-entrypoint.sh

# 上游镜像通常已有自己的 entrypoint/CMD，推荐用 cube-entrypoint.sh 包裹它
ENTRYPOINT ["/usr/local/bin/cube-entrypoint.sh"]
CMD ["/bin/sh", "-c", "sudo --preserve-env=E2B_LOCAL /root/.jupyter/start-up.sh"]

从轻量 Python 镜像出发的例子（注意 EXPOSE 49983 8000，应用在 8000）：

FROM python:3.11-slim

COPY --from=ghcr.io/tencentcloud/cubesandbox-base:2026.16 \
     /usr/bin/envd /usr/bin/envd
COPY --from=ghcr.io/tencentcloud/cubesandbox-base:2026.16 \
     /usr/local/bin/cube-entrypoint.sh /usr/local/bin/cube-entrypoint.sh

RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

RUN pip install --no-cache-dir fastapi uvicorn

COPY app.py /srv/app.py

EXPOSE 49983 8000
ENTRYPOINT ["/usr/local/bin/cube-entrypoint.sh"]
CMD ["uvicorn", "app:app", "--app-dir", "/srv", "--host", "0.0.0.0", "--port", "8000"]

方式 B：在模板构建阶段注入——不改 Dockerfile，用 --enable-inject-envd 上传并注入 envd。

cubemastercli tpl create-from-image \
  --image <your-image> \
  --writable-layer-size 1G \
  --expose-port 49983 \
  --probe 49983 \
  --probe-path /health \
  --enable-inject-envd
参数说明
--enable-inject-envd从 cubemastercli 上传一个 envd 二进制并写入模板 rootfs
--envd-path运行 CLI 的机器上的本地路径；仅设置 --enable-inject-envd 时生效。省略则用 CLI 构建期内嵌的默认 envd

CLI 通过 multipart 上传二进制，CubeMaster 校验后写入 rootfs 的 /usr/local/bin/envd，并把二进制的 SHA-256 纳入指纹（避免复用不同 envd 构建的 artifact）。上传文件必须是非空 ELF 二进制、不超过 16 MiB、且与目标 rootfs 的 OS/CPU 架构兼容。若 CLI 构建时没有内嵌默认 envd，则必须同时指定 --envd-path：

make cubemastercli ENVD_LOCAL_PATH=/path/to/envd
cubebox 类型额外行为：CubeMaster 会保留注入标记，创建沙箱时自动包装主容器启动命令——先后台运行 /usr/local/bin/envd，再执行镜像原有命令，并补充暴露 49983 端口。因此无需修改原镜像入口；非 cubebox 类型不会应用该启动包装。

入口脚本契约：为什么必须 -isnotfc

cube-entrypoint.sh 实现「envd 后台 + 用户应用前台」的组合模式：

  1. 启动时一律后台拉起 envd -port "${ENVD_PORT:-49983}"，使 /health 在容器启动约 1 秒内就能响应。
  2. 如果启动时带了 CMD，脚本 exec 执行它——envd 后台伴跑，用户进程占用 stdout/stderr 并接收 SIGTERM。
  3. 如果没有 CMD，脚本 wait 住 envd，让它成为前台主进程。
变量默认值说明
ENVD_PORT49983envd 监听端口
ENVD_EXTRA_ARGS（空）追加到 -port 之后；未包含 -isnotfc 时脚本会自动追加以跳过 Firecracker MMDS 查询
ENVD_LOG_FILE/var/log/envd.logenvd stdout/stderr 落盘位置；设为 - 则继承容器 stdio
ENVD_BIN/usr/bin/envdenvd 安装在别处时覆盖
 
#!/bin/bash
# your-entrypoint.sh

# 后台启动 envd
# -isnotfc 是必须的：它让 envd 跳过对 169.254.169.254 的 Firecracker MMDS
# 查询。CubeSandbox 不使用 Firecracker，MMDS 服务不存在。缺少此参数时
# envd 会尝试访问不存在的 MMDS，可能引发网络超时、/init 延迟、
# env_vars 注入失败等各种问题。
/usr/bin/envd -port 49983 -isnotfc >/var/log/envd.log 2>&1 &

# ... 你原本的启动流程 ...
exec "$@"
为什么必须 -isnotfc：envd 默认会去 169.254.169.254 查 Firecracker MMDS。CubeSandbox 不用 Firecracker，该服务不存在；缺少此参数会触发网络超时、/init 延迟、env_vars 注入失败等连锁问题。cube-entrypoint.sh 会自动追加，手写入口时务必自己加上。

本地验证镜像（可选）

创建模板前，先确认镜像用默认启动命令能保持运行且 envd 可响应。宿主需 Docker，镜像内需 curl 与 /usr/bin/envd，全程同一终端。

# 1. 启动镜像
IMG=my-registry.example.com/my-team/my-sandbox:v1
cid=$(docker create "$IMG") && docker start "$cid"

# 2. 检查状态与 envd（应 running + 204）
docker inspect --format '{{json .State}}' "$cid"
docker exec "$cid" curl -sS --noproxy '*' --connect-timeout 1 --max-time 3 \
    -o /dev/null -w 'envd /health => %{http_code}\n' \
    http://127.0.0.1:49983/health
# 预期: envd /health => 204
docker exec "$cid" /usr/bin/envd -version
# => 2026.16

# 3. 失败时，删除前先看状态与日志
docker logs --tail 100 "$cid"
logdir=$(mktemp -d)
docker cp "$cid":/var/log/envd.log "$logdir/envd.log" && tail -n 100 "$logdir/envd.log"

# 4. 清理测试容器
docker rm -f "$cid"
探活必须输出 204，其他状态码（包括 200、500）都不算通过。docker start 成功不代表容器会保持运行——docker inspect 须显示 "Status":"running" 与 "Running":true；即使 ExitCode 为 0，容器退出也不能视为通过。本地检查不覆盖集群拉镜像、sandbox 网络和 envd /init。

排错速查

现象可能原因解决

5从运行中沙箱提交模板

当环境不适合写 Dockerfile、或你已有一个调好的运行环境时，可把运行中沙箱的当前文件系统和内存状态直接制成模板，供后续复用。

操作沙箱

创建沙箱后用 cubecli 进入（类似 docker），在内部装依赖、执行命令等：

cubecli exec -it <sandbox-id> bash

提交沙箱

cubemastercli tpl commit --sandbox-id <sandbox-id>

提交成功后，CubeMaster 会生成新的 tpl-... 模板 ID，并在源沙箱所在节点创建初始副本。

高级配置：为新模板指定创建请求

执行 tpl commit 时，CubeMaster 不仅保存文件系统和内存状态，还会为模板保存一份 CreateCubeSandboxReq，用于之后恢复容器、启动命令、端口和网络等配置。默认无需额外文件，会自动恢复源沙箱原创建请求；只有希望新模板用一套不同的配置时，才通过 --file <path> 提供完整 JSON：

cubemastercli tpl commit \
  --sandbox-id <sandbox-id> \
  --file template-request.json
--file 是整体替换，不是合并：它会用文件中的请求完整替换自动恢复的原请求。文件里没包含容器、启动命令、环境变量或暴露端口时，这些配置不会被自动保留，生成的模板可能无法按预期启动。若只是想把当前沙箱保存为模板，不要传 --file。

即使使用 --file，CubeMaster 仍会读取源沙箱的持久化创建请求以继承模板托管的 QoS；记录不可读时 commit 会失败，而不是生成无 QoS 限速的模板，也不要在文件中设置 cube.master.net 或 cube.master.blk.qos（由模板托管，传入会被拒绝）。

{
  "instance_type": "cubebox",
  "network_type": "tap",
  "cube_network_config": {
    "allowInternetAccess": true,
    "allowOut": ["10.0.0.0/8"],
    "denyOut": []
  }
}
参数作用
--allow-internet-access=false显式设置请求中的联网开关
--allow-out-cidr <cidr>追加允许访问的出站 CIDR，可重复传入
--deny-out-cidr <cidr>追加禁止访问的出站 CIDR，可重复传入

这些网络参数只修改 --file 提供的请求，必须与 --file 一同使用：

cubemastercli tpl commit \
  --sandbox-id <sandbox-id> \
  --file template-request.json \
  --allow-internet-access=false

6预热模板服务

普通模板能预装系统和依赖，但应用仍可能在每次沙箱启动后执行耗时初始化（加载 SDK、创建 Agent 会话、扫描工作区、建本地缓存）。预热模板让 CubeSandbox 等应用完成这些工作后再制作快照，使后续沙箱从已初始化的内存和进程状态恢复。

工作原理

1 常驻服务：镜像启动一个常驻进程，负责承载预热状态。
↓
2 初始化：服务完成需要预热的初始化工作，此时就绪端点仍返回 503。
↓
3 就绪：全部状态就绪后，就绪端点才返回 HTTP 2xx。
↓
4 探针命中：CubeSandbox 探测到成功响应，保存此刻的文件系统、内存和进程状态。
↓
5 恢复即用：从模板创建沙箱时，常驻服务随快照恢复，可直接处理请求。
就绪端点不要过早返回成功。HTTP server 刚开始监听时不应返回 2xx，应先返回 503，直到所有需要保存在快照中的状态都准备完成。

常驻服务 → 探针 → 就绪 时序

常驻服务启动

镜像 CMD 拉起 adapter / 业务常驻进程，envd 作为后台伴跑。

初始化预热内容

加载 SDK、创建 AgentSession、建缓存；此刻就绪端点返回 503。

探针命中 2xx

CubeSandbox 探测 --probe-path（如 /readyz）返回 200。

保存快照

固化为模板：文件系统 + 内存 + 进程状态一并保存。

恢复即用

从模板创建沙箱，常驻服务随快照恢复，直接处理请求。

Pi Agent 示例

Pi Agent 普通运行方式会为每个任务启动新进程；示例中的 warmup adapter 作为常驻进程，启动阶段创建一个 Pi SDK AgentSession，只有会话初始化完成后 GET /readyz 才返回 200。

1）常驻服务核心逻辑（pi_warmup_adapter.mjs）：

let ready = false;

const server = http.createServer((request, response) => {
  if (request.method === "GET" && request.url === "/readyz") {
    response.writeHead(ready ? 200 : 503);
    return response.end();
  }

  // 处理恢复后的业务请求。
});

session = await createAgentSession(/* ... */);
ready = true;
server.listen(8080, "0.0.0.0");

2）把常驻服务设为镜像 CMD（Dockerfile.warmup）：

ARG PI_AGENT_IMAGE=pi-agent-cube:latest
FROM ${PI_AGENT_IMAGE}

COPY pi_warmup_adapter.mjs /tmp/pi_warmup_adapter.mjs
RUN PI_PACKAGE_DIR="$(npm root -g)/@earendil-works/pi-coding-agent" \
    && install -m 0755 /tmp/pi_warmup_adapter.mjs \
       "${PI_PACKAGE_DIR}/pi_warmup_adapter.mjs" \
    && rm /tmp/pi_warmup_adapter.mjs

ENV PI_WARMUP_HOST=0.0.0.0 \
    PI_WARMUP_PORT=8080

EXPOSE 49983 8080

CMD ["sh", "-c", "exec node \"$(npm root -g)/@earendil-works/pi-coding-agent/pi_warmup_adapter.mjs\""]

端口 8080 提供应用就绪检查和任务接口；49983 由基础镜像中的 envd 使用，以保留 SDK 的命令、文件和终端能力。

3）构建并推送：

docker build --platform linux/amd64 \
  -t localhost:5000/pi-agent-cube:latest \
  examples/pi-agent-integration

docker build --platform linux/amd64 \
  -f examples/pi-agent-integration/Dockerfile.warmup \
  --build-arg PI_AGENT_IMAGE=localhost:5000/pi-agent-cube:latest \
  -t localhost:5000/pi-agent-warmup-cube:latest \
  examples/pi-agent-integration

docker push localhost:5000/pi-agent-cube:latest
docker push localhost:5000/pi-agent-warmup-cube:latest

4）用应用探针制作模板——暴露 envd 和 warmup adapter 端口，但探针指向真正代表 Pi 会话初始化完成的 /readyz：

cubemastercli tpl create-from-image \
  --image localhost:5000/pi-agent-warmup-cube:latest \
  --alias pi-warmup \
  --writable-layer-size 4G \
  --expose-port 49983 \
  --expose-port 8080 \
  --probe 8080 \
  --probe-path /readyz
不能拿 49983/health 当预热完成信号：它只说明 envd 就绪，不能说明 Pi AgentSession 已创建。应等待 /readyz 就绪，此时所有服务才均已启动完成。

设计自己的预热服务

  • 探测真实的预热状态：完成模型加载、运行时初始化或缓存构建后，再让就绪端点返回 2xx。
  • 保持进程常驻：完成初始化的进程必须继续运行，才能随内存快照一起恢复。
  • 不要把密钥写入模板：构建期不要注入 API Key、令牌或用户数据；应在沙箱恢复后通过请求、密钥保险柜等运行时机制提供。
  • 谨慎处理外部连接：数据库连接、长连接和临时凭证在恢复时可能已失效，恢复后应检测并重建。
  • 明确并发模型：Pi 示例一个 adapter 只维护一个 session，并发任务返回 HTTP 409；需要并发时应用连接池 / 会话池，或让每个沙箱只处理一个任务。
  • 保持就绪检查轻量：探针只读本地状态，不重复执行昂贵初始化或产生外部副作用。

排查问题

现象检查项
模板构建一直等待探针确认服务监听 0.0.0.0、端口和路径匹配，并查看初始化日志
模板 READY，但应用首次请求仍需初始化就绪端点返回过早；把 ready 状态设置移到完整初始化之后
SDK 命令或文件 API 不可用确认镜像包含 envd，并通过 --expose-port 49983 暴露其端口

7本地与远程镜像实战

两条实操路线：方式一本地构建镜像（镜像只在当前机器，无需推送到远端）；方式二远程镜像（镜像已推送 Registry，集群从远端拉取）。先看前置条件。

前置条件

  • 已安装 cubemastercli 并加入 $PATH；已安装 Docker。
  • CubeMaster 服务正常（cubemastercli tpl list 能返回结果）。
  • 已找到 mkcert CA 证书路径（SDK 连接沙箱时需要）：ls ~/.local/share/mkcert/rootCA.pem。

方式一：本地构建镜像

适合在 CubeMaster 所在机器上本地开发调试。Dockerfile 基于预装 envd 的 cubesandbox-base：

FROM ghcr.io/tencentcloud/cubesandbox-base:latest

# 安装你需要的工具和依赖
RUN apt-get update && apt-get install -y --no-install-recommends \
    python3 python3-pip curl wget git vim jq \
    && rm -rf /var/lib/apt/lists/*

RUN pip install --no-cache-dir numpy pandas requests httpx

保存为 /tmp/Dockerfile.cube-test，构建并验证 envd 正常（期望 204）：

docker build -f /tmp/Dockerfile.cube-test -t my-sandbox:v1 .

cid=$(docker run -d my-sandbox:v1)
sleep 2
docker exec "$cid" curl -s -o /dev/null -w "envd /health => %{http_code}\n" http://127.0.0.1:49983/health
# 期望输出: envd /health => 204
docker rm -f "$cid"

制作模板 → 拿到 job_id / template_id → watch 等待 READY：

cubemastercli tpl create-from-image \
  --image my-sandbox:v1 \
  --writable-layer-size 2G \
  --expose-port 49983 \
  --probe 49983 \
  --probe-path /health

cubemastercli tpl watch --job-id <job_id>

验证模板可用（方式 B 的 cubesandbox SDK 无需 SSL 证书，推荐）：

export CUBE_API_URL=http://127.0.0.1:3000
export CUBE_TEMPLATE_ID=<template_id>
export CUBE_PROXY_NODE_IP=127.0.0.1   # 本机；远程访问填 CubeProxy 节点 IP

python3 - << 'EOF'
import os
from cubesandbox import Sandbox, Config

cfg = Config(
    api_url=os.environ["CUBE_API_URL"],
    template_id=os.environ["CUBE_TEMPLATE_ID"],
    proxy_node_ip=os.environ.get("CUBE_PROXY_NODE_IP", ""),
)

with Sandbox.create(config=cfg) as sb:
    r = sb.run_code('import sys; print(sys.version); print("hello-cube")')
    for line in r.logs.stdout:
        print(line, end="")
EOF
run_code 依赖 Jupyter kernel（49999 端口）：自定义模板需在 Dockerfile 中安装 jupyter_kernel_gateway ipykernel，并在制作模板时同时暴露 49983 和 49999 两个端口。若用 e2b_code_interpreter 方式，则需 export SSL_CERT_FILE=~/.local/share/mkcert/rootCA.pem。

方式二：远程镜像

适合团队共享镜像或多节点集群：镜像推送到 Registry 后，各节点都能拉取。Dockerfile 同方式一；构建时带 Registry 前缀，然后登录推送：

docker build -f /tmp/Dockerfile.cube-test \
  -t ccr.ccs.tencentyun.com/<命名空间>/<镜像名>:v1 .

docker login ccr.ccs.tencentyun.com
docker push ccr.ccs.tencentyun.com/<命名空间>/<镜像名>:v1

私有仓库需加认证参数：

cubemastercli tpl create-from-image \
  --image ccr.ccs.tencentyun.com/<命名空间>/<镜像名>:v1 \
  --writable-layer-size 2G \
  --expose-port 49983 \
  --probe 49983 \
  --probe-path /health \
  --registry-username <用户名> \
  --registry-password <密码>

两种方式对比

本地镜像远程镜像
是否需要推送不需要需要 push
适用场景单机开发调试团队共享、多节点集群
镜像名格式my-sandbox:v1registry/ns/image:tag
私有仓库认证不需要可能需要 --registry-username/password
速度快（本地直接读）取决于网络和镜像大小

探针参数速记

参数说明
--expose-port声明容器对外暴露的端口
--probe探活使用的端口，必须已在 --expose-port 中声明
--probe-path探活的 HTTP GET 路径，必须以 / 开头且返回 2xx
错误配置现象正确做法
--probe 端口未在 --expose-port 中声明参数校验报错先 --expose-port 再 --probe，端口一致
--probe-path 填不存在的路径（/healthz 实际是 /health）探活超时，模板 FAILED本地先 curl http://127.0.0.1:<port><path> 确认 2xx
sandbox-code 只暴露 49983，未暴露 49999模板 READY 但 run_code 连接失败同时暴露 49999 和 49983
--probe-path 漏写开头 /（写成 health）探活 404路径必须以 / 开头

#现象原因与解决

8环境变量的可见性

CubeSandbox 设置环境变量有三种时机：创建模板时、创建沙箱时、单次命令/PTY/代码执行时。关键陷阱：不同时机创建的环境变量，对不同交互方式（envd 处理的命令 vs Jupyter kernel）可见性不同。

创建模板时

可写进 Dockerfile ENV、SDK Template.build(envs=...)，或 create-from-image --env：

cubemastercli tpl create-from-image \
  --image cube-sandbox-cn.tencentcloudcr.com/cube-sandbox/sandbox-code:latest \
  --writable-layer-size 1G \
  --expose-port 49999 \
  --expose-port 49983 \
  --probe 49999 \
  --env DEMO_ENV=template-only
envd 不继承 OCI process envs。因此构建模板时设置的环境变量，通过 sandbox.commands.run / sandbox.pty.create 是不可见的（echo -n DEMO_ENV=$DEMO_ENV 输出空）；但 sandbox.run_code（走 Jupyter kernel 而非 envd）可以看到镜像 ENV 和模板构建 env，cubecli exec 交互终端与沙箱主进程也可见。写入模板的 env 对所有使用者可见，不要存放密钥。

创建沙箱时

用 Sandbox.create(envs={...}) 注入，仅对当前沙箱可见，不写回模板、不注入主进程/长期服务/cubecli exec。commands.run 可读，但 run_code 默认读不到（lightweight code interpreter 不把 envd 中的沙箱变量注入 Jupyter kernel）；若需继承，参考 run-code-env-inheritance 派生镜像。

with Sandbox.create(
    template="tpl-example",
    envs={"DEMO_ENV": "sandbox-only"},
) as sandbox:
    print(sandbox.commands.run('echo -n "DEMO_ENV=$DEMO_ENV"').stdout)
    # DEMO_ENV=sandbox-only

单次命令 / PTY / 代码执行时

调用级 envs 仅作用于当前调用，并覆盖创建沙箱时的同名变量（优先级最高）：

with Sandbox.create(
    template="tpl-example",
    envs={"DEMO_ENV": "sandbox-only"},
) as sandbox:
    print(sandbox.commands.run('echo -n "DEMO_ENV=$DEMO_ENV"',
    envs={"DEMO_ENV": "one-shot"}).stdout)
    # DEMO_ENV=one-shot

可见性总结

来源commands.run / SDK PTYcubecli exec / OCI Exec主进程 / 服务
镜像 ENV、模板 build envs不应依赖 / 当前通常不可见可见可见
Sandbox.create(envs=...)可见不可见不可见
command / PTY 调用 envs当前调用可见，优先级最高不适用不影响
run_code(..., envs=...)不适用仅当前执行不适用
选择建议：固定配置（运行环境、默认参数）用模板 --env；动态配置（密钥、用户参数）用 Sandbox.create(envs={...})——最常用、灵活且不污染模板；临时变量在代码内 os.environ 设置。

9模板别名

模板别名是稳定且易读的名称。应用配置无需保存 tpl-01abc... 这样的生成 ID，可改用 python-runtime。模板重建或替换后，应用仍可使用固定别名，由运维把别名切到新模板。

from cubesandbox import Sandbox

with Sandbox.create(template="python-runtime") as sandbox:
    print(sandbox.commands.run("python3 --version").stdout)

命名规则与行为

  • 只能包含小写字母、数字和连字符；必须以字母或数字开头；长度为 1 到 64 个字符。
  • 不能使用保留的 tpl- 或 snap- 前缀；不能分配给快照。
  • 同一时间只能属于一个 READY 模板；每个模板最多一个别名。
有效别名无效别名无效原因
python、python-3-12、app-v2MyApp含大写
—my_app含下划线
—-my-app以连字符开头
—tpl-custom使用保留前缀 tpl-
把已有别名分配给另一个模板时，别名会转移到目标模板并从原模板清除。应视为一次部署变更：已运行的沙箱不受影响，后续通过该别名执行的操作会解析到新模板。

创建时设置别名

cubemastercli tpl create-from-image \
  --image ghcr.io/example/python-runtime:3.12 \
  --alias python-runtime \
  --writable-layer-size 2G \
  --expose-port 49983 \
  --probe 49983 \
  --probe-path /health

模板 ID 仍由服务端生成；模板达到 READY 并成功取得别名后，别名才可使用。通过 E2B 风格 SDK 构建时，name 字段即稳定别名：

from cubesandbox import Template

job = Template.build(
    image="ghcr.io/example/python-runtime:3.12",
    name="python-runtime",
    writable_layer_size="2G",
    exposed_ports=[49983],
    probe_port=49983,
    probe_path="/health",
)
print(job.template_id)

设置、修改或清除别名

# 为已有的 READY 模板设置或修改别名
cubemastercli tpl set-alias tpl-01abc --alias python-runtime

# 第一个参数既可以是模板 ID，也可以是模板当前的别名
cubemastercli tpl set-alias python-runtime --alias python-runtime-v2

# 清除别名
cubemastercli tpl set-alias tpl-01abc --clear

各语言 SDK 提供相同操作：

# Python
Template.set_alias("tpl-01abc", "python-runtime")
Template.set_alias("tpl-01abc", None)  # 清除

# Go
info, err := client.SetTemplateAlias(ctx, "tpl-01abc", "python-runtime")
_, err = client.SetTemplateAlias(ctx, info.TemplateID, "") // 清除

# Node.js
await Template.setAlias("tpl-01abc", "python-runtime");
await Template.setAlias("tpl-01abc", null); // 清除

使用和查询别名

任何接受模板标识符的位置都能传别名（包括创建沙箱）。列表和详情响应的 aliases 数组返回已配置别名，也可直接经 CubeAPI 解析：

curl http://<cubeapi-host>:3000/templates/aliases/python-runtime
# { "templateID": "tpl-01abc", "public": false }

安全发布流程

1 构建新模板：暂时不修改生产环境使用的别名。
↓
2 验证：等待新模板 READY，用生成的模板 ID 完成验证。
↓
3 切换别名：把生产别名分配给新模板。
↓
4 回归：用别名创建测试沙箱，确认解析符合预期。
↓
5 收尾：按回滚策略保留或删除旧模板。
修改别名不会改变或重启已经存在的沙箱。

10MCP 网关

MCP（Model Context Protocol）是 AI Agent 发现和调用工具的协议。mcp 参数用于创建沙箱时声明需要哪些 MCP 服务，这些服务运行在沙箱内部，与你自己的机器隔离。创建后你会拿到一个 URL 和一个 Token，Agent 连上即可调用所有已声明服务提供的工具。

预览特性：MCP 支持目前处于预览阶段，mcp 参数和示例网关都可能调整。 
from cubesandbox import Sandbox

sandbox = Sandbox.create(mcp={"time": {}, "fetch": {}})
url = sandbox.get_mcp_url()      # http://50005-<sandbox-id>.<domain>/mcp
token = sandbox.get_mcp_token()  # 以 "Authorization: Bearer <token>" 发送

工作原理与调用链

MCP 调用链
你的 AgentMCP over HTTP + Token
CubeProxy50005-<id>.<domain>
↓ 路由到沙箱 50005
沙箱内的 mcp-gateway端口 50005 /mcp
↓ stdio
time 服务
fetch 服务
github/... 服务
1 CubeAPI：校验 mcp 结构，格式不对在创建任何沙箱前返回 400。它不保存该值，也不下发调度层或在响应中返回。
↓
2 模板：SDK 按「模板优先级」确定模板，该模板中必须包含 mcp-gateway 程序，默认沙箱镜像里没有。
↓
3 SDK：沙箱启动后，SDK 以 root 执行 mcp-gateway --config '<json>'，通过 GATEWAY_ACCESS_TOKEN 传随机 Token，最多等 60 秒。
↓
4 网关：拉起所需服务并在 50005 对外提供工具；CubeProxy 把 50005-<id>.<domain> 路由到该端口。
↓
5 失败处理：命令失败或超时，SDK 销毁沙箱并抛出附网关输出的 Failed to start MCP gateway: ...。

Cube 本身只负责第 1、3 步和路由；沙箱里实际跑什么，由模板决定。

模板优先级

顺序规则
1传了 template（Go 为 TemplateID），用对应模板
2未传 template，用别名为 mcp-gateway 的模板
3上述都不存在，用环境变量 CUBE_TEMPLATE_ID 对应模板
4全部不存在，创建失败并报模板不存在错误

想改默认别名（默认 mcp-gateway），设环境变量 CUBE_MCP_TEMPLATE_ID：

export CUBE_MCP_TEMPLATE_ID=custom-mcp-gateway

网关约定

任何程序都可充当网关，只要以 mcp-gateway 为名装在 PATH 中并满足以下约定：

项目要求
命令以 root 执行 mcp-gateway --config '<json>'，<json> 即创建沙箱时的 mcp 对象
Token从 GATEWAY_ACCESS_TOKEN 读取并写入 /etc/mcp-gateway/.token；get_mcp_token() 从此文件取回
就绪命令退出后网关需继续服务；端点就绪才以 0 退出，失败以非零码退出并输出可读错误；必须 60 秒内完成
端点端口 50005、路径 /mcp 上的 MCP streamable HTTP 端点，拒绝无 Authorization: Bearer <token> 的请求
模板创建模板时暴露端口 50005

示例网关快速上手

cd examples/mcp-gateway
docker build -f template/Dockerfile \
  --build-arg BASE_IMAGE=cube-sandbox-cn.tencentcloudcr.com/cube-sandbox/sandbox-code:latest \
  --build-arg MCP_SERVERS="duckduckgo fetch time arxiv" \
  -t <镜像仓库>/mcp-gateway:latest .
docker push <镜像仓库>/mcp-gateway:latest

cubemastercli tpl create-from-image \
  --image <镜像仓库>/mcp-gateway:latest \
  --alias mcp-gateway \
  --writable-layer-size 1G \
  --expose-port 49983 --expose-port 49999 --expose-port 50005 \
  --probe 49983 --probe-path /health

调用工具（pip install mcp）：

import asyncio
from cubesandbox import Sandbox
from mcp import ClientSession
from mcp.client.streamable_http import streamablehttp_client

async def main():
    with Sandbox.create(mcp={"time": {}, "fetch": {}}) as sandbox:
        headers = {"Authorization": f"Bearer {sandbox.get_mcp_token()}"}
        async with streamablehttp_client(sandbox.get_mcp_url(), headers=headers) as (read, write, _):
            async with ClientSession(read, write) as session:
                await session.initialize()
                print([tool.name for tool in (await session.list_tools()).tools])
                result = await session.call_tool("get_current_time", {"timezone": "Asia/Shanghai"})
                print(result.content[0].text)

asyncio.run(main())

示例网关支持三类条目：目录服务（duckduckgo、arxiv、fetch、time、filesystem、memory、sequentialthinking，可在模板内 mcp-gateway catalog 查看）、GitHub 服务（github/<owner>/<repo>，执行 installCmd 后 runCmd）和本地命令（任意带 runCmd 的键）。同名工具按服务名排序，第一个保留原名，其余重命名为 <server>_<tool>；网关只聚合工具，不提供 prompts 和 resources。端口 50005 上的 GET /health 无需 Token，返回服务数和工具数。

输入校验

以下情况 CubeAPI 返回 400：

  • mcp 不是对象；某个条目不是对象；
  • GitHub 键不符合 github/<owner>/<repo> 格式；缺少 runCmd 或为空；
  • envs 中有非法变量名或非字符串值；
  • 服务数量超过 64 个。

服务名是否可识别由网关判断，示例网关遇到未知服务名会启动失败，SDK 会把这个错误报出来。

生命周期

  • 暂停 / 恢复：网关及其服务进程属于内存快照的一部分，恢复后继续用原 Token 服务。
  • 重新连接：get_mcp_token() 读 Token 文件，新的 SDK 句柄可直接复用端点。
  • 克隆与快照恢复：运行中的网关及 Token 一并复制，所有克隆接受同一 Token，应视为同一信任域。
  • 进程崩溃：某个服务进程退出后，网关会在下一次调用时重新启动它。

安全说明

同一沙箱内的所有 MCP 服务属于同一信任域，彼此之间没有隔离。示例网关以 root 运行所有服务，任何服务都能读取其他服务的 envs（如 /proc/<pid>/environ）和 /etc/mcp-gateway/.token 并外传；GitHub 服务的 installCmd/runCmd 本身就是以 root 执行的任意命令。不要把不可信的服务和敏感凭据放进同一个沙箱；需要隔离时为不同信任域分别创建沙箱。
  • Token 只保护 MCP 端点本身；CubeProxy 鉴权和网络策略照常生效，沙箱内服务也受出网规则约束。
  • 与 E2B 约定一致，SDK 通过命令行参数传 mcp 配置，网关启动期间（最长约 60 秒）完整配置（含 envs）会出现在进程参数中，沙箱内任何进程都能读到。
  • 示例网关会从自身及每个服务的环境变量中移除 Token，只把 envs 设到所属服务环境变量，不写盘或日志（但不能防范恶意服务）。
  • 示例网关日志 /var/log/mcp-gateway.log 会记录各服务 stderr；服务自行打印密钥时也会出现在其中。

使用自己的网关

你可以用任何满足「网关约定」的程序替换示例网关。例如在 Docker MCP Gateway 这类网关前放一个名为 mcp-gateway 的轻量启动脚本；E2B 托管的 mcp-gateway 模板就基于 Docker MCP Gateway 构建。注意 Docker MCP Gateway 会把每个服务作为容器运行，因此模板里还需一个能在沙箱内正常工作的 Docker 守护进程——CubeSandbox 尚未验证过这种方式（以官方文档为准）。

自测

自测

1. 自定义镜像里 ENTRYPOINT 必须保留 cube-entrypoint.sh，它自动追加的参数是什么？为什么不能省？

自动追加的是 -isnotfc。它让 envd 跳过对 169.254.169.254 的 Firecracker MMDS 查询。CubeSandbox 不使用 Firecracker，MMDS 服务不存在；缺少此参数会让 envd 访问不存在的 MMDS，可能引发网络超时、/init 延迟、env_vars 注入失败等问题。

2. 模板已经 READY，但 distribution 显示 0/N ready 且长时间不变，你会怎么查？

多数情况是 artifact 正在分发到各节点，多节点集群稍等即可；若长时间未恢复，去目标节点查 Cubelet 日志：journalctl -u cubelet -f。同时可先重跑 tpl info 确认状态。

3. 为什么创建沙箱时用 Sandbox.create(envs={...}) 注入的变量，commands.run 能看到，但默认 run_code 看不到？

commands.run 经 envd 处理，会带上沙箱级 envs；而 run_code 走 lightweight code interpreter / Jupyter kernel，默认不会把 envd 中的沙箱环境变量注入 Jupyter kernel。若希望 run_code() 自动继承 Sandbox.create(envs=...)，需使用仓库的 run-code-env-inheritance 派生镜像。
