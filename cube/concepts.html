生命周期、Webhook 与 QoS

1沙箱状态模型

沙箱（Sandbox）是 CubeSandbox 的核心运行单元。任一时刻，一个沙箱只处于下表的六种状态之一；状态迁移由 timeout（空闲秒数）和 on_timeout（"kill" 或 "pause"）两个参数驱动。

状态与迁移
create() → running → pausing → paused → resuming → running
running — timeout & on_timeout=kill → terminated ← timeout & on_timeout=kill — paused
running — kill() → terminated ← kill() — paused
unknown ← 创建中 · 容器已退出 · 节点读取失败
状态含义是否瞬时能否恢复
running正在运行，CPU/内存被实际占用，可以接收请求与执行代码否—
pausing平台正在暂停沙箱（保存 VM 快照中）是—
paused已暂停，VM 内存已落盘为快照，不消耗 CPU 与内存，状态完整保留否可以（connect / auto_resume）
resuming平台正在从快照恢复沙箱是—
terminated被显式销毁（kill）或因 on_timeout="kill" 超时回收否（终态）不可以
unknownCubeAPI 无法把沙箱映射为上表任一状态：仍在创建、容器已退出，或无法从节点读取状态取决于原因视情况而定
unknown 不等于「已经没了」。上述三种情况 CubeAPI 都会报 unknown。上表的 terminated 描述的是 kill() 与 on_timeout="kill" 的结果；容器自行退出时报的是 unknown，而不是另一个独立的终态。只看 state 无法区分「还在启动」还是「已经死了」，判据是 POST /sandboxes/<id>/connect：容器已经退出时返回 HTTP 409（... is not connectable in state 'stopped'），另外两种情况仍能正常 connect。

timeout 的取值语义

timeout 取值行为
不传使用服务端配置的默认空闲超时；服务端未配置或设为 <= 0 时，永不超时
NEVER_TIMEOUT（-1）永不超时，不会因空闲被自动回收（Go：cubesandbox.NeverTimeout；Python：from cubesandbox import NEVER_TIMEOUT）
0立刻超时，空闲后首次扫描即回收
正整数 N空闲 N 秒后触发超时

timeout 的单位是秒（e2b 的 timeoutMs 是毫秒）。on_timeout 默认为 "kill"；只有显式设为 "pause" 才会在超时后暂停而不是销毁。SDK 不再自带 300 秒之类的默认值。

异常与退出原因（errorReason）

当沙箱进入 unknown 或发生暂停失败时，可通过 GET /sandboxes/<id> 返回的 errorReason 查看原因。它是 CubeSandbox 扩展字段，e2b API 中无对应字段；仅反映主容器，正常运行或无异常记录时省略。

errorReason含义
Completed主进程正常退出（退出码 0）
Error主进程异常退出（非零退出码或被信号终止）
OOMKilled因内存不足被终止
SandboxCrashed沙箱运行时异常中断
PauseFailed暂停失败（沙箱可能仍在运行）

errorReason 仅提供诊断信息，不改变 state；沙箱恢复运行后会清除旧的退出原因，删除后不保留历史。若沙箱启用了自动重启，重启进度和最近一次触发重启的原因请看 查询重启状态。

endAt 与 endAtStatus

endAt 是沙箱预计超时的时间，用最后一次设置 timeout 的时刻（创建、set_timeout、resume）加上 timeout 算出来。有流量的沙箱会被保活，实际暂停可能晚于这个时间，所以把它当作「最早可能暂停的时间」，而不是准确时刻。暂停不会取消有限的超时，因此暂停中的沙箱在详情和列表 API 里仍返回相同的 endAt。E2B SDK 要求每个响应都带该字段，所以它总是存在；具体含义看旁边的 endAtStatus。

endAtStatusendAt含义
deadline预计时刻存在有限的超时。它是估算值，有流量时实际暂停会更晚
never9999-12-31T23:59:59Z沙箱永不超时。哨兵不是真实时刻
unknown9999-12-31T23:59:59Z截止时间查询失败。按未知处理，不要据此回收沙箱

同一响应还会回显沙箱持久化的配置：lifecycle（onTimeout 与 autoResume）、allowInternetAccess（出网开关）、network（allowOut、denyOut、allowPublicTraffic、maskRequestHost）。字段缺席是因为持久化 spec 没读到（未知），或该项从未设置、由服务端默认值生效。egress 规则永远不会出现在这些响应里，因为规则可能携带 inject 密钥；当规则是沙箱唯一的出网策略时，network 只带 "rulesPresent": true，告知「存在策略」而不暴露内容。

2生命周期操作：创建、查询、销毁与暂停

SDK 形态与 e2b 保持一致，便于已有 e2b 用户直接迁移。下面按「创建 → 查询/列出 → 销毁 → 暂停/恢复」给出最小可用代码与 API 语义。

创建沙箱

from cubesandbox import Sandbox

# 创建沙箱，空闲 60 秒后自动销毁（默认 on_timeout="kill"）
sandbox = Sandbox.create(
    template="<your-template-id>",
    timeout=60,                # 单位：秒
)

print(sandbox.sandbox_id)
Sandbox.create() 参数说明
template模板 ID，沙箱基于它启动；缺省读环境变量 CUBE_TEMPLATE_ID
timeout可选，空闲超时（秒），取值见上一节
lifecycle生命周期策略，{"on_timeout": "pause", "auto_resume": true} 等形式
metadata任意键值对，写入沙箱元数据，可在列表 / 详情接口中读出
env_vars注入沙箱进程的环境变量
allow_internet_access是否允许出公网；network 提供更细粒度的出站策略
Cube 不像托管 e2b 那样有严格的 24h/1h 单次运行上限。省略 timeout 时，实际空闲 TTL 由集群运维在服务端配置（见 集群默认空闲超时）。

显式销毁

sandbox.kill()

kill() 是不可逆的：与暂停不同，被 kill 的沙箱不能恢复。即便 lifecycle.on_timeout="pause"，调用 kill() 仍然立即终止并丢弃快照。

kill() 和 DELETE /sandboxes/{sandboxID} 均可用于删除处于 running 或 paused 状态的沙箱。删除 paused 沙箱时，CubeSandbox 不会先 Resume / 唤醒 MicroVM；控制面直接删除 paused tombstone、清理 pause 快照（catalog / CoW）并清除 pause 元数据。Plugin volume 的 refcount 已在 Pause 时调整，删除路径无需为销毁再挂载一遍。

删除 paused 沙箱的返回含义与处理
204 No Content沙箱、pause 快照及相关资源已经完成清理；接口保持同步语义，只有清理完成后才返回
503 Service Unavailable + Retry-After: 2沙箱正在进入暂停状态，或其他生命周期操作（pause / resume / delete）尚未完成并持有沙箱锁；至少等待 2 秒后重试
404 / 408行为保持不变；running 沙箱的删除行为也保持不变

删除路径不是一次 Resume：不会触发 sandbox.resumed 生命周期事件、不会重置空闲超时、也不需要节点容量准入。Retry-After 的单位为秒，仅用于提示客户端等待后重试；它不表示 CubeSandbox 会在后台继续删除，也不会启动后台重试任务。

暂停与恢复

sandbox.pause()                       # 主动保存快照，释放 CPU/内存
# ... 一段时间过去 ...
sandbox = Sandbox.connect(sandbox.sandbox_id, timeout=300)  # 从快照恢复，并重置空闲超时
sandbox.run_code("print('back!')")    # 像没暂停过一样继续用
未关闭的 cubecli exec / 交互会话会阻止 Pause。Cubelet 返回 TaskPauseFailed（130588）和 pause forbidding / terminate exec tasks first 类错误，但沙箱保持 running（不会落成 unknown(failed)）；会话结束后 auto-pause 会重试。Cubelet 只有在 shim 声明支持 CheckPauseAllowed（update.check_pause_allowed）时才先做预检；没有声明的 shim 直接走 PauseToSnapshot，由它在冻结前做同样的检查。该 busy-reject 分类需要 Cubelet、CubeMaster 与 CubeShim 一起升级；新版 CubeShim 会在拒绝信息前加 shim_error_pause_busy 错误码，CubeMaster 同时识别该错误码与历史文案。

pause() 不会取消空闲回收。默认 on_timeout="kill" 时，之后被暂停的沙箱空闲仍超过 timeout 一样会被销毁。若要保住暂停中的沙箱，请传 timeout=NEVER_TIMEOUT、省略 timeout（且服务端未设正数默认）、或把 timeout 设得足够大。

connect(timeout=...)效果
不传 / None保持当前超时
NEVER_TIMEOUT（-1）连接后永不超时
N > 0确保至少剩余 N 秒；运行中或暂停中的沙箱保留更长的现有 deadline，否则在连接后重新开 N 秒窗口
0 或 N < -1拒绝请求并返回 HTTP 400

连接或恢复暂停中的沙箱时，如果该沙箱上另一个生命周期操作尚未完成、沙箱还没有运行，CubeAPI 返回 HTTP 503 和 Retry-After: 2，请至少等待该时间后重试。如果并发请求已经把沙箱恢复，connect 会成功并返回连接信息，POST /sandboxes/<id>/resume 则返回 409（已在运行）。connect 返回 409 也可能是沙箱容器已经退出：这种状态不可恢复，重试不会成功。

已弃用的 resume(timeout=...)效果
不传 / None保持当前超时
0保持当前超时（立刻到期请用 set_timeout(0)）
NEVER_TIMEOUT（-1）恢复后永不超时
N > 0从恢复时刻起重新开 N 秒窗口
N < -1拒绝请求并返回 HTTP 400

对于运行中的沙箱，connect(timeout=...) 的正数 timeout 只会在请求窗口更长时延长 deadline；如果要主动缩短生命周期，请使用 set_timeout(...)。跨机 Resume（jfs 或 s3，且 remote_status=ready）见 快照与跨机迁移。

Resume 会重建 guest NIC／主机端口，并重写 Redis 沙箱代理路由。CubeMaster 随后调用 CubeProxy 的 POST /admin/backend_cache/delete 清理 local_cache，避免流量继续打到 pause 前的旧 IP；清理失败时，Resume 会直接返回错误。

3自动暂停与自动恢复

很多 Agent 工作负载并不持续繁忙：用户敲一段代码 → 模型推理 → 沙箱执行 → 等待下一轮交互。在等待期间让沙箱自动暂停，下次请求来时再自动恢复，可以显著降低资源占用。Cube 提供与 e2b lifecycle 完全一致的配置形态。

sandbox = Sandbox.create(
    template="<your-template-id>",
    timeout=300,                      # 5 分钟空闲后触发 on_timeout
    lifecycle={
        "on_timeout": "pause",        # 空闲超时后 → 暂停（而不是销毁）
        "auto_resume": True,          # 暂停后下一次请求 → 透明恢复
    },
)

行为说明

  • on_timeout="pause"：沙箱空闲 timeout 秒后，平台调度暂停流程，state 变为 paused，VM 内存被冷藏到快照存储。
  • auto_resume=True：当再有任何请求路由到这个 paused 沙箱（HTTP 请求、run_code、文件读写等），平台自动唤醒它，调用方无需显式 connect()；典型恢复时间在亚秒级到秒级。
  • 如果 auto_resume=False（或省略），沙箱暂停后必须显式 Sandbox.connect(sandbox_id=...) 才能再用，适合「等用户决定」的场景。

何时算「活跃」与 timeout 重置

下列动作都会重置 idle 计时：

  • 通过 SDK 调用：sandbox.run_code(...)、sandbox.commands.run(...)、sandbox.files.read(...) / write(...)。
  • 通过 HTTP 直连沙箱内的服务（例如 getHost() 返回的 URL）。
请求在开始时和响应结束时各算一次活跃，中间的执行时间不算。因此单个请求若运行时间超过 timeout（例如 timeout=300 时执行 commands.run("sleep 900")），可能在执行途中被暂停。对这类调用，请在长请求运行期间定期（间隔小于 timeout）向沙箱发送轻量请求，或先用 set_timeout(...) 调大超时。

每次自动恢复成功后，空闲计时重置，但超时时长不变。所以「恢复 → 短暂使用 → 再次空闲超时 → 再次暂停」的循环可以无缝持续。未配置 auto_pause / 不传 lifecycle 的沙箱默认行为是 on_timeout="kill"：空闲超过 timeout 秒后平台会主动销毁该沙箱。

端到端示例

T+0最后一次活跃

一次 run_code、文件读写或 HTTP 响应结束，idle 计时重新开始。

T+timeout空闲超时

lifecycle.on_timeout="pause"，平台调度暂停流程，进入 pausing。

暂停中pausing → paused

VM 内存冷藏到快照存储，CPU 与内存物理释放，状态完整保留。

T+X请求到达

HTTP、run_code 或文件操作被路由到 paused 沙箱。

恢复中resuming → running

auto_resume=True 自动恢复，调用方无需 connect()，典型亚秒到秒级。

恢复后idle 计时重置

超时时长不变，可继续循环；若 on_timeout="kill" 则超时后直接销毁。

平台提供两个互为镜像的端到端演示，对应 on_timeout 的两种取值：

export CUBE_TEMPLATE_ID=<your-template>

# 自动暂停 + 自动恢复
python examples/code-sandbox-quickstart/auto-resume.py

# 自动销毁（不可恢复）
python examples/code-sandbox-quickstart/auto-kill.py
  • auto-resume.py：on_timeout="pause" + auto_resume=True。创建沙箱、空闲触发自动暂停、再发请求触发自动恢复，最终对比「内核内存 + 文件系统」两层状态，验证全状态保留。
  • auto-kill.py：on_timeout="kill"（默认行为）。创建沙箱、空闲触发自动销毁、验证后续请求以 410 Gone 快速失败、Sandbox.list() 不再返回该沙箱，并通过创建一个对照沙箱排除集群整体故障。

资源释放与节点调度配额

沙箱暂停后，其 CPU 和内存在物理上已被回收；但在默认情况下，节点资源计账仍然将暂停中（paused / pausing）的沙箱视为「已占用」调度配额。这意味着：即使大量闲置沙箱被暂停，宿主机上仍然没有「空位」来创建新沙箱。

为此 Cube 提供节点级调节旋钮 host.quota.paused_resource_release_ratio（在 Cubelet/config/config.toml 中配置），值域 [0, 1]，默认 0。

取值行为适用场景
0.0暂停沙箱保留完整配额（与旧版本行为一致）。恢复始终有保障，不会因资源不足被拒绝对可用性要求极高、不希望恢复失败的场景
1.0暂停沙箱的 CPU/内存配额全部释放给调度器。恢复变为尽力而为，节点资源不足时恢复会被拒绝追求最大化部署密度、允许恢复偶尔失败的场景
0 < r < 1释放 r 比例，保留 (1-r) 作为余量。保留的配额仍计入调度器 CPU/内存使用量，暂停密集的节点会被自然降权在可用性和高利用率之间折中
 
# Cubelet/config/config.toml
[host.quota]
paused_resource_release_ratio = 0.5   # 释放一半，保留一半

当 ratio > 0 时，恢复操作会触发本地实时准入检查；如果节点当前无法容纳该沙箱释放出去的资源量，恢复会被拒绝：

resume rejected by paused_resource_release_ratio policy: need 1024MB > quota 512MB

拒绝信息通过 Cubelet (130409 Conflict) → CubeAPI (HTTP 409) → WebUI（显示容量诊断） 透传给客户端。409 是可重试的状态码：当其他沙箱被销毁或暂停、节点资源释放后，恢复可以重新尝试。

注意事项：磁盘和 MvmNum 不受 ratio 影响，暂停快照始终占用存储空间，沙箱对象始终存在；ratio=0 是零值安全的默认值；此项为节点级配置，不同节点可设不同比值；大批沙箱同时唤醒、单节点无法承载时，控制面返回 409 并给出具体配额数字，使用共享后端时调度器可回退到其他兼容节点。

集群默认空闲超时（default_timeout_insec）

客户端不传 timeout 时，由 CubeMaster 读取 CubeMaster/conf.yaml 中的 cubelet_conf.default_timeout_insec（one-click 安装路径：/usr/local/services/cubetoolbox/CubeMaster/conf.yaml）。

配置值客户端省略 timeout 时的效果
未配置或 <= 0不设集群级空闲 TTL，沙箱不会因空闲被自动回收
正整数 N默认空闲 N 秒后触发超时

仓库默认不配置集群级空闲超时（default_timeout_insec: -1）。若希望集群自动回收未显式传 timeout 的沙箱，可改为正数（例如 300），修改后需重启 cube-sandbox-cubemaster.service。同一段里的 create_timeout_insec 与空闲 TTL 无关，仅限制创建/调度 RPC 的截止时间。

状态保真与运维

  • 暂停的状态保真度：CPU 寄存器、进程内存、TCP 连接（无外部对端）、文件系统改动都会随快照保留；面向外部的连接（如沙箱主动建立的 outbound socket）会在暂停时断开，恢复后由应用层自行重连。
  • 集群一致性：自动暂停由 cube-lifecycle-manager 协调，Helm chart 与 Terraform 一键部署默认都是两个温备副本。两个副本都消费生命周期事件、发现 CubeProxy 并处理恢复回调，由 Redis 租约选出一个副本执行空闲扫描、销毁和过期注册清理。leader 故障切换后沙箱可能多一次 pause/resume，下次请求会照常 auto-resume。每沙箱 Redis 状态转换与 CubeMaster lifecycle lock 共同串行化跨副本的有效暂停/恢复操作。
  • 失败回退：自动恢复 RPC 失败时，CubeProxy 直接对客户端返回 503 + Retry-After，不会让用户卡在长超时上；当沙箱已经被销毁（killing / killed），则返回 410 Gone 让客户端立即停止重试。
  • 故障排查：控制节点上执行 docker logs cube-lifecycle-manager，关键事件包括 create event applied、auto-paused sandbox、auto-resumed sandbox、timeout-killed sandbox。每个 CubeProxy 副本额外提供 GET http://<node-ip>:8082/admin/healthz，其中 heartbeat_last_pushed_ms 表示该副本最近一次向 manager 上报心跳的时间戳；管理端口默认 8082，被占用时可用 CUBE_PROXY_ADMIN_PORT 覆盖。

4进程退出后的重启

创建沙箱时可以带 restartPolicy，语义和 Kubernetes 的 restartPolicy 一样：重启由沙箱主进程（主容器的 init 进程）退出或存活探针失败触发，单位是整台沙箱（一台 MicroVM），不是沙箱里的某个进程。

restartPolicy行为
Never（默认）退出后不重启
OnFailure非 0 退出、OOM、沙箱崩溃，或存活探针失败时重启
Always任何退出都重启，包括正常退出；存活探针失败也会重启

退避与重启上限

重启会保留磁盘、网络、卷与宿主目录挂载，以及沙箱 ID，再冷启动一次；内存不保留。连续失败从 10 秒开始退避，每次加倍，最长 300 秒；运行满 10 分钟视为稳定，重启计数清零。「稳定」从当前这次运行开始运行的时刻起算——即沙箱被创建、重启成功或从暂停中恢复的时刻。失败的重启尝试不会重置这个计时，因此崩溃循环无法给自己续命；稳定窗口一到，节点就会执行清零，不需要等到下一次退出。

重启次数上限由 restartBackoff.maxRestarts 控制，默认 0 表示不限；集群可以用 cubelet_conf.max_restarts_cap 设全局上限，配置后，0（不限）也会被收紧到该值。达到上限后不再重启，沙箱不再自动拉起，但仍计入节点 MvmNum 配额，直到空闲超时或被显式销毁。重启 Cubelet 也不会让已达到上限的沙箱复活：稳定期重置只负责归还重试额度，不会代替策略去启动一个已经放弃的沙箱。

存活探针

存活探针写在创建请求里。没有探针、且镜像带 envd（暴露 49983）时，节点会默认请求 GET /health；没有 envd 的镜像不会被探测，避免误重启。Never 配存活探针会被拒绝，返回 HTTP 400：探测永远不可能触发重启，只会把沙箱杀掉。

{
  "restartPolicy": "OnFailure",
  "restartBackoff": {
    "initialIntervalSecond": 10,
    "multiplier": 2,
    "maxIntervalSecond": 300,
    "maxRestarts": 5
  },
  "livenessProbe": {
    "httpGet": {
      "path": "/health",
      "port": 8080
    },
    "initialDelaySecond": 30,
    "periodSecond": 10,
    "probeTimeoutSecond": 1,
    "failureThreshold": 3
  }
}

上面的片段会检查 8080 端口上的 GET /health，连续失败三次后按 OnFailure 策略冷重启整个沙箱。如需 TCP 探测，可将 httpGet 替换为 tcpSocket；两种探测类型只能配置一种。探针时间的单位均为秒；未填写或填写非正数时，默认启动延迟 30 秒、检查周期 10 秒、单次超时 1 秒、连续失败阈值 3 次。

查询重启状态

GET /sandboxes/<id> 和列表接口会返回 restartStatus，它是 state 之外的独立对象：state 回答「沙箱在生命周期哪一站」，restartStatus 回答「重启状态机走到哪、为什么停下」。容器自行退出后，state 只会报 unknown，只有靠这个对象才能分清正常退出、崩溃和放弃重启。

它不改变 state，只在策略为 OnFailure / Always、或沙箱发生过退出时出现；默认 Never 且从未退出过的沙箱没有它。restartState 首字母大写，和 state 的小写枚举不是一套；表中的「主进程」指主容器的 init 进程。

restartState含义
Running重启状态机空闲：创建成功或最近一次重启成功。不代表沙箱正在运行，是否在运行看 state
Restarting正在重建：销毁旧 VM，再冷启动新 VM
BackOff已退出，等待退避结束；nextRestartAt 是下次尝试时间
GaveUp达到 maxRestarts，或重建/销毁遇到不可恢复的失败（包括保留的根盘经 e2fsck 仍无法修到干净），不再重试
Succeeded主进程正常退出（退出码 0），策略决定不重启（Never，或 OnFailure 且退出码为 0）
Failed主进程异常退出，策略决定不重启（Never 下的任何失败）

Restarting、BackOff 是重启流程中的瞬时态；GaveUp、Succeeded、Failed 是终态，不会再自动拉起。Always 不会停在 Succeeded / Failed：它会一直重启；如果设了 maxRestarts，达到上限后进入 GaveUp。这两个瞬时态期间不会自动暂停；但空闲超时照常生效，重启操作也不会重置空闲计时。对象里还有 restartCount、lastExitCode、lastExitReason、lastRestartAt 等字段，可用于定位退出原因。

暂停不算一次重启：pause() 后恢复会保留 restartCount 与退出诊断信息，退避间隔也从该计数继续计算。只有稳定期重置才会清零它，因此已经达到 maxRestarts 的沙箱即便中间暂停再恢复，下一次退出后仍会停止重启。

errorReason 与 restartStatus.lastExitReason 的区别：errorReason（仅详情接口）反映主容器当前保存的异常或退出原因，宿主机断电这类未产生退出事件的场景下可能为空；restartStatus.lastExitReason 反映重启管理器记录的最近一次触发重启决策的原因（包括存活探针失败 LivenessProbeFailed、宿主机断电 SandboxCrashed 等）。排查重启过程时以 restartStatus 为准。

宿主机宕机与 Cubelet 重启后的恢复

宿主机断电、内核崩溃或其他导致整机重启的故障不会留下退出事件：容器运行时状态在 tmpfs 上，随机器一起消失，沙箱来不及记录自己是怎么结束的。Cubelet 启动时会重新读取每个沙箱的真实状态，并按下列规则决定是否拉起：

恢复时看到的状态判定结果
找不到容器或 task，且此前没有记录过退出SandboxCrashed（lastExitCode 为 0）OnFailure、Always 按退避策略冷重启；Never 不重启
task 处于停止状态，带真实退出码按真实退出码判定：0 为 Completed，非 0 为 ErrorOnFailure 只在非 0 时重启；退出码与原因会写入 restartStatus
崩溃前已因存活探针失败、OOM 等进入退避沿用那条记录的原因继续按原退避与 maxRestarts 计数重试

宿主机宕机按崩溃处理，因此断电重启不会让 OnFailure 沙箱停在 Succeeded；restartStatus.lastExitReason 会记录 "SandboxCrashed"。

Cubelet 自身重启（不是宿主机宕机）时，VM 通常仍在运行，恢复只重挂存活探针，不改变任何状态。若 VM 恰好在 Cubelet 停止期间正常退出（退出码 0），OnFailure 仍按真实退出码判为 Completed 并进入 Succeeded，不会误重启；若它以非 0 退出，则按真实退出码重启。上一次运行留下的 lastExitCode / lastExitReason 只用于展示诊断信息，不参与本次判定。

以下情况一律不会被自动拉起：Never、暂停中的沙箱、已进入终态（GaveUp、Succeeded、Failed）的沙箱，以及正在被删除的沙箱。大批量沙箱同时恢复时，节点按固定并发上限分批重建（默认 16，远低于节点自身的创建/销毁并发上限），其余沙箱保持 BackOff 排队；排队期间不消耗 maxRestarts，被节点并发限制拒绝的尝试不算一次重启失败。

5生命周期 Webhook

CubeMaster 会向运维配置的接收端 POST 生命周期通知。它是静态订阅，作用于整个集群，默认关闭，不是 SDK 管理的用户级订阅。Webhook 只观察既有业务结果，投递失败不改变这些结果。

开启通知

  1. 准备接收 JSON POST 的服务，处理重复请求，接纳下游工作后及时返回 2xx。
  2. 将下面的配置块合并到各 Master 配置，替换占位 URL；保留其它平台设置，包括业务 Redis。
  3. 使用一致配置重启所有 Master。运行中的订阅不热更新。执行真实沙箱操作，检查接收端记录和 Master 指标。

  ingress_capacity: 1024
  workers: 4
  request_timeout: 5s
  max_attempts: 3
  store:
    max_records: 10000
  subscriptions:
    - id: lifecycle-receiver
      enabled: true
      url: https://receiver.example.com/cubesandbox/events
      events:

        - sandbox.lifecycle.resumed

事件流转

1. 业务成功：创建、暂停、恢复、销毁等操作返回既有成功结果。
↓
2. 捕获与过滤：CubeMaster 捕获事件，按订阅精确匹配完整事件名，未匹配则丢弃。
↓
3. 编码与入队：生成 v2 payload，写入 ingress 缓冲，同时受 ingress_capacity 与 store.max_records 约束。
↓
4. 投递：worker 以 HTTP POST 发送，携带 e2b-webhook-id 与每次尝试新的 e2b-delivery-id。
↓
5. 结果：任意 2xx 成功；非 2xx、网络错误或超时按指数退避重试，预算耗尽后丢弃，接收端恢复也不会自动重放。

事件与成功边界

完整事件名CubeMaster 观察到成功的时点

sandbox.lifecycle.resumed公开创建从可信用户快照模板启动成功，或暂停恢复的最终代理 purge 成功。不能仅凭调用方 annotation / ID 前缀判为快照

  • XFS 与 S3 的 pause / checkpoint 都表示本地成功，不表示 S3 上传完成、远端耐久性或跨节点恢复能力；后续上传状态不撤回或重复事件。
  • 创建、暂停、READY 写入或最终 resume purge 失败，不发布其对应成功事件。内部创建回滚、暂停拆除和 resume timeout 刷新不额外产生用户级 killed / updated。Mock 旁路不是真实生命周期通知入口。
  • SetTimeout 接受正数秒数、0（立即截止）和 -1（永不超时），-1 不发 timeout-only 事件。Refresh 只接受正数秒数，拒绝 0 和负数。有限成功响应的 EndAt > 0 即可发布，provider 缺失或失败时也可能如此，因为截止时间可由既有 fallback 提供；这不确认 Redis HSET 或 XADD 成功。Resume 内部刷新不发布 updated。重复成功操作可各自产生新事件。
  • 创建取消遵循既有业务结果：取消先赢、操作返回失败时，后台随后成功和内部回收均不发布 created / resumed / killed。若业务成功先返回，之后请求在通知 hook 前取消，不抑制 created 或用户快照 resumed。投递仍为 best effort。
  • Killed 遵循原业务对缺节点、nil / not-found 响应和 warn-only 清理的成功规则，不增加物理销毁或 binding 删除完成的独立证明。业务重试仍执行原节点调用，通知不引入完成门控或生产端去重。

容量、丢失与退出

每 Master 有两级上限，由该 Master 全部订阅共享：

  • Ingress 按等待 writer 的捕获事件计数，满时丢弃事件。
  • store.max_records 按目标任务计数，含 pending 重试和 inflight HTTP。一个事件匹配三个订阅需三条记录。Fanout 可部分成功，任务满时丢该目标，不等空位。Retry 复用原记录，成功 / 耗尽 / 取消释放容量。

每个目标任务的编码正文最多 256 KiB。目标副本和 worker / transport 也占用内存，因此这些上限不限制进程 RSS。通知状态由 DeliveryStore 后的进程内存保存；重启、崩溃或退出可丢失剩余工作。各 Master 不共享通知积压、不互相接管。没有磁盘 / Redis 持久化、严格顺序、恰好一次、零丢失、历史 / 查询或 replay API；Redis 持久化 / HA 留待后续，业务 Redis 仍是平台依赖。

Webhook 先停止接收，在单一两秒总预算或 caller 更早截止时间内尽力 drain，然后取消通知 HTTP / 等待并丢弃剩余工作。不保证全部投完，也不限制整个 App / systemd 两秒退出；SIGKILL 跳过 drain。App 组装当前 memory + HTTP adapter，Go 调用者可通过公开 NewRuntime、通用 options 和静态订阅注入 DeliveryStore / DeliverySender；没有新增 backend YAML 键或持久实现。Put / Claim / Retry / Complete 均有界（App 为 1s），清理共享剩余退出预算。Complete 失败不能确认终态；Close 只统计实际丢弃，未来持久 backend 保留的工作不算丢弃。实现必须遵守 context 取消，sender.Close 只做快速本地释放。

HTTP 与配置安全

  • 公网目标要求 HTTPS，正常验证证书 / 主机名。私网 / 回环 HTTPS 还要求显式匹配的 allowed_cidrs。
  • 本地 HTTP 测试时，将 allow_http: true 与 allowed_cidrs: ["127.0.0.1/32"] 合并到 webhooks，并将订阅 URL 改为 http://127.0.0.1:18096/events。HTTP 必须同时显式开启并匹配私网 / 回环 CIDR，公网 HTTP 仍被阻止。
  • CIDR 不关闭 TLS，不放行 metadata、link-local、未指定、组播或文档地址等被禁特殊地址。全部 DNS 结果均须符合策略，混合允许 / 禁止结果被拒绝。新连接直接拨号到已检查 IP，已检查连接可复用。
  • 禁环境代理、重定向和自动 POST 重放。拒绝 URL 用户凭据 / fragment、未知键和错误类型。响应 body 读取 8 KiB、Header 16 KiB。
  • 非法 webhook 配置只禁用通知，诊断脱敏 webhook 值。主 YAML 非法或其它模块仍沿用原错误策略。API 健康不代表 webhook 已开启。
  • 敏感撤销前先停止全部旧投递实例，再应用新启动配置；混合配置期间仍可发给旧目标。已开始请求无法撤回。重启丢弃旧内存积压，新订阅不接收历史事件。

6QoS：网络与块设备 I/O 限速

QoS（Quality of Service）用来限制单个沙箱的网络和块设备 I/O 消耗。当前版本中该功能默认关闭，且只能在创建模板时配置；模板中的限制会分别应用到每个由它创建的沙箱。网络 QoS 只影响流量速率，不改变沙箱的网络可达范围；块设备 I/O QoS 限制吞吐量和操作速率，不改变文件系统容量或权限。

按源文档口径，本章的 qos 配置只覆盖网络（network）与块设备 I/O（blockIo）。CPU 与内存不属于该 qos 字段的限速范围；它们的资源回收与调度计账由暂停/恢复、paused_resource_release_ratio 和节点 MvmNum 配额等机制承担（见第 3 节）。不要为了限制 CPU / 内存而臆造 qos 子字段，源文档未定义这些字段。

工作原理

QoS 配置从模板进入沙箱运行时，最后由 CubeShim 在 virtio-net 和 virtio-blk 数据路径中执行：

控制面
模板 QoSnetwork / blockIo
CubeMaster模板运行时配置
Cubelet设备请求
↓ 下发到节点数据路径
数据面
CubeShimvirtio 执行点
virtio-net上 / 下行独立限速
virtio-blk每设备吞吐与 IOPS
  • 网络分别限制每个沙箱的两个方向：上传从沙箱发往外部网络，下载从外部网络进入沙箱。配置的带宽上限和数据包处理速率上限会独立应用到上传和下载。
  • 块设备 I/O分别限制沙箱中的每个 virtio-blk 设备。同一设备的读取和写入共享配置的吞吐量桶和操作速率桶，不单独设置读写上限。
  • 底层分别使用吞吐量和操作速率 Token Bucket：吞吐量桶按处理的字节数扣减，操作速率桶每处理一次操作扣减一次。额度按固定速率恢复；桶里有余量时允许短时突发，额度耗尽后需要等待恢复。因此很短的测速可能暂时超过配置值，持续测试的平均速率应接近配置上限。额度大小和恢复速度由平台自动设置，用户只需填写公开的限制值。
  • QoS 是运行时配置，不会修改模板的 rootfs。文件系统输入相同时，不同 QoS 配置仍可复用同一份 rootfs artifact。

配置语义

{
  "network": {
    "bandwidthMbps": 100,
    "packetsPerSecond": 5000
  },
  "blockIo": {
    "throughputMiBps": 64,
    "iops": 1000
  }
}
字段含义约束
network.bandwidthMbps每个沙箱每秒兆比特数，上传与下载分别使用独立额度与 packetsPerSecond 至少配置一个，且为大于 0 的整数
network.packetsPerSecond每秒 virtio-net 数据包处理操作数。启用分段等卸载功能时，一个操作可能对应多个线上数据包，实际线上 PPS 可能与配置值不同同上；不同沙箱之间不共享额度
blockIo.throughputMiBps持续块设备吞吐量，单位 MiB/s与 iops 至少配置一个；同一组限制独立应用到每个 virtio-blk 设备
blockIo.iops每秒块设备 I/O 操作数同上；每个设备分别维护自己的额度

可以只配置网络限制、只配置块设备 I/O 限制，或同时配置两者。当前版本只支持在创建模板时配置 QoS：使用该模板创建的每个沙箱都会应用相同的限制，创建沙箱时不能单独设置或覆盖 QoS。模板未配置 qos 时，不会设置网络或块设备 I/O 限制。

使用边界

  • bandwidthMbps 只限制单个沙箱的最大网络速率。节点级、租户级或 NAT 出口的总带宽仍由底层基础设施决定；所有活跃沙箱的需求超过实际链路容量时，沙箱之间仍会竞争带宽。
  • 当前上传和下载使用相同的带宽和数据包处理速率配置，暂不支持分别设置两个方向的上限；块设备 I/O 也不区分读取和写入限制。
  • QoS 不提供优先级、最低保障吞吐量或权重调度。

内部注解与兼容性

网络和块设备 I/O QoS 内部使用 cube.master.net 和 cube.master.blk.qos 注解存储。它们是运行时契约，不属于公开 API：

  • 沙箱或模板请求中直接设置这两个注解会被拒绝，请改用模板的 qos 字段。
  • 模板的 create_request、preview 和 snapshot 响应不再包含这两个注解，请读取 configuredQos。
  • 带 create_request override 的模板 commit 仍会读取源沙箱的持久化创建请求，以便继承模板托管的 QoS；如果该记录不可读，commit 会失败，而不是生成一个没有限速的模板。

使用 iperf3 验证网络限速

先创建带网络 QoS 的模板并等待模板进入 READY 状态，再使用该模板创建待测沙箱。下面的客户端命令都在这个沙箱内执行。iperf3 不一定预装在服务端或沙箱镜像中，测试前先在两端运行 iperf3 --version；不存在时按系统或镜像使用的包管理器安装，例如 Debian/Ubuntu：

apt-get update
apt-get install -y iperf3

在沙箱能够访问的机器上启动服务端，并确认沙箱能访问服务端 IP、防火墙已放通所选 TCP 端口：

iperf3 -s -p 5201

# 沙箱上传到服务端
iperf3 -c <server-ip> -p 5201 -t 10 -O 3 -P 4

# 沙箱从服务端下载
iperf3 -c <server-ip> -p 5201 -t 10 -O 3 -P 4 -R

测试结果会受到协议开销、Token Bucket 短时突发和测量窗口影响。100 Mbps 的配置通常会测得接近 100 Mbps，不要求精确相等。模板返回 configuredQos 只能说明配置已经保存，带宽限速需要通过持续上传、下载测试确认实测值接近配置上限。iperf3 不能直接测量数据包处理操作数；如果只配置 PPS，应使用固定大小的数据包工作负载，并在测试端点通过报文计数器验证，同时注意卸载功能可能导致线上 PPS 与配置的操作速率不同。

验证多沙箱并发带宽限制时，一个 iperf3 server 进程通常一次只处理一个测试；多个客户端连接同一个 server 端口时测试可能被串行执行，无法反映并发带宽。为每个沙箱启动独立端口：

for port in 5301 5302 5303 5304 5305; do
  iperf3 -s -p "$port" -D
done

同时启动沙箱客户端，分别连接 5301 到 5305。如果模板配置为 100 Mbps，并且宿主机和网络容量足够，5 个沙箱应各自接近 100 Mbps，总吞吐接近 500 Mbps。多沙箱测试还需保证配置的带宽上限之和不超过测试链路容量，否则结果会同时受到共享链路竞争影响，不能只根据单个沙箱低于配置上限判断带宽 limiter 是否正常。

使用 fio 验证块设备 I/O

先创建带块设备 I/O QoS 的模板并等待模板进入 READY 状态，再使用该模板创建待测沙箱。fio 不一定预装在沙箱镜像中，测试前先运行 fio --version；不存在时按镜像使用的包管理器安装，例如 Debian/Ubuntu：apt-get update && apt-get install -y fio。

先在沙箱中执行 lsblk，选择位于可写 virtio-blk 文件系统中的测试目录；不要直接对根块设备执行破坏性测试。下面的命令使用 /tmp/qos-fio 文件，并绕过 guest page cache：

# 持续顺序写吞吐量
fio --name=block-qos-bw --filename=/tmp/qos-fio \
  --size=1G --rw=write --bs=1M --direct=1 --runtime=30 --time_based

# 随机读 IOPS
fio --name=block-qos-iops --filename=/tmp/qos-fio \
  --size=1G --rw=randread --bs=4k --direct=1 --iodepth=32 \
  --runtime=30 --time_based

rm -f /tmp/qos-fio

初始 Token Bucket 额度耗尽后，持续吞吐量和 IOPS 应接近配置上限。virtio-fs 或内存中的文件不会经过 virtio-blk limiter，不能用于这项验证。

7模板核心概念

模板是 CubeSandbox 创建沙箱时使用的可复用运行环境。它不仅包含来自 OCI 镜像的根文件系统，还包含沙箱启动所需的配置和预热后的 MicroVM 快照。基于同一个模板可以反复创建相互隔离、环境一致的沙箱，并通过恢复快照缩短启动时间。

OCI 镜像

OCI（Open Container Initiative）定义了容器镜像的开放标准。日常使用的 Docker 镜像通常就是 OCI 镜像：它由一组只读文件系统层和镜像配置组成，记录了操作系统文件、应用及依赖，以及 ENTRYPOINT、CMD、环境变量等启动信息。镜像一般以 仓库/名称:标签 引用，例如 docker.io/library/python:3.11，也可以用 digest 锁定具体内容。

CubeSandbox 不会把 OCI 镜像直接当作沙箱运行。它会拉取并展开镜像，将其转换为适合 MicroVM 使用的 rootfs，按镜像中的启动配置运行服务，然后生成可快速恢复的模板快照。因此，OCI 镜像是模板的输入，模板才是创建沙箱时使用的产物。

什么时候制作模板快照

CubeSandbox 拉取 OCI 镜像后，会用它启动一个临时 MicroVM。镜像中的入口程序、系统服务和应用会像正常启动沙箱一样运行。Cube 不会在进程刚启动时立刻制作模板，而是等待指定的 HTTP 探针返回 2xx；这个响应表示环境已经到达适合保存的时刻。随后 Cube 冻结此时的文件系统和内存状态并生成模板快照。

OCI 镜像
→
临时 MicroVM按启动配置运行
→
HTTP 探针 2xx定义启动完成
→
冻结文件系统 / 内存
→
模板快照可快速恢复

选择探针，本质上是在定义「什么时候算启动完成」。探针返回得太早，快照可能生成在应用仍在初始化或依赖尚未预热时；探针始终不成功，模板构建则会超时。理想的探针端点应在模板中需要预热的服务都准备完成后才返回 2xx。

用端口和探针定义就绪时机

Cube 平台在制作模板时，会启动容器并通过 HTTP 探测容器是否已就绪。因此：

  1. 你的容器镜像必须在某个固定端口上启动一个 HTTP 服务器，并提供返回 2xx 的就绪端点；它可以来自 envd，也可以来自你的应用。
  2. 创建模板时必须指定以下参数：--expose-port <port>（声明 HTTP 服务监听的端口）、--probe <port>（告诉 Cube 要探测哪个端口）、--probe-path <path>（Cube 将 GET 的 HTTP 路径，如 / 或 /health）。
  3. 被选择的探针端点应在需要预热的服务完全准备好之后才返回 HTTP 2xx。Cube 会以此为信号制作快照；如果探测的是 envd，该信号只表示 envd 本身已经就绪。

一次模板构建选择一个探针端口和路径，Cube 会持续请求 http://<sandbox>:<probe-port><probe-path>，直到收到 HTTP 2xx 响应后制作快照。

envd 是预装在 CubeSandbox 基础镜像中的一个后台服务：沙箱创建后，SDK 的「执行命令」「读写文件」和「打开终端」等操作，实际都会请求沙箱内的 envd。envd 默认监听 49983，其 /health 接口会在 envd 可以接收这些请求时返回 204。最常见的配置是开放 envd 的 49983 端口，监听探测 49983 端口，并在 /health 返回成功后制作模板快照：

--expose-port 49983 --probe 49983 --probe-path /health
envd 就绪只代表 SDK 数据面已经就绪，不一定代表业务应用也已完成启动。如果模板需要预热 Web 应用、Jupyter 等其他服务，应把探针指向能够反映该应用就绪状态的端口和路径。envd 也不是制作模板的必需组件：只提供自有 Web 服务且不使用命令、文件或终端等 SDK 能力的镜像，可以不安装 envd，直接探测应用自己的健康检查端点；需要这些 SDK 能力时，则应使用包含 envd 的基础镜像，或在构建模板时注入 envd。

沙箱就绪语义

被探测的端口同时也是沙箱的就绪契约：由于模板只有在探针返回 HTTP 2xx 后才会被标记为就绪，因此由该模板创建的运行中沙箱，其被探测端口在创建返回时即可提供服务。客户端无需在 create 创建沙箱后额外等待或重试；通过 resume / 自动恢复重新运行起来的沙箱同样适用。

  • 该保证只覆盖被探测的端口。仅用 --expose-port 暴露而未被探测的端口，其上的服务在沙箱开始接收流量时可能仍在启动中；如果需要同样的就绪保证，请改为探测该端口。
  • 服务自身必须健康。该保证针对的是平台侧的端口可达性——运行中的沙箱里若服务崩溃或停止监听，在其恢复之前仍然不可访问。

如何制作与收敛模板

CubeSandbox 支持两种制作方式：

  • 从 OCI 镜像制作：准备包含系统、工具和应用依赖的 OCI 镜像，再由 CubeSandbox 将其转换为模板。这是创建可复现模板的常用方式。
  • 从运行中的沙箱制作：先在沙箱内安装软件或调整环境，再将其当前文件系统和内存状态提交为新模板。适合交互式调试和快速固化环境。

无论采用哪种方式，模板制作过程都可以概括为：准备根文件系统，启动 MicroVM 并等待环境就绪，生成快照，最后注册并发布模板。模板就绪后，CubeSandbox 可以用它快速创建新的沙箱。如果是历史模板或旧部署中仍保存在 CubeMaster 本地盘上的 artifact，也可以后续再用 cubemastercli tpl merge <template-id> 把该 rootfs 迁入 TC 管理的 artifact 存储。

对存量镜像对应的历史模板，文档口径应统一为：tpl merge 解决历史 artifact 的存储收敛问题，tpl redo 解决节点侧重新分发 / 必要时重建问题。典型场景是后续开启 s3Backed=true，需要将历史 artifact 从本地盘迁移到 S3 托管存储；若同一次运维还需要重新覆盖节点，则在 merge 完成后再执行 redo。

8易错点、记忆卡片与自测

易错点

1. unknown ≠ 已经没了。terminated 只描述 kill() 与 on_timeout="kill" 的结果；容器自行退出时 state 报 unknown。用 POST /sandboxes/<id>/connect 是否返回 409（... is not connectable in state 'stopped'）来区分「容器已退出」与「仍在启动 / 状态读取失败」。
2. pause() 不会取消空闲回收。默认 on_timeout="kill" 时，暂停后的沙箱空闲仍超过 timeout 一样会被销毁。要保住它，请用 NEVER_TIMEOUT、省略 timeout（且服务端未设正数默认），或把超时设得足够大。
3. 自动恢复重置的是「计时」，不是「时长」。恢复后 idle 计时从零开始，但 timeout 不变；长请求中间的执行时间不算活跃，可能执行到一半被暂停。
4. 删除 paused 沙箱不是一次 Resume。不会触发 sandbox.resumed、不重置空闲超时、不需要节点容量准入；持锁时返回 503 + Retry-After: 2，等待后重试，不要假设后台会继续删除。
5. Webhook 的 e2b-delivery-id 不是幂等键。它是每次投递尝试的新 UUID；去重请用 payload id（必要时加订阅作用域）。Webhook 也没有签名 / 认证 Header，且默认关闭、运行中不热更新，改配置必须重启所有 Master。
6. configuredQos 只是配置记录。它不能证明 limiter 已在 hypervisor 生效；限速要用 iperf3 / fio 持续测试验证。QoS 只能在创建模板时配置，创建沙箱时不能覆盖。
7. 探针只保证被探测的端口。envd 就绪只代表 SDK 数据面就绪，不代表业务应用就绪；需要业务就绪时，把 --probe 指向业务健康端点。
8. 达到 maxRestarts 后，暂停再恢复也不会复活。暂停保留 restartCount 与退出诊断，退避从该计数继续；只有运行满 10 分钟的稳定期重置才会清零。

自测

3 道自测题

1. 一个沙箱处于 unknown，如何判断它是「还在启动」还是「容器已经退出」？

调用 POST /sandboxes/<id>/connect：容器已经退出时返回 HTTP 409（... is not connectable in state 'stopped'），不可恢复；仍在创建或无法从节点读取状态时仍能正常 connect。不要仅凭 state=unknown 就判定沙箱已死。

2. 使用 timeout=300 且 lifecycle.on_timeout="pause"，执行 commands.run("sleep 900") 会发生什么？为什么？

可能在执行途中被暂停。请求只在开始和响应结束时各算一次活跃，中间 900 秒的执行时间不计入活跃；当空闲达到 300 秒就会触发 pause。应在长请求期间以小于 timeout 的间隔发送轻量请求，或先用 set_timeout(...) 调大超时。

3. 模板返回了 configuredQos，能否直接断定 100 Mbps 限速已经生效？怎样验证？

不能。configuredQos 只是记录的请求配置，不能证明 limiter 已在 hypervisor 生效，也不能证明每项限制都已配置。应创建待测沙箱，用 iperf3 分别做持续上传和下载测试，确认实测值接近配置上限；块设备 I/O 用 fio 顺序写与随机读测试。只配置 PPS 时，还需要固定大小数据包负载与端点报文计数器。
