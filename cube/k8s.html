1全景：分层与四个 DaemonSet

K8s 部署是 K8s 原生路径：组件跑在集群里，由 Helm 管理。控制面是无状态 Deployment（CubeAPI / CubeMaster / CubeOps / WebUI / CubeProxy / lifecycle-manager / cubemastercli），依赖 MySQL / Redis / MinIO 继续用原生 StatefulSet；计算面是四个原生 apps/v1 DaemonSet，负责把沙箱运行时落到每一台计算节点上。安装只需要标准 Kubernetes 与 Helm，不依赖任何自定义 Operator。

Preview 版本警告（官方源文档原文要点）

① 计算节点资源紧张时，Pod 可能被 K8s 控制面错误驱逐，导致沙箱中断；② 计算节点升级会重建 cube-node，Pod 网络下会中断该节点存量沙箱网络（默认宿主机网络下 netns 不随重建销毁）；③ 默认 hostNetwork 可能与 CNI / Pod Security Admission 冲突。请在部署前先读升级文档，并先在非生产集群验证。

1.2 计算面四个 DaemonSet

四个 DaemonSet 拆开的理由很实际：产物安装（Installer）与可 reboot 的 PVM 引导（PVM）分离；非 PVM 计算节点不会去拉 PVM 大镜像；只升 Installer / Bootstrap / PVM 时可以不碰 Big Pod 的 Pod template。

DaemonSet调度 placement核心内容会 recreate Big Pod 吗
cube-node（Big Pod）placement.computewait-node-prep init + 内嵌 network runtime 的 cubelet + cube-egress / cube-egress-net + 可选 cube-s3lvol是（镜像 / 资源 / Pod template 变更即重建）
cube-node-installerplacement.computecube-shim-install / cube-kernel-install / cube-guest-install，把 shim / kernel / guest 整目录换到宿主机 toolbox否（可独立 RollingUpdate）
cube-node-bootstrapplacement.computewait-pvm-host → cube-node-init；写 node-prep-ready；hostPID: true否
cube-node-pvmplacement.pvmpvm-host-bootstrap；PVM host kernel 安装（可能 reboot）；管理 L0 污点并写指纹；保持 Pod 网络否（但节点可能 reboot）
cube-juicefs（可选）相同计算节点 placementOnDelete 挂载 DaemonSet；格式化 Job 初始化共享卷，经 /data/cubelet 传播否（日常 Helm 升级不自动卸载）
NodeID 与 Endpoint 的解析规则

Big Pod 的 NodeID 取 spec.nodeName（CUBE_SANDBOX_NODE_ID），Endpoint 取 status.podIP（CUBE_SANDBOX_ENDPOINT_IP，宿主机网络下即节点 IP）。同一节点上 NodeID 不变，所以 Pod IP 变化后，控制面（CubeOps / CubeMaster）与数据面（CubeProxy）都会按 NodeID 动态解析最新 Endpoint。

2节点角色、标签与污点

CubeSandbox 用标签区分两类节点，再用污点阻止无关负载落进来。Chart 用显式 label 授权而不是「通配」部署，原因是 PVM 引导会换 host kernel 并可能 reboot，计算面又大量使用 privileged / hostPath，误调度的代价很高。

角色必打标签污点建议规格说明
控制面节点cube.tencent.com/cube-control=true可选：cube.tencent.com/control=true:NoSchedule≥ 1 台；生产建议 3+；≥ 4C8G跑 Cube 控制面组件
计算节点cube.tencent.com/cube-node=true必打：cube.tencent.com/compute=true:NoSchedule≥ 1 台；建议 16C32G+跑沙箱；建议使用独立机器
PVM 计算节点额外 cube.tencent.com/allow-pvm-bootstrap=true沿用计算节点的 compute 污点—非裸金属服务器时打此 label，即可自动安装 PVM

2.1 多节点：控制面 / 计算面分离（推荐）

# 控制面节点
kubectl label nodes <control-node> cube.tencent.com/cube-control=true --overwrite

# 计算节点（跑沙箱）
kubectl label nodes <compute-node> cube.tencent.com/cube-node=true --overwrite

# 若计算节点不是裸金属服务器，则还需要打这个 label，即可自动安装 PVM
kubectl label nodes <pvm-compute-node> cube.tencent.com/allow-pvm-bootstrap=true --overwrite
# 角色污点（避免无关负载落到这些节点上）
# 可选
# kubectl taint nodes <control-node> cube.tencent.com/control=true:NoSchedule --overwrite

# 计算节点必打
kubectl taint nodes <compute-node> cube.tencent.com/compute=true:NoSchedule --overwrite
placement 与标签必须对得上

Chart 默认值：placement.controlPlane.nodeSelector 为 cube-control=true，placement.compute.nodeSelector 为 cube-node=true，placement.pvm.nodeSelector 包含 allow-pvm-bootstrap=true。PVM 的 label 不得写进 placement.compute，否则所有计算节点都会去拉 PVM 大镜像，Chart 在渲染阶段会直接报错。

2.2 单节点：一台机器兼做控制面与计算面（不推荐）

只有一台机器时，官方更推荐走「快速开始」的一键脚本，而不是 K8s。若坚持单节点，可按下面方式同时打两枚独立角色 label 与两把污点：

export NODE=<你的节点名>

kubectl label nodes "$NODE" \
  cube.tencent.com/cube-control=true \
  cube.tencent.com/cube-node=true \
  cube.tencent.com/allow-pvm-bootstrap=true \
  --overwrite

kubectl taint nodes "$NODE" cube.tencent.com/control=true:NoSchedule --overwrite
kubectl taint nodes "$NODE" cube.tencent.com/compute=true:NoSchedule --overwrite
混部的关键是「独立 key」

控制面与计算面要打两枚不同 key 的 label（cube-control 与 cube-node），不要用同一个 key 覆盖写；再叠加 values-single-node.yaml，让两侧都容忍两把角色污点。扩容纯计算节点时只打 cube-node + compute 污点，不要再打 cube-control。

PVM 是什么

PVM（Pagetable-based Virtual Machine）是一种基于页表的嵌套虚拟化框架，构建于 KVM 之上；它不依赖宿主 hypervisor 向 guest 暴露 VT-x / AMD-V，而是在 guest 内核层通过共享内存区域和影子页表完成特权级切换与内存虚拟化，对宿主 hypervisor 完全透明。相关工作已开源至 OpenCloudOS 内核，并在腾讯云生产环境大量部署。

4.1 计算节点数据盘

Cube 会在宿主机 /data/cubelet 下写入数据，且该路径必须是 XFS 文件系统。生产建议每台计算节点单独挂一块格式化好的 XFS 数据盘到 /data/cubelet，然后在 values 里关掉 loopback：

bootstrap:
  nodeInit:
    dataCubelet:
      loopback:
        enabled: false

没有独立数据盘时，默认会在首次初始化时创建一块 25G loop 设备。要调整容量：

bootstrap:
  nodeInit:
    dataCubelet:
      loopback:
        enabled: true
        size: 200G   # 按容量规划调整；需小于存放 image 的文件系统剩余空间
只影响「第一次」创建

默认仅在 /data/cubelet-xfs.img 不存在时自动创建镜像文件，后续修改 size 不会自动扩容。要换更大盘需在维护窗口内手工处理。

4.2 链路追踪

链路追踪默认关闭，Chart 也不安装接收端。如需导出沙箱生命周期 span，在安装前给各组件的 env 数组加 OTEL_EXPORTER_OTLP_ENDPOINT，指向外部 OTLP/gRPC 接收端（如 OpenTelemetry Collector 或 Tempo），格式为 http://<receiver-host>:<OTLP-gRPC-port>：

controlPlane:
  api:
    env:
      - name: OTEL_EXPORTER_OTLP_ENDPOINT
        value: http://10.0.0.5:4317
  master:
    env:
      - name: OTEL_EXPORTER_OTLP_ENDPOINT
        value: http://10.0.0.5:4317
  templateCenter:
    env:
      - name: OTEL_EXPORTER_OTLP_ENDPOINT

env 数组是「整体替换」

组件的 env 数组会整体替换 chart 默认值，务必保留 chart 已为该组件设置的条目，不要直接覆盖整个列表。要关闭时，把端点设为显式空字符串 value: "" 再重新应用即可。各服务以各自名字上报（cube-api、cubemaster、cubetemplatecenter、cubelet、cube-shim），不要设置全局共享的 OTEL_SERVICE_NAME；CubeOps 与 lifecycle manager 目前不上报 span。

5升级：网络模式与 Big Pod

一句话结论

控制面可以有序滚动升级；计算面升级会 recreate cube-node Big Pod——默认的宿主机网络下这对沙箱网络是安全的，Pod 网络下则会中断沙箱。部署当前版本后若计划升级，应先评估改动、做测试再实施。

5.1 为什么网络模式决定重建代价

CubeSandbox 的网络（cubevs）钩子挂在 Pod 的网卡上，沙箱的 TAP 设备也与 Pod 处于同一 netns。Pod 重建时：

项目说明
触发条件任何导致 Pod 重建的操作：DaemonSet template 变更、镜像升级、手工 kubectl delete pod 等
hostNetwork: true（默认）netns 即宿主机 netns，不随 Pod 重建变化，TAP 设备得以保留。cubelet 重启后沙箱存活尚未实机验证——在此之前仍应 drain
hostNetwork: false（Pod 网络）Pod netns 被销毁：该节点上所有沙箱网络全部中断（入站、出站均中断）且不能自愈，只能销毁并重建受影响的沙箱
BIG

什么是 Big Pod

即 cube-node DaemonSet 的 Pod：hostNetwork: true，wait-node-prep 作为 initContainer（指纹匹配后 exit 0，不作为常驻 sidecar），主容器是内嵌 network runtime 的 cubelet，并带 egress 与可选 s3lvol sidecar。它的 Pod template 一旦变化就会重建。

UID

重建的可见信号

Pod UID 会变；宿主机网络下 PodIP 即节点 IP，不会变。所以「Pod 重建但负载 IP 没变」是正常现象，不能用 IP 变没变来判断是否重建。

5.2 升什么，动哪条工作负载？

计算面拆成四条线。日常升级只改对应组件的镜像 tag，避免顺手改 Big Pod 的 env / volumeMount / 容器列表——这些同样会 recreate。

会 recreate

升运行时组件

改 images.cubelet / images.waitNodePrep 等 → 动 Big Pod（cube-node）。镜像 / 资源 / Pod template 变更都会删除重建。

不碰 Big Pod

升 toolbox 产物

改 images.cubeShim / images.cubeKernel / images.cubeGuest → 动 Installer（cube-node-installer），可独立 RollingUpdate。

不碰 Big Pod

升节点预检

改 images.nodeInit → 动 Bootstrap（cube-node-bootstrap），hostPID: true，低频变更。

可能 reboot

升 PVM 换核

改 images.pvmHostBootstrap → 动 cube-node-pvm，不 recreate Big Pod，但节点可能重启以换 host kernel。

图 5：升级决策图。「改什么 → 动哪条工作负载 → 是否 recreate Big Pod」。

5.3 日常升级（推荐路径）

在本地 runtime-values.yaml（与首次安装相同的 values 文件）里只更新要升的镜像 tag：

images:
  cubelet:
    tag: v0.8.0

  # cubeShim:
  #   tag: v0.8.0

  -f runtime-values.yaml
# TKE / 单节点等场景继续叠加首次安装时用过的 values-tke.yaml / values-single-node.yaml
生产请逐个节点、逐个组件灰度升级

确认升级成功：

kubectl get pods -n cube-system -l app.kubernetes.io/component=cube-node -o wide

# 控制面 Deployment 可按常规滚动验收

5.4 升级顺序

1. 先起 CubeOps

新 cubelet 把 meta_server_endpoint 指向 cube-ops，地址不可达会 fail-fast，所以必须先把 CubeOps 起好。

2. 再起 CubeMaster

CubeMaster 启动时如果配置了 cube_ops_addr 且 CubeOps 不通，会 fail-fast。

3. 切流期不要新老 cubelet 混跑

旧 cubelet 向 cube-master :8089 上报，新 cubelet 向 cube-ops :3010 上报；混跑会导致节点状态不一致。逐节点滚动，或先停整个计算面再升。

4. 最后滚动控制面与计算节点

以上就绪后，再按需滚动 cube-master、cube-api 与计算节点。

5.5 红线：这些操作也会 recreate Big Pod

不要随便做为什么
改 cubeNode.hostNetwork会让沙箱数据面跨 netns 迁移；由 pre-install / pre-upgrade / pre-rollback Hook 拦截
增删 Big Pod 容器（含改槽位数量）改 Pod template，DaemonSet 会重建 Pod
改 volumeMount / securityContext / 容器名 / 直接改 env同上，template 变更即重建
改 wait-node-prep 的 env / mount（只 bump 镜像也会 recreate）wait 为 initContainer；template 变更即重建
手动删 Big Pod等于重建数据面
把产物安装塞进 Big Pod破坏分工；产物应走 Installer

另外，cubeNode.env、cubeNode.podAnnotations、网络相关 env、global.timezone 也会改 Pod template——不是日常无感升级项。

5.6 特殊场景

A. 改 PVM kernel pattern / boot args（会 reboot）

日常只换 images.pvmHostBootstrap 镜像、且指纹仍匹配时，一般不会再打 pvm-not-ready 门闩。若你要主动改 bootArgs / kernel pattern（期望指纹变化），建议在 helm upgrade 之前打运维门闩（value=maintenance，与 Hook 自动打的 true 不同——旧 hold 默认不会清 maintenance）：

# 1. 确认 CNI、kube-proxy 能容忍该 NoSchedule 污点
kubectl taint node <pvm-node> \
  cube.tencent.com/pvm-not-ready=maintenance:NoSchedule --overwrite

# 2. 在 runtime-values.yaml 里改好 bootArgs / kernel 相关配置后升级
helm upgrade cube ./deploy/kubernetes/chart -n cube-system \
  -f runtime-values.yaml
bootstrap:
  pvmHostKernel:
    bootArgs: "nopti pti=off <new-arg>"

节点恢复后，只有新的 PVM init 在 live 指纹匹配时才会清掉 maintenance。任一步失败都不应 reboot。要关某节点的 PVM，去掉该节点的 allow-pvm-bootstrap label 即可；不要指望只改 cubeNode.pvmGuestKernel.enabled=false 把已在跑 PVM 的节点悄悄切回 bm。

B. 卸干净重装（最后手段）

helm uninstall cube -n cube-system
sudo ./deploy/kubernetes/chart/scripts/cleanup-node-host.sh
helm upgrade --install cube ./deploy/kubernetes/chart \
  -n cube-system -f runtime-values.yaml

这会清掉 Chart 管理的对象；宿主机 hostPath / 内核改动需脚本与平台 runbook 另行处理。

6高可用与生命周期

Chart 默认 lifecycleManager.replicas=2 且 leaderElection.enabled=true，以主备方式运行：每个副本都消费生命周期事件、处理恢复回调，由 Redis 租约选出的 leader 执行空闲扫描 / 销毁和过期注册清理；共享的沙箱状态只有 leader 会写。replicas 大于 1 却关闭选主会在 Helm 校验阶段失败。

running → paused → running（auto-resume） → dead

图 6：pause / resume 语义。leader 故障切换后，记录不一致的沙箱按安全的一侧记为 paused，下次请求照常 auto-resume。

6.1 故障切换后的用户可见影响

现象是否预期机制
沙箱多一次 pause / resume预期，且只发生一次，不是循环新 leader 接管时重新核对每个沙箱状态，记录不一致时按安全的一侧记为 paused
是否向 VM 发 pause？不会这只是记录层面的修正，下次请求会照常 auto-resume
为什么不记成 running？安全优先把实际已停止的沙箱记成 running，会让流量打到已停机的 VM
代价最多一次额外的 auto-resume用户可见影响见 FAQ；Terraform 一键部署默认同样是双副本主备

PVM 内核还需卸包、改 GRUB、reboot。也可使用 Chart 附带的 deploy/kubernetes/chart/scripts/cleanup-node-host.sh。PVC / PV 是否删除取决于实际 StorageClass 的 reclaimPolicy（TKE 的 cube-cbs-wffc 常见为 Delete；Retain 则会留下）。

helm rollback 不会回滚 host kernel

Helm 只管 K8s 对象。kernel / GRUB / fstab / XFS 等需单独的宿主机回滚 runbook。

9易错点与自测

9.1 易错点

把 allow-pvm-bootstrap 写进 placement.compute

PVM 的 label 只能出现在 placement.pvm，写进 placement.compute 会让所有计算节点去拉 PVM 大镜像，Chart 渲染阶段直接失败。反过来，placement.pvm 必须包含 allow-pvm-bootstrap=true。

以为改 cubeProxy.advertiseIP 会改变入口

它只是 values.yaml 注释写明的 optional hint，不会写入 Proxy / DNS / Service 模板。改它再重启 Proxy 也不会改变集群行为，真正要改的是外部 DNS / LB 或 Service / Ingress。

在已有 release 上改 cubeNode.hostNetwork

这属于 Pod template 字段，会重建所有 Big Pod，且沙箱数据面会跨 netns 迁移。preflight Hook 会拦截：要么保持现状写回线上值，要么先逐节点 isolate、等待 ≥ 60s、销毁沙箱，再设 cubeNode.hostNetworkChangeAck: true。不要在 helm rollback 里切回模式——回滚重放的是目标 revision 的 stored values。

以为改 loopback size 能扩容

默认仅在 /data/cubelet-xfs.img 不存在时创建镜像文件，后续改 size 不会自动扩容。生产建议关掉 loopback，改用预挂载的大容量 XFS 盘。

其它小坑

helm test 的 --timeout 需要 Helm 3.13+ 才生效；cubeNode.env 是整体替换而不是合并；kubectl exec 不带 -c 时默认目标是 cubelet（本次变更从 network-agent 改过来）；升级 PostgreSQL 加列场景下，旧实例要先摘流停止再启动会自动迁移的新版本。保持默认 hostNetwork 时，cubelet（9998 / 9999 / 9966）与启用时的 CubeS3lvol 占用宿主机端口，已被占用时 cube-node-init 会 fail-fast；cubelet 端口无认证，防火墙应把 9999 按 kubelet 10250 同级对待。

9.2 记忆卡片

四个 DaemonSetBig Pod（cube-node）、Installer、Bootstrap、PVM；加 JuiceFS 挂载 DS 是第五个 OnDelete。
三个标签control 打 cube-control，compute 打 cube-node，非裸金属再打 allow-pvm-bootstrap；计算节点必打 compute 污点。
网络模式定代价hostNetwork=true 时 netns 是宿主机的，重建保留设备；Pod 网络下重建即全断且不自愈。
升级只改 tag升运行时改 images.cubelet，升产物改 Installer 的 image，升预检改 images.nodeInit，升换核改 images.pvmHostBootstrap。
卸载不管宿主机label / taint、hostPath 数据、PVM 内核改动都要另行清理。
CLM 双副本Redis 租约选主；故障切换最多一次额外 pause/resume，不会循环。

9.3 自测

自测

1. 为什么 allow-pvm-bootstrap 只能写在 placement.pvm，不能写进 placement.compute？

因为 placement.compute 会被 cube-node / installer / bootstrap 三条 DaemonSet 使用。若把 allow-pvm-bootstrap=true 写进 compute，所有计算节点都会匹配 cube-node-pvm，从而拉取 PVM 大镜像并触发宿主机换核流程；Chart 在 templates/validate.yaml 中明确禁止这种写法。PVM 的引导只应发生在显式打了该 label 的 placement.pvm 节点上。

2. 在 Pod 网络模式（cubeNode.hostNetwork: false）下重建 cube-node Pod，会发生什么？如何恢复？

Pod 重建会销毁该 Pod 的 netns，而沙箱的 TAP 设备与 cubevs 钩子都在这个 netns 里，因此该节点上所有沙箱的网络会全部中断（入站、出站均中断），且不能自愈。恢复只能销毁并重建受影响的沙箱。预防是保持默认的宿主机网络；若因 NetworkPolicy 必须用 Pod 网络，则升级前必须 drain，并接受重建即中断的代价。

3. 只升级 shim / kernel / guest 产物，应该改哪个镜像键？会 recreate Big Pod 吗？

改 images.cubeShim / images.cubeKernel / images.cubeGuest，它们对应 Installer（cube-node-installer）里的 cube-shim-install / cube-kernel-install / cube-guest-install 容器。Installer 可独立 RollingUpdate，不会 recreate Big Pod，因为 Big Pod 的 Pod template 不变。这也是把计算面拆成四条线的核心收益。
