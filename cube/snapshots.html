1概念模型：四个原语

先记住一句话：Snapshot 是「存档」，Clone / Fork 是「存档后开新档玩」，Rollback 是「读档重来」。四者都建立在「把沙箱某一时刻的完整状态固定下来」这一能力之上，区别在于固定之后怎么用、落在哪个沙箱上。

1.1 四个原语分别是什么

  • Snapshot（快照）：把运行中的沙箱完整状态（内存 + 文件系统）持久化成一份镜像，返回 SnapshotInfo，其 snapshot_id 可反复用于创建新沙箱或回滚。默认 full 模式，另有只保留文件系统的 fs-only 模式。
  • Clone（克隆）：对运行中的沙箱调用 sb.clone(n=N)，立即派生 N 个完全独立、从源沙箱当前状态出发的副本，互不干扰，源沙箱继续运行。
  • Fork（分叉）：sb.fork(count=N) 通过一次服务端调用派生 N 个运行中的副本——服务端对源沙箱只打一次快照，所有副本从该快照派生，临时快照由服务端管理。
  • Rollback（回滚）：sb.rollback(snapshot_id) 把正在运行的沙箱原地恢复到某次快照的状态，沙箱 ID 不变，sb 对象可以继续使用。
与 e2b 的差异：快照、克隆、回滚是 Cube Sandbox 特有能力，e2b SDK 没有对应接口。cubesandbox SDK 兼容 e2b SDK，可直接替换，同时获得这些进阶能力。本文接口需要 cubesandbox>=0.2.0。

1.2 检查点如何分叉成两条分支

在同一个检查点上，既可以「继续往下写」，也可以「回滚后再写别的」。从时间轴看，这就是两条互不影响的分支。

时间轴
沙箱运行 v1写完 /tmp/v.txt
↓ create_snapshot() 打检查点
检查点 checkpointfull 快照 · snap-xxx
↙ 分支 A　　↓ rollback 回检查点　分支 B ↘
分支 A继续写 v2
回到快照文件系统还原为 v1
分支 B改写 v3
↓ 两条分支各自再打快照
分支 A / 分支 B 都成为独立时间线，互不可见

对应到原语：Snapshot 产出检查点；Clone / Fork 从检查点横向开出多个新沙箱；Rollback 让同一个沙箱回到检查点后继续走另一条分支。

1.3 四原语对比

原语 接口 是否保留内存 是否独立 并发 有效期 典型场景
快照 full sb.create_snapshot() 保存 产物与源沙箱解耦，源 kill() 后仍可用 每份独立 可传 ttl_seconds；0 或不传＝长期 checkpoint、持久化状态
快照 fs-only create_snapshot(mode="fs-only") 不保存 独立；用它创建的是冷启动 捕获期间源沙箱持续运行 同上 只要文件、可接受冷启动
克隆 Clone sb.clone(n=N) 保存（内部打 full 快照） 副本互相隔离，源沙箱继续运行 concurrency，默认 1；任一失败即全回收 内部临时快照，最后一个克隆被杀后清理 Agent 并行 rollout、可重复实验
分叉 Fork sb.fork(count=N) 保存 副本各自独立，部分成功可保留 由服务端决定 服务端管理临时快照 大批量 fan-out
回滚 Rollback sb.rollback(snap_id) 恢复快照中的内存 同一沙箱，ID 不变 单沙箱原地 依赖所回滚的 full 快照 撤回失败一步、回到分支点继续
一句话区分 Snapshot 不产生新沙箱；Clone / Fork 产生新沙箱；Rollback 保持同一个沙箱。Clone 由客户端编排、全成或全败；Fork 一次服务端调用、各自独立成败。

2快照 Snapshot

sb.create_snapshot() 将沙箱当前状态（文件系统 + 内存）持久化为一份快照，返回 SnapshotInfo，其中 snapshot_id 可直接作为 Sandbox.create(template=...) 的入参。

Python · 创建快照
from cubesandbox import Sandbox

with Sandbox.create(template=TEMPLATE_ID) as sb:
    sb.run_code("open('/tmp/data.txt','w').write('hello')")
    snap = sb.create_snapshot()
    print(f"snapshot: {snap.snapshot_id}")
命名限制：可选的 name 不能以 tpl- 或 snap- 开头，否则返回 HTTP 400——这两个前缀表示 ID。环境变量约定：CUBE_API_URL=http://127.0.0.1:3000、CUBE_TEMPLATE_ID=tpl-xxxxxxxxxxxxxxxxxxxxxxxx。

2.1 生命周期与删除

  • 快照生命周期独立于沙箱：源沙箱被 kill() 之后，快照仍然可用。
  • 不再需要时调用 Sandbox.delete_snapshot(snapshot_id_or_name) 手动清理：成功返回 True，快照不存在返回 False。
  • 按名称删除时 只匹配快照、不匹配模板：名称没有对应快照时返回 False，即使存在同名模板别名也不会删除；名称匹配多个快照时返回 HTTP 409 且不删除任何对象，请改用 snap- ID。
  • 该行为要求 CubeAPI 支持 snapshot_only；旧版服务端会忽略该参数，名称没有对应快照时仍会路由到同名模板。

2.2 有效期（TTL）

临时检查点、实验快照、短期恢复备份建议设置有效期，让系统在不再需要时自动清理。需要长期保留的不传有效期，或传 0，之后再手动删除。

Python · 带有效期
snap = sb.create_snapshot(name="checkpoint", ttl_seconds=3600)
print(snap.expires_at)

# 快照有效期内，每次恢复都会创建一个新的沙箱。
restored = Sandbox.create(template=snap.snapshot_id)
  • 有效期从快照就绪时开始计算；expires_at 是 UTC 过期时间，未设置时为 None。
  • SDK、CubeAPI、CubeMaster 都需为支持快照有效期的版本。Node SDK：sb.createSnapshot("checkpoint", { ttlSeconds: 3600 })；Go SDK：sb.CreateSnapshot(ctx, "checkpoint", cubesandbox.CreateSnapshotOptions{TTLSeconds: 3600})。
  • 过期后不能再用该快照创建沙箱或回滚；已经从它启动的沙箱仍能正常运行。
  • 系统定期清理，需等待运行中的沙箱和其他依赖释放引用后才回收存储，所以过期不代表立即释放磁盘空间。
节点永久丢失时：遗留的待完成恢复会阻止清理。管理员可先隔离节点（确保旧 VM 与排队请求不能恢复运行），删除快照，并等待待完成预约至少满 24 小时，再执行 cubemastercli snapshot recover-create。节点信息必须与该次待完成恢复记录一致。
Shell · 释放遗留预约
cubemastercli snapshot recover-create \
  --snapshot-id snap-example --sandbox-id reserved-example \
  --node-id retired-node --node-ip 192.0.2.10 \
  --confirm-node-fenced --reason "Host powered off and prevented from restarting"

该命令只释放匹配的过期预约；节点仍健康、实例仍存在或快照操作尚在进行时会拒绝执行。后续对账会继续物理清理，正常过期不需要手动运行此命令。

2.3 full 与 fs-only 的区别

给 create_snapshot() 传 mode="fs-only"，只捕获文件系统、不捕获 guest 内存。调用期间 guest 不会暂停，返回时即可继续读写；代价是用它创建的沙箱会冷启动——文件都在，但所有进程都是新的。

Python · fs-only
snap = sb.create_snapshot(mode="fs-only")
assert snap.mode == "fs-only"

child = Sandbox.create(template=snap.snapshot_id)
# 快照前的文件可见……
out = child.run_code("print(open('/tmp/data.txt').read())").logs.stdout[0]
assert out.strip() == "hello"
# ……但进程不在。
维度 mode="full"（默认） mode="fs-only"
guest 内存保存不保存
调用期间源沙箱短暂暂停持续运行
用它创建的沙箱恢复内存，进程继续冷启动，进程全新
之后的 pause() / resume()保留内存保留内存（首次 pause 是全量捕获）
rollback(snapshot) 回滚到它支持拒绝（snapshot_filesystem_only_rollback_unsupported）
外部挂载（plugin 卷、host mount）快照记录挂载配置，恢复后重新挂载不记录挂载；用这份快照创建时重新声明即可
配置 restart 策略时 restart保留文件保留文件（复用捕获时的可写层）

fs-only 的几个关键行为

  • 不是增量链：每份快照都是独立的时间点镜像，打 N 次就存 N 份。不要假设「只存文件系统所以很小」——实际占用取决于存储后端的 CoW/reflink 能力。
  • 从 fs-only 快照创建的沙箱之后与普通沙箱无异：配置 restart 策略时，restart 复用捕获的可写层、保留文件、重建进程；也可以对它再打 fs-only 快照，新包记录它实际使用的可写层。
  • fs-only 包只记录根文件系统，不携带任何外部挂载：创建时必须重新声明要用的 plugin 卷与 host mount（含容器路径），没声明的不会挂载；没有「必须与快照一致」的限制；沙箱可以落在任意节点，宿主路径在目标节点解析，挂不上就让创建失败，不会留下空目录。

fs-only 错误码

HTTP错误码触发条件处理建议
409snapshot_filesystem_only_unsupported_node控制面或节点 agent 不支持 fs-only升级版本较旧的一侧；不会静默退回 full。shim 能力声明上线后可能在 guest 暂停之前返回，沙箱保持运行
409snapshot_filesystem_only_freeze_unsupported / ..._rootfs_unsupported节点不支持冻结文件系统 / 该 rootfs 类型集群侧能力缺口，重试前先确认节点状态
5xxsnapshot_filesystem_only_freeze_failed / ..._thaw_failed冻结或解冻在捕获过程中失败集群侧问题，重试前先确认节点状态
409snapshot_filesystem_only_shared_volume_unsupported源沙箱挂了可写 plugin volume可写 plugin volume 不属于被捕获的根文件系统；先用不含该卷的沙箱再打快照
409snapshot_filesystem_only_multi_container_unsupported沙箱带有额外的用户容器一份包只记录一个可写层，请使用单容器沙箱

响应里的 mode 永远是实际记录的模式；与请求不一致时调用直接失败（409 snapshot_mode_conflict），不会把这份产物返回给你，因此不会静默拿到一份 full 快照。

2.4 列举与过滤快照

Python · 分页与过滤
# 获取快照列表（第一页）
items, next_token = Sandbox.list_snapshots()

# 按 sandbox_id 过滤
items, _ = Sandbox.list_snapshots(sandbox_id=sb.sandbox_id)

list_snapshots() 返回 (list[SnapshotInfo], next_token)，把 next_token 传回可获取后续页；为 None 表示没有更多页。

3克隆与分叉

对一个正在运行的沙箱调用 sb.clone(n=N)，可以立即派生 N 个独立副本。每个副本完整继承源沙箱在 clone 时刻的运行状态（内存 + 文件系统），但之后写入互不影响，源沙箱继续正常运行。

Python · 克隆
src = Sandbox.create(template=TEMPLATE_ID)
src.run_code("open('/tmp/shared.txt','w').write('hello')")

clones = src.clone(n=3)
for sb in clones:
    # 每个克隆都继承 src 里写入的文件
    out = sb.run_code("print(open('/tmp/shared.txt').read())").logs.stdout[0]
    assert out.strip() == "hello"

3.1 并发克隆

默认串行创建；fan-out 场景可以传 concurrency=C 并发执行。

Python · 并发克隆
clones = src.clone(n=10, concurrency=5)
全成或全败：任一子任务失败时，已成功创建的克隆会被自动 kill()。调用方拿到的要么是 N 个沙箱，要么是异常，不会留下孤儿资源。

3.2 继承性与隔离性

性质含义
继承性每个副本的初始状态与源沙箱在 clone 时刻完全一致
隔离性副本之间的写入互不可见，与源沙箱也互相隔离
连续性源沙箱在 clone() 返回后仍在运行，状态不受影响

3.3 分叉 Fork

sb.fork(count=N) 通过一次服务端调用派生 N 个运行中的副本：后端对源沙箱只打一次快照，所有副本都从该快照派生。源沙箱继续运行，临时快照由服务端管理，客户端无需清理。

Python · 分叉，按槽位独立成败
src = Sandbox.create(template=TEMPLATE_ID)
forks = src.fork(count=3)
for sb in forks:
    if isinstance(sb, Sandbox):
        sb.run_code("print('alive')")   # 运行中的副本
    else:
        print(f"fork failed: {sb}")     # 该槽位的异常

每个 fork 独立成败。返回值恰好有 count 个元素——Sandbox，或阻止该 fork 启动的 Exception。部分成功会保留副本且不抛异常；只有整体失败才抛异常（如源沙箱不存在）。

3.4 clone 与 fork 的区别

维度clone(n=N)fork(count=N)
失败语义全成或全败：任一失败即回收兄弟并抛异常各自独立：部分成功保留成功项
编排方式客户端：打快照 + N 次 create一次服务端调用（单次快照，N 路派生）
临时快照最后一个克隆被杀后由 SDK 删除由服务端管理
并发concurrency 参数（默认 1）由服务端决定

3.5 参数与错误

  • count：1..100，默认 1。越界在所有 SDK 中都会抛错。
  • timeout：新派生沙箱的空闲存活时长，不影响源沙箱。各 SDK 单位不同：Python 为秒，Node 为 timeoutMs 毫秒，Go 为 time.Duration；线上传输单位是秒。
  • 404 源沙箱不存在；409 源沙箱当前状态不可 fork——刚创建的沙箱可能需要片刻才能打快照，稍后重试即可。

4回滚 Rollback

sb.rollback(snapshot_id) 把当前沙箱原地恢复到指定快照的状态：文件系统完全还原，沙箱 ID 不变，sb 对象可以继续使用。回滚只支持 full 快照——对 fs-only 快照回滚会被拒绝（snapshot_filesystem_only_rollback_unsupported）。

Python · 原地回滚
sb = Sandbox.create(template=TEMPLATE_ID)
sb.run_code("open('/tmp/v.txt','w').write('v1')")
checkpoint = sb.create_snapshot()

sb.run_code("open('/tmp/v.txt','w').write('v2')")
sb.rollback(checkpoint.snapshot_id)

after = sb.run_code("print(open('/tmp/v.txt').read())").logs.stdout[0]
assert after.strip() == "v1"

4.1 在回滚后的分支上继续操作

回滚后沙箱仍然可写，可以继续执行并再次创建快照，非常适合 Agent 的回退—重试循环。

Python · 继续走另一条分支
# 在回滚后的分支上继续
sb.run_code("open('/tmp/v.txt','w').write('v3')")
new_snap = sb.create_snapshot()

with Sandbox.create(template=new_snap.snapshot_id) as forked:
    out = forked.run_code("print(open('/tmp/v.txt').read())").logs.stdout[0]
    assert out.strip() == "v3"
running v1 → create_snapshot → running v2 → rollback → v1 → running v3（ID 不变）

4.2 最佳实践

  • 快照不是免费的：每个快照对应底层一份完整镜像，记得用完即删，或定期调用 list_snapshots() 清理。
  • with 语句不会自动删快照：上下文管理器只负责 kill 沙箱，快照需要显式调用 Sandbox.delete_snapshot() 清理。
  • clone() 会自动清理内部快照：临时派生几个副本时直接用 clone()，无需手动管理快照生命周期。
  • 大批量派生优先用 fork(count=N)：一次往返、各自独立成败、服务端统一清理。需要全成或全败语义时再用 clone(n=N, concurrency=C)。

5跨机迁移：条件与架构

沙箱的跨机迁移，指把正在机器 A 上运行的沙箱迁移到机器 B 上继续运行，并尽可能保留原来的运行状态。价值主要有三个：资源调度（宿主资源不足时迁走长时间运行的 Agent，而不必重跑任务）、宿主机维护（升级内核、重启或下线前提前迁走）、负载均衡（Agent 任务 CPU 使用率动态波动，迁移帮助重新分配资源）。

Cube 默认使用的 xfs 后端只在源节点保存 rootfs、memory 和 metadata。跨机迁移需要使用共享后端：将源节点上的沙箱暂停或打快照后，把相关数据上传到共享存储，再在目标节点恢复。目前支持两种共享后端：JuiceFS 与 S3（CubeS3lvol）。

5.1 整体架构：源节点 → 共享存储 → 目标节点

源节点（A）
沙箱 runningrootfs + memory + metadata
↓ pause() 或 create_snapshot()，export 上传
共享存储
JuiceFS元数据引擎 + 对象存储
S3 / MinIOCubeS3lvol 发布包
↓ remote_status=ready 后可被调度
目标节点（B）
恢复沙箱FromSnap / Resume → running

5.2 跨机迁移的三个条件

并不是所有沙箱都支持跨机迁移，需要同时满足：

  1. 沙箱使用共享后端的模板/快照创建；
  2. 源节点和目的节点 CPU、kernel、KVM 兼容；
  3. 源节点不可调度（离线或被隔离）。

条件一：用共享后端创建模板

用 cubemastercli 或 SDK API 默认创建的模板使用 xfs 后端，不支持跨机迁移。要支持跨机，需主动声明 --backend jfs|s3。

Shell · 创建 JuiceFS 模板
# 创建 juicefs 模板
cubemastercli tpl create-from-image \
  --image <img> \
  --writable-layer-size 4Gi \
  --expose-port 49983 \
  --probe 49983 \
  --probe-path /health \
  --backend jfs
不可转换：已创建的模板不支持在已有的 xfs、jfs 和 s3 产物之间转换。选错后端只能重建模板。

条件二：CPU / kernel 兼容

为保证跨机后沙箱能正常恢复，源节点与目的节点 CPU、kernel 需兼容。查看整个集群的兼容类别：

Shell · 按门禁给节点分组

type-2   AMD            AMD EPYC 7B13 ...     2      node-4,node-5

也可以用 cubeopscli node list --json 查看每个节点的 HostFacts 信息。门禁字段如下：

cpuid_hashCPU 身份与特性哈希相等匹配
host_kernel_releaseuname -r相等匹配
kvm_module_taint强制、树外或未签名 KVM 模块标记目标侧非空则拒绝

条件三：源节点不可调度

由于跨机需要把共享数据上传到目标节点，第一次在非本机节点恢复的性能较差，因此在源节点可用时调度器始终优先调度源节点。优先级为：

① 源节点健康且可调度：在源节点恢复（最快，无需跨机）
↓ 源节点不可用
② 源节点离线或被隔离：检查共享数据和主机兼容性
↓ 条件满足
③ 选择兼容节点恢复；否则返回错误
外部存储也会限制调度：
  • host-mount：若沙箱挂载了宿主机目录，则无法跨机迁移，因为无法保证挂载的目录在目标节点也能访问。从 fs-only 快照创建的沙箱不记录挂载，需在创建时重新声明，按普通新建沙箱调度。
  • Plugin Volume：沙箱可以跨机，但需保证目标节点也安装了对应 driver 并能访问后端。Cube 不会自动检查目标节点的 Volume 状态与可用性，需运维侧自行保证。

6JuiceFS 共享存储部署

JuiceFS 是开源、POSIX 兼容的分布式文件系统，采用数据与元数据分离的设计：数据存储在对象存储，元数据存储在元数据存储，支持 Redis、MySQL、TiKV 等元数据存储和 MinIO、S3、COS 等对象存储。CubeSandbox 借助 JuiceFS 实现跨机存储方案。

预览版：JuiceFS 存储方案目前处于 Preview 阶段，适合快速上手与早期试用。配置项、部署脚本和运行行为在后续版本仍可能调整。默认搭配控制节点 Redis/MinIO 仅适用于试用；生产环境请先在测试环境验证，并参考「更换存储」切换到更可靠的元数据引擎与对象存储。

6.1 前置条件

  • 所有节点的内核需要 FUSE 支持；
  • 所有节点能够访问同一个 JuiceFS 元数据引擎和对象存储。

6.3 更换存储

从 MinIO 迁移到其他对象存储

Shell · 例如改用腾讯云 COS
ONE_CLICK_ENABLE_JFS=1

# 可继续使用现有 Redis；新卷时必须是新的、空的元数据地址。
CUBE_JFS_META_URL="redis://<redis-host>:6379/0"
CUBE_JFS_META_PASSWORD="<redis-password>"

# 例如使用腾讯云 COS
CUBE_JFS_STORAGE="cos"
CUBE_JFS_BUCKET="https://<bucket>-<appid>.cos.<region>.myqcloud.com"

CUBE_JFS_SECRET_KEY="<COS-SecretKey>"

然后参考 one-click 安装部署，重新进行控制节点和计算节点初始化。注意：目前 Cube 暂不支持从对象存储 A 平滑切换到对象存储 B，请在安装时指定要用的对象存储，或参考 JuiceFS 官方的数据同步文档进行迁移。

使用 Redis 之外的元数据引擎

CUBE_JFS_META_URL 可以使用 JuiceFS 支持的 MySQL、PostgreSQL、TiKV 等地址。例如：

CUBE_JFS_META_URL="mysql://user:@(10.0.0.20:3306)/juicefs"
CUBE_JFS_META_PASSWORD="password"

新集群直接填写该地址后执行控制节点初始化即可。已有卷迁移时，先停止写入并卸载所有客户端，再用 juicefs dump 从旧元数据引擎导出、用 juicefs load 导入一个空的新元数据引擎，随后更新所有节点的 CUBE_JFS_META_URL 并重新挂载。对象存储密钥默认不会包含在 dump 中，需要在新元数据引擎上重新配置。

先参考 K8s 部署的 Helm 安装章节，安装 Helm 并完成集群初始化，然后准备 values 文件。

6.5 节点变更

新增节点

  1. 按正常流程安装并注册新的 Cube 计算节点；
  2. 在新节点的 .one-click.env 写入 ONE_CLICK_ENABLE_JFS=1；
  3. 在新节点执行 sudo /usr/local/services/cubetoolbox/scripts/cube-jfs/mount.sh；
  4. 回到控制节点执行 check.sh，确认新会话出现。
控制节点只需在初始化时执行一次 init.sh，后续新增节点不需要再次执行。

删除节点

先隔离节点并清空沙箱，然后在待删除节点卸载，再在控制节点删除记录：

Shell · 卸载并删除节点
sudo /usr/local/services/cubetoolbox/scripts/cube-jfs/mount.sh unmount
cubeopscli node delete <node-id>
不要删共享目录：卸载节点不会删除共享 JuiceFS 中的数据。CUBE_JFS_ROOT 下的共享命名空间（objects/、snapshots/、pause-snapshots/）是全集群共享的，可能仍被其他节点引用，不要直接删除。

6.6 关键配置变量

变量默认值说明
CUBE_JFS_MOUNT_PATH/data/cubelet/storage/jfs挂载点
CUBE_JFS_ROOT.直接在挂载点保存共享命名空间
CUBE_JFS_CACHE_DIR/data/cubelet/jfs-cache本地缓存目录，读缓存与写 staging 都在其中，建议放 NVMe/SSD 数据盘
CUBE_JFS_CACHE_SIZE_MB102400（100 GiB）读缓存大小上限
集群内所有节点必须使用相同的 CUBE_JFS_MOUNT_PATH（以及 CUBE_JFS_ROOT）。快照 catalog 记录的是挂载点下的绝对路径，挂载点不一致的节点无法解析其他节点创建的包。

缓存目录与容量

CUBE_JFS_CACHE_DIR 同时存放两类数据：读缓存（raw/，从对象存储拉回的数据块，受 CUBE_JFS_CACHE_SIZE_MB 上限约束，可随时按 LRU 淘汰）和写 staging（rawstaging/，--writeback 下尚未上传的脏数据块，上传完成后即删除，不占用 CUBE_JFS_CACHE_SIZE_MB 配额）。

  • CUBE_JFS_CACHE_SIZE_MB 是上限而不是预留空间，缓存按需增长；磁盘不足 100 GiB 时挂载不会失败，读缓存只增长到实际可用大小。
  • JuiceFS 默认 --free-space-ratio 0.1：缓存所在文件系统剩余空间低于 10% 时，按近似 LRU 的 2-random 算法主动淘汰读缓存块。注意该 10% 是相对该目录所在数据盘总容量计算的。
  • 若磁盘被缓存之外的数据持续占满，读缓存被持续压缩，越来越多读请求退化为直读对象存储；剩余空间低于阈值一半（默认 5%）时 staging 写入同样受限。
  • staging 没有独立配额：数据盘被写满时，--writeback 下的新写入会直接失败，快照、暂停等操作可能报错，必须为 staging 和其他数据预留空间。
  • 建议将缓存目录放在独立的快速数据盘上，CUBE_JFS_CACHE_SIZE_MB 不超过该盘可用空间的 70%–80%。

6.7 镜像分发

目标节点默认从 Cube 自己的镜像仓库拉取 JuiceFS 客户端镜像 cube-sandbox-int.tencentcloudcr.com/cube-sandbox/juicefs:ce-v1.4.1。在 .env 里设置 MIRROR=cn 可改用 -cn 镜像。离线环境可提前 docker load，并修改 CUBE_JFS_IMAGE 指向本地镜像名；Kubernetes 部署中改为设置 images.juicefs.repository / tag。非必要无需升级，应让所有节点使用同一个固定版本。

6.8 排障

现象排查 / 处理
服务无法启动 先看 journalctl -u cube-sandbox-jfs.service -n 200 --no-pager、docker logs cube-sandbox-jfs、docker logs cube-sandbox-jfs-redis。常见：CUBE_JFS_META_URL/CUBE_JFS_META_PASSWORD 未写入或各节点不一致；无 /dev/fuse；拉不到 CUBE_JFS_IMAGE；Redis/MinIO/S3 不可达或凭证失效
容器运行但宿主机看不到挂载 用 findmnt -T /data/cubelet/storage/jfs 与 docker inspect cube-sandbox-jfs --format '{{.State.Status}}'。挂载脚本会建立 self bind 并设置 rshared，不要绕过 systemd 直接跑没有 bind-propagation=rshared 的容器
Cubelet 报 jfs storage is not configured 确认 [cow.jfs] enable = true，核对 mount_path、root、cache_dir 与 .one-click.env 一致；改后 sudo systemctl restart cube-sandbox-cubelet.service
remote_status 长时间停在 inprogress 使用 --writeback 时文件关闭后仍可能有 block 留在本地 staging。检查 JuiceFS 容器日志、对象存储连通性、缓存盘空间和上传带宽；不要直接删 cache 中的 staging 数据
只能在源节点恢复 依次确认 resource 的 backend 是 jfs、remote_status 已为 ready、所有节点元数据地址与 root 相同、目标节点 CPU/kernel 满足条件；host-mount 仍会把沙箱固定在源节点
K8s 首次安装格式化 Job 失败 凭证错误时 Job 会重试耗尽失败，挂载 Pod 停在 Init:CrashLoopBackOff。修正凭证后删除失败 Job 再 helm upgrade：kubectl -n cube-system delete job -l app.kubernetes.io/component=cube-juicefs-format
误删 JuiceFS 元数据 Secret 该 Secret 保存 Chart 管理的 Redis 密码，删除后 Chart 会生成新密码而 Redis 仍用旧密码。把 cubeJuiceFS.metadata.password 设为 Redis 实际密码（可从 Pod 内 /etc/redis/redis-auth.conf 读取），临时设 lifecycleChangeAck: true 重新升级，完成后移除

7CubeS3lvol 部署与性能

backend=s3 通过 CubeS3lvol 将暂停包和快照发布到共享 S3。跨机调度与 CPU/kernel 条件同第 5 节。

部署范围：CubeS3lvol 在 one-click 和 Kubernetes 上都默认关闭，需要显式启用。

7.1 配置后端 S3 服务

Cube 安装时默认安装 MinIO 作为 S3 服务，方便开箱体验；若要接入自己的 S3，按 CubeS3lvol 文档配置即可。

one-click

Shell · 启用（使用内置 MinIO 可直接复用凭证）
ONE_CLICK_ENABLE_S3LVOL=1
CUBE_S3LVOL_BUCKET=cube-s3lvol

外部对象存储还需设置 CUBE_S3_ENDPOINT、CUBE_S3_ACCESS_KEY_ID、CUBE_S3_SECRET_ACCESS_KEY 和 CUBE_S3_REGION。MinIO 等 path-style 服务设置 CUBE_S3LVOL_PATH_STYLE=true。安装程序会生成 /data/cubelet/s3.cfg、创建 WAL，并启用 cube-sandbox-s3lvol.service。

Kubernetes（Helm）

YAML · 最小启用
cubeS3lvol:
  enabled: true
  # 可选：覆盖 endpoint / 密钥。桶必须与 cube-volumes 分开。
  # s3:
  #   endpoint: https://s3.example.com
  #   accessKeyId: ...
  #   secretAccessKey: ...
  #   bucket: cube-s3lvol

sidecar 复用 chart 内置 MinIO（或已配置的 volumeS3）的 endpoint 与凭证，写入独立的 cube-s3lvol 桶——始终与 S3 volume 插件的 cube-volumes 桶分开。通常只需额外设置两种情况：外部 S3 端点为 path-style 时设 cubeS3lvol.s3.pathStyle: true；CPU 核做了隔离时设 cubeS3lvol.cpuMask（默认绑本进程 Cpus_allowed_list 里的最后两核）。

会重建 Big Pod：开启该开关会重建计算节点的 Big Pod，请在维护窗口操作，最好在创建任何沙箱之前开启。身份来自完整 Kubernetes 节点名，哈希成 rcow-<8hex>；Pod 重建仍是同一台机器。cubeS3lvol.lvsName 会给集群里每个节点钉同一个名字——多节点不要设。

首次启动时若 WAL 文件不存在会创建稀疏文件；journalMB / walMB / cacheMB 只在文件出现之前生效。开启 sidecar 后，Big Pod 的 terminationGracePeriodSeconds 会提高到至少 180s，以便 rcow_stop 完成 disconnect 与 unload。

其中包含默认 1 GiB 整对象 RAM cache（RCOW_CACHE_HOT_BUFS=1024）和默认 4 GiB 的 /dev/shm 写回环；cache 设为 0 可只使用磁盘 cache。

快照对象存放在共享 S3 上，但每台运行 s3lvol 的节点还需要一块本地 WAL 镜像盘。没有这块盘的节点既无法制作快照，也无法恢复快照。已确认、尚未进入 S3 的写在 /dev/shm 写回环里，不在磁盘 WAL 中；节点重启会丢掉还没进入 S3 的记录。

WAL 镜像盘

  • 路径：/data/cubelet/rcow/wal_bdev.img
  • 逻辑大小：默认 512 GiB，由 one-click install.sh 或 Helm sidecar 入口在首次启动时以稀疏文件方式创建
  • 只创建一次：journal / WAL / cache 三段的划分在创建时就固定，之后无法调整（只能重新创建镜像）
区域默认大小作用
Journal1024 MiB在途写操作记录，挂载 lvstore 时回放
WAL32768 MiB（32 GiB）磁盘上的区域，用于回放 0.7.2/0.7.3 写下的记录；新的、尚未进入 S3 的已确认写在 /dev/shm 写回环里
Chunk cache490496 MiB（≈479 GiB）最近写入 chunk 的本地缓存
镜像是稀疏文件：预留 512 GiB 逻辑空间并不会立即占用 512 GiB 物理磁盘。物理占用按实际写入增长，容量规划应围绕写入工作集，而非逻辑大小。

集群规划

  • 每台可能参与跨机恢复的节点都要在本地磁盘准备自己的 WAL 镜像——包括运行沙箱的计算节点，以及运行 s3lvol 的控制节点。
  • 三段大小在安装时通过 RCOW_JOURNAL_MB / RCOW_WAL_MB / RCOW_CACHE_MB（一键安装）、chart 的 cubeS3lvol.journalMB / walMB / cacheMB（Helm）或 CubeS3lvol 运行时环境配置设置。调整只在首次启动前有意义——镜像一旦创建，布局即固定。
  • 镜像不长期保存快照数据：它只是写缓冲加缓存，持久副本在 S3。

7.4 已知问题

  1. S3 快照对象由 S3lvol 异步删除，被引用的快照会拒绝删除。删除接口返回时，对象不一定已从 S3 消失。被引用时 CubeS3lvol 以 EBUSY 拒绝（export 仍在发布、有 live lease、lease miss 还不到 source grace 约 60 秒、本地 esnap clone 仍在读、存在多个 clone、正在 decouple）。此时会记录 pending-delete 标记（按 lvstore uuid + lvol uuid 记录，不按名字，避免同名快照被误删），可通过 rcow_get_lvstores 的 delete_pending 字段查看，deletable 表示当前是否可删。之后约 60 秒一次的 poller 会在阻塞消失后自动完成删除；poller 能自行完成的阻塞会返回成功并带 deferred: true。
  2. DB / FS 结构相较 0.7.0 之前版本变化较大，老数据适配仅覆盖 0.6.0。新版本会对老版本数据结构做适配，但适配测试只覆盖到 0.6.0；遇到未覆盖、适配失败的环境，需要手动清理老的 snapshot 文件与对应 DB 数据。
  3. 跨机 Resume 或从快照创建的沙箱，短时间内无法再次 Pause 或制作快照。需要等待的时间取决于 snapshot 文件大小，下个版本会修复。

8恢复决策与生命周期

恢复一个沙箱时，第一判断永远是「源节点还能不能用」——能用就在源节点本地恢复，不能用才走跨机。

8.1 本地恢复 vs 跨机恢复

本地恢复

源节点健康且可调度

直接在源节点恢复（xfs 或共享后端均可）。速度最快、无线程上传说，调度器始终优先此选项。

跨机恢复

源节点离线 / 被隔离

检查三件事：① 模板是 backend=jfs|s3；② remote_status=ready；③ 目标节点 cpuid_hash / host_kernel_release 匹配。全部满足才选兼容节点，否则报错。

禁止跨机

使用了 host-mount

挂载了宿主机目录的沙箱无法跨机。若必须迁移，改用 fs-only 快照并在目标节点重新声明挂载。

8.2 生命周期时间线：快照 → 暂停 → 迁移 → 恢复

以 S3 共享后端为例，一次典型的跨机迁移经历以下阶段（各阶段耗时见第 7.3 节基准表）：

T0快照 / 暂停

对源沙箱 create_snapshot() 或 pause(wait=True)。S3 同一时刻只能有一个 export；Pause 总在源节点完成。

T1共享 export

把包推送到共享 S3 / JuiceFS，轮询 remote_status 直到 ready。这段等待在基准里单列为「快照共享 / 暂停共享」。

T2隔离源节点

用 cubeopscli 隔离源节点使其不可调度，调度器才会考虑兼容的目标节点。

T3目标节点 import

目标节点登记 + lease + activate（FromSnap / Resume），开始按需拉取页面，进入 running。

T4恢复完成

沙箱在目标节点 running，guest 继续后台按页拉取。注意：短时间内无法再次 Pause 或制作快照（已知问题 3）。

running（源） → export / pause → inprogress → ready → running（目标）

remote_status 常见取值为 pending → inprogress → ready；长时间停在 inprogress 时按第 6.8 节排查 staging 上传与网络。

9易错点、记忆卡片与自测

9.1 易错点

1. 用 fs-only 快照回滚被拒。fs-only 只记录文件系统、不含内存，rollback() 会返回 snapshot_filesystem_only_rollback_unsupported。回滚只支持 full 快照。
2. 快照名称用了保留前缀。name 不能以 tpl- 或 snap- 开头，否则 HTTP 400。
3. 以为 with 会删快照。上下文管理器只 kill 沙箱，不删快照；需显式 Sandbox.delete_snapshot()。只有 clone() 的内部快照会自动清理。
4. 用 xfs 模板做跨机。默认 xfs 后端只在源节点保存数据，跨机必须用 --backend jfs|s3 创建模板，且已创建的模板不能转换后端。
5. host-mount 沙箱期望跨机。host-mount 会把沙箱固定在源节点；fs-only 快照不记录挂载，需创建时重新声明。
6. 各节点 JFS 挂载点不一致。快照 catalog 记录绝对路径，CUBE_JFS_MOUNT_PATH 与 CUBE_JFS_ROOT 必须全集群一致，否则无法解析其他节点创建的包。
7. 以为删除 S3 快照立即释放。S3 快照对象异步删除，被引用时 EBUSY 拒绝，需等约 60 秒 poller 或 --retry-pending。

9.2 记忆卡片

四原语Snapshot 存档、Clone/Fork 开新档、Rollback 读档重来；Rollback 保 ID 不变。
full vs fs-onlyfull 存内存可续进程；fs-only 只存文件、冷启动、不能回滚。
clone vs forkclone 客户端编排全成全败；fork 一次服务端调用、各自成败。
跨机三条件共享后端模板 + CPU/kernel 兼容 + 源节点不可调度。
JFS 必配全节点 FUSE、同一元数据/对象存储、挂载点全集群一致。
S3 必配每节点本地 512 GiB 稀疏 WAL 镜像 + 约 2 核 23 GiB；x86_64 需 AVX2。

9.3 自测

自测

Q1：想对运行中的沙箱开 100 个并行副本，且允许部分成功，应该用 clone 还是 fork？为什么？

用 fork(count=100)。它是一次服务端调用、单次快照、N 路派生，且各自独立成败——部分成功保留副本且不抛异常，临时快照由服务端管理。若需要「全成或全败」语义，才用 clone(n=100, concurrency=C)。count 上限为 100。

Q2：一个用 --backend jfs 创建、且挂载了宿主机目录的沙箱，源节点下线后能否跨机恢复？

不能。host-mount 会把沙箱固定在源节点，无法保证挂载目录在目标节点可访问。若必须迁移，应改用 fs-only 快照（不记录挂载），在目标节点创建时重新声明挂载，按普通新建沙箱调度。

Q3：为什么 create_snapshot(mode="fs-only") 之后调用 rollback() 会失败？想回滚该怎么办？

fs-only 不捕获 guest 内存，只保存文件系统，回滚需要还原内存，因此被拒绝（snapshot_filesystem_only_rollback_unsupported）。想回滚必须使用 mode="full"（默认）创建的快照。注意 fs-only 也不是增量链，每份都是独立镜像。
