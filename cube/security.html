1安全总览：四道防线

CubeSandbox 的安全不是一个总开关，而是分布在四条信任边界上的分层防线。它们彼此独立：任意一层配置失误，其余层仍能提供保护；反过来，缺少任意一层都会在某些场景留下缺口。

2出网安全代理：拦截链路

每台宿主机上部署一个透明出网代理 CubeEgress，位于沙箱的 TAP 设备与外网之间。沙箱发起的出方向 HTTP/HTTPS 请求会被它拦截，按运维侧定义的 L7 规则匹配，对每个请求选择放行、拒绝或在转发前重写。三类核心能力——域名过滤、凭证注入、访问审计——全部由「创建沙箱时携带的同一份规则列表」驱动。

CubeEgress 是一个 host-network 容器，在面向沙箱的 IP 上 bind 两个 TPROXY listener：8080（HTTP）与 8443（HTTPS）。哪些流量进哪个 listener 由每条规则声明的 port/scheme 映射决定，而不是绑定固定的目的端口。

链路中的每一步：

  • eBPF（mvmtap）：按 allow_out_v3 里的 (host, port)→scheme 映射，在出方向 SYN 上写 skb->mark（HTTP 或 HTTPS）。
  • iptables mangle/PREROUTING：-m mark -j TPROXY，HTTP mark 送到 192.168.0.1:8080，HTTPS mark 送到 192.168.0.1:8443。
  • ssl_certificate_by_lua：按客户端 SNI 现场签发一张 leaf 证书，签名链根是 CubeEgress 的 root CA——它在模板构建时已被烘进沙箱 rootfs 的系统 CA。
  • access_by_lua：匹配 L7 规则，做放行 / 拒绝 / 注入决策。
  • proxy_pass：转发到原始目的 IP（依赖 IP_TRANSPARENT 保留目的地址）。

为什么工作负载「看不到」MITM：leaf 证书的签名链能被沙箱系统 CA 信任，所以 TLS 客户端不会报错，代理也就能合法读写请求 / 响应。前提是模板构建时把 CubeEgress 的 root CA 烘进了沙箱——见第 4 节「不经过代理的路径」。
超时语义：proxy_read_timeout / proxy_send_timeout 为 2h（与 CubeProxy 同量级），限制的是相邻读写操作之间的空闲时间，而不是连接总时长；proxy_connect_timeout 仍是 10s。
WebSocket 边界：出方向 ws:// 与 wss:// 复用 HTTP / HTTPS listener，代理对初始握手应用 L7 规则，升级成功后转发帧；其他协议的 Upgrade 请求头不会转发。若客户端发了 Upgrade 而上游未经协商就返回 101 Switching Protocols，nginx 仍可能切换为隧道，切换后的流量不再经过 L7 规则检查。

3出网代理：过滤与凭证注入

域名过滤：先到先得，默认拒绝

每条规则有一个 match（命中条件）和一个 action（命中后做什么）。先到先得：第一条命中的规则决定结果；任何规则都不命中的请求被默认拒绝。

from cubesandbox import Sandbox, Rule, Match, Action

rules = [
    # 用 host 精确匹配阻止 apex
    Rule(
        name="deny_example_apex",
        match=Match(scheme="https", host="example.com"),
        action=Action(allow=False),
    ),
    # 用 *.<domain> 形态的 SNI 通配放行所有子域
    Rule(
        name="allow_example_subdomains",
        match=Match(scheme="https", sni="*.example.com"),
        action=Action(allow=True),
    ),
]

with Sandbox.create(network={"rules": rules}) as sb:
    sb.commands.run("curl -s https://www.example.com")  # → 上游
    sb.commands.run("curl -s https://example.com")      # → CubeEgress 返回 403
字段类型说明
scheme"http" / "https"大小写不敏感。与 port 的搭配语义见「自定义 L7 端口」。
portint要拦截的目的 TCP 端口，1–65535。必须与 scheme 同时设置。
snistringTLS ClientHello 的 SNI；以 *. 开头表示「任意子域」。*.example.com 命中 www.example.com 与 foo.bar.example.com，不命中 apex。
hoststring匹配 HTTP Host: 头（自动去端口）；语义同 sni，支持精确匹配或 *. 子域通配。
method方法列表列表内 OR 关系，如 ["GET", "POST"]。
pathstring匹配 ngx.var.uri；默认精确匹配，或以单个 * 结尾的前缀匹配（/v1/* 命中 /v1/chat 与 /v1/embeddings）。

请求要同时满足所有出现的字段；未出现的字段视作通配。

单层 vs 多层子域：*.example.com 不区分子域层数，所有结尾命中的子域都算。若只想放行单层子域（如 www、api），需要对不希望放过的嵌套子域单独追加 host="…" 的 deny 规则。
deny 的代价很低：deny 命中时 CubeEgress 直接返 HTTP 403，完全不接触上游——沙箱马上看到拒绝，没有 DNS 泄漏、没有 TCP 握手。

自定义 L7 端口

默认情况下一条规则拦截经典的 {80/http, 443/https} 集合。可选的 port + scheme 组合可以收窄或扩展哪个 TCP 端口会被送进代理：

portscheme拦截范围
省略省略{80/http, 443/https} —— 默认集合（向后兼容）
省略"http" / "https"仅该 scheme 的默认端口（http → 80，https → 443）
设置设置精确的 (host, port, scheme) 组合，例如 tcp/8443 上的 API
设置省略非法 —— port 必须搭配 scheme
 
from cubesandbox import Sandbox, Rule, Match, Action

rules = [
    # 拦截一个非标准 HTTPS 端口上的内部 API
    Rule(
        name="internal_api",
        match=Match(host="api.internal.example", port=8443, scheme="https"),
        action=Action(allow=True),
    ),
    # 拦截自定义端口上的明文 HTTP
    Rule(
        name="custom_http",
        match=Match(host="metrics.internal.example", port=18080, scheme="http"),
        action=Action(allow=True),
    ),
    # 只给 scheme 时仍走经典端口，但只匹配其中一侧
    Rule(
        name="https_only",
        match=Match(host="public.example", scheme="https"),
        action=Action(allow=True),
    ),
]

约束（SDK 客户端先校验，服务端再校验一次）：

  • port 必须在 [1, 65535]；scheme 必须是 http 或 https（大小写不敏感）。
  • L7 规则的 host 必须是域名或单个 IP —— 不支持子网 CIDR（子网无法出现在 HTTP Host: 头或 TLS SNI 里）。
  • 共享同一个 (host, port) 的所有规则必须对 scheme 达成一致；冲突的 policy 会被整体拒绝。
  • 每个 host 最多 8 个不同的 (port, scheme) 组合。
未覆盖端口怎么走：任何规则都没有覆盖的端口，仍回落到 L3/L4 的 allow_out / deny_out 策略，不会进入 CubeEgress。
allow 与 deny 省略 port 的语义不同：allow 省略 port 收窄到 {80/http, 443/https}（fail-closed）；deny 省略 port 时在该 host 内与端口无关，任何端口进来的被拦截流量都会命中。这能防止「较宽的 host deny 被较窄的自定义端口 allow 绕过」——deny host="*.example.com" 仍会命中 api.example.com:8443，想放行这个例外，请把更具体的 allow 规则放在前面。
L3/L4 与 L7 并存：同一个域名可以同时出现在 allow_out 列表和某条 L7 rule 里，两者并存——学到的 IP 既有一条纯 /32 任意端口放行（保留普通 SNAT 访问），也有每个 rule 端口一条 L7 (ip, port) 条目（让这些端口进代理）。给已在 allow_out 里的域名再加 L7 rule，不会移除它原有的纯 L3 放行，只是在 rule 端口上叠加了 L7 拦截。

凭证注入：密钥留在控制面

inject 规则在匹配成功后向出方向请求追加固定 header，最经典的场景是注入 API token：

from cubesandbox import Sandbox, Rule, Match, Action, Inject

rules = [
    Rule(
        name="deepseek_api",
        match=Match(scheme="https", host="api.deepseek.com",
                    method=["POST"], path="/v1/chat",
                    sni="api.deepseek.com"),
        action=Action(
            allow=True,
            audit="metadata",
            inject=[Inject(
                header="Authorization",
                format="Bearer ${SECRET}",
                secret="sk_xxxxxxxx",  # 运维侧密钥，沙箱永不可见
            )],
        ),
    ),
]
  • 工作负载发请求时不带 Authorization header；CubeEgress 接到请求、走完 match、再按 inject 列表追加 Authorization: Bearer sk_xxxxxxxx，然后 forward 给上游。
  • format 默认 "${SECRET}"（raw secret 作为 header 整值）；非 bearer 方案用 "Bearer ${SECRET}" 或任何含 ${SECRET} 占位符的模板。
  • inject 仅在 action.allow=true 时生效；deny 规则带 inject=[…] 是配置错误，会被忽略。
  • host="*" 与 sni="*" 可以带 inject，密钥会加到这条规则命中的每个目的地上，校验和具名主机相同。
核心价值「密钥留在运维侧」：密钥只存在于规则列表里，沙箱创建时被推到 CubeEgress，永远不会暴露给沙箱的环境变量、文件系统或进程空间。
安全提醒：HTTP 凭证注入有风险，应只在受控内网使用。明文 HTTP 无法验证对端身份——规则按 Host 匹配成功后，凭证会随请求发往当时解析出的目的 IP。若攻击者能控制该域名的 DNS，就能把凭证发往被控服务器。这不是 CubeSandbox 本身的问题，而是明文 HTTP 无法认证对端。
优先使用 HTTPS：为 inject 规则显式指定 scheme="https"。只有上游位于你完全掌控的内网时，才用 scheme="http"。省略 scheme 会同时匹配 HTTP 和 HTTPS，HTTP 一侧同样会注入凭证。

4出网代理：审计、边界与扩展

访问审计

每个请求按规则上的 action.audit 字段在三档审计级别里走一档：

级别落盘内容
none不记录
metadata（默认）请求 ID、沙箱 ID/IP、目的 IP/端口、HTTP 方法/主机/路径/状态及收发字节、TLS SNI/版本/加密套件、命中规则及决策、耗时（微秒）、脱敏请求头
full预留 —— 当前等同 metadata，未来用于完整请求/响应 body 抓取

日志在主机 /data/log/cube-egress/access.jsonl，每行一条 JSON：

{
  "ts": "2026-05-29T11:24:01+08:00",
  "request_id": "42-1",
  "event": "http_request",
  "sandbox": { "src_ip": "192.168.1.154", "policy_id": "sandbox-1" },
  "conn": { "original_dst_ip": "203.0.113.10", "original_dst_port": 443 },
  "tls": { "sni": "api.example.com", "cipher": "TLS_AES_128_GCM_SHA256", "version": "TLSv1.3" },
  "http": { "method": "POST", "host": "api.example.com", "path": "/v1/chat", "status": 200, "req_bytes": 412, "resp_bytes": 1856 },
  "policy": { "matched_rule": "api_rule", "decision": "allow", "duration_us": 384000 },
  "redacted_request_headers": { "Content-Type": "application/json" }
}

没有值的字段会被省略。记录凭证注入时才出现 credentials；发生安全事件或上游失败时才出现 security。upstream_addr 与 upstream_status 仅在上游失败时出现在 security 中。同一日志文件还落两类 schema 略有不同的事件：

  • security_event —— default-deny 拒绝、规则畸形短路、host/SNI 不一致、inject 触发等，带规则名 + reason 字段描述哪个守卫触发了。
  • tls_handshake —— TLS 握手本身失败时（leaf 签发失败、客户端中途断开等）发出，此时还没有 HTTP 报文，用于区分「TLS 没握上」与「请求被解密后被拒」。
密钥被脱敏：inject 的 secret 值在写入任何日志路径前都会被剥除。审计日志仅记录规则名和 inject 已运行的事实；密钥本身从不离开 lua VM。

不经过代理的路径（重要边界）

少数情形不走 CubeEgress，必须清楚边界，避免误以为「配置了规则就全拦住了」：

路径是否经过 CubeEgress说明
cube-dev 内部流量否沙箱到沙箱、沙箱到集群内服务（Cube API 等）不进 TPROXY 链路，不受规则约束
未被 L7 规则覆盖的 TCP/UDP否只重定向被规则标记的流量；其余端口仍受 L3/L4 allow_out/deny_out 约束，但代理看不到
没烘 CA 的模板否（TLS 失败）--with-cube-ca=false 创建的模板不信任 leaf 证书，HTTPS 在规则评估前就因 self-signed cert 报错
代理本身的部署（systemd 单元、CA 引导、iptables oneshot 服务）见 deploy/one-click 源码——那套脚本会自动把 CubeEgress 接到 control 和 compute target 里。

扩展代理：自定义 lua

match / inject 语法故意写得很窄，覆盖 80% 的常见场景（放行某个 host、拒绝另一个、附加 token），仅靠运维侧配置就够了。当你需要规则表达不出的行为——内容检查、跨请求状态、调外部分类服务——CubeEgress 本质就是一个 OpenResty 服务，你可以自行修改或新增 lua 脚本来扩展它。

文件Phase作用
cert_signer.luassl_certificate_by_lua按 SNI 现场签发 leaf 证书
bootstrap.luainit_worker_by_lua（仅 worker 0）启动时从 Cubelet 内置 network runtime 拉初始策略
access_phase.luaaccess_by_lua每个请求做 match → action → inject 决策
policy.lua（模块）内存中的策略表，由 admin.lua 和 bootstrap.lua 写入
admin.lua:9091 上的 content_by_lua（默认；CUBE_EGRESS_ADMIN_PORT）策略 CRUD admin API
audit.lualog_by_lua落 JSONL 审计日志
redactor.lua（helper）把敏感数据从用户可见路径里抹掉

nginx.conf 在每个 phase block 里通过 require("…") 调它们；比如 HTTP 和 HTTPS server 块的 access_by_lua_block 都调 require("access_phase").decide()。lua_package_path 配置为 /usr/local/openresty/nginx/lua/?.lua，所以放进这个目录的任何新文件，nginx reload 之后就能 require("name") 用。

一个 phase 钩子示例：写一个 prompt 内容过滤器，拦截发往 LLM 端点的请求体，扫描 prompt 文本，命中黑名单就拒。

-- lua/prompt_filter.lua
-- 在 access_by_lua 决定 allow 之后：检查发往 LLM 上游的
-- POST 请求体，命中禁用模式则拒。
local cjson = require("cjson.safe")
local _M = {}

local FORBIDDEN_PATTERNS = {
    "ignore previous instructions",
    "system prompt",
    "DAN mode",
}

local function is_target_endpoint(host, path)
    return host == "api.deepseek.com" and path == "/v1/chat/completions"
end

function _M.inspect()
    local host = ngx.var.cube_audit_host or ngx.var.http_host
    local path = ngx.var.uri
    if not is_target_endpoint(host, path) then
        return
    end

    -- 必须显式 read_body —— nginx 默认不把 POST body 给 lua。
    ngx.req.read_body()
    local body = ngx.req.get_body_data() or ""

    local payload, err = cjson.decode(body)
    if not payload or err then
        return  -- 非 JSON，放过
    end

    for _, msg in ipairs(payload.messages or {}) do
        local content = (msg or {}).content or ""
        for _, pat in ipairs(FORBIDDEN_PATTERNS) do
            if string.find(string.lower(content), pat, 1, true) then
                local audit = require("audit")
                pcall(audit.write_security_event, "prompt_filter:" .. pat,
                      ngx.ctx.cube_decision)
                return ngx.exit(ngx.HTTP_FORBIDDEN)
            end
        end
    end
end

return _M

把新模块挂在同一个 access_by_lua_block 里，让它在规则放行之后才跑：

server {
    listen 192.168.0.1:8443 ssl transparent reuseport;
    # ...

    location / {
        access_by_lua_block {
            require("access_phase").decide()
            require("prompt_filter").inspect()   # ← 新加这行
        }
        # ...
    }
}

lua 文件是烘进 cube-egress 容器镜像的，重新构建并重启：

# 重新构建镜像并重启服务
cd CubeEgress && make build
sudo systemctl restart cube-sandbox-cube-egress

  ...其它启动参数...
sudo docker exec cube-egress nginx -s reload

实现建议

  • 挂在 access_phase 之后，不要在前。这样 deny 规则先短路，你的 hook 不会为已经会被拒的请求做昂贵计算。
  • 走 audit 模块、不要光 ngx.log。手写日志不会进 access.jsonl，下游工具（SIEM ingest、SOC 大盘）按 JSONL schema 解析。
  • 控制延迟。调外部分类服务时，lua-resty-http 的超时要明显小于上游的 proxy_connect_timeout——沙箱在等你。
  • 失败要 fail-safe。分类服务挂时，提前决定走「拒绝（安全优先）」还是「放行（可用性优先）」，但一定不要让 worker 崩。外部调用包 pcall，无论结果如何写一条 security_event。
  • 别把密钥塞进 ngx.shared.*。那些 dict 对所有 worker 可见；敏感材料应该走 inject 路径（只写出方向）或 init_by_lua 的 per-worker 全局变量。

5API 鉴权：回调式身份校验

Cube API Server 默认不启用鉴权，所有请求直接放通。如需鉴权，启动时指定一个回调地址即可。启用后，每个入站请求的凭证 header 都会被转发到你的回调服务——Cube API Server 仅负责转发，鉴权决策由回调方完成。

启用方式

通过 --auth-callback-url 启动参数或对应的环境变量指定回调地址（CLI 参数优先级高于环境变量）：

# 启动参数
./cube-api --auth-callback-url https://your-auth-service/verify

# 或环境变量
export AUTH_CALLBACK_URL=https://your-auth-service/verify
./cube-api

未设置 AUTH_CALLBACK_URL 时（默认），所有请求无需凭证即可通过。

工作原理

客户端Bearer / API Key
→
CubeAPI提取 + 转发
→
回调服务200 / 非 200
① 客户端：携带 Authorization: Bearer <key> 或 X-API-Key: <key> 请求 CubeAPI
↓
② CubeAPI：从请求 header 提取凭证（Authorization: Bearer 优先于 X-API-Key），记录原始请求路径与 HTTP 方法
↓
③ CubeAPI → 回调：向 AUTH_CALLBACK_URL 发 POST，透传凭证 header、X-Request-Path、X-Request-Method
↓
④ 回调服务：同时校验路径与方法，返回 200 放行，其他状态码拒绝
↓
⑤ CubeAPI 回写：回调 200 → 放行；非 200 → 客户端收到 401 Unauthorized；回调不可达 → 500

SDK 侧配置

E2B SDK 会将 E2B_API_KEY 的值以 Authorization: Bearer <key> 的形式附加到每个请求中：

export E2B_API_KEY=your-actual-api-key

如果不使用 E2B SDK，也可以直接发送 X-API-Key：

X-API-Key: your-actual-api-key

两种格式均支持。两者同时存在时，Authorization: Bearer 优先。

回调请求格式

Cube API Server 向回调地址发送的 POST 请求包含以下 header：

Header值
AuthorizationBearer <token> —— 客户端使用 Bearer 鉴权时透传
X-API-Key<key> —— 客户端使用 API Key 鉴权时透传
X-Request-Path原始请求路径，如 /templates/my-tmpl
X-Request-Method原始请求的 HTTP 方法，如 GET、DELETE

两个凭证 header 互斥，回调方收到哪个取决于客户端发送的是哪种格式。若两者都未携带，CubeAPI 直接返回 401，不会调用你的服务。

回调示例（Python / FastAPI）

from fastapi import FastAPI, Request
from fastapi.responses import Response

app = FastAPI()

# 读操作方法集合
READ_METHODS = {"GET", "HEAD"}

# 只读凭证与完全访问凭证分开管理。
# 必须同时校验路径和方法——同一路径（如 /templates/:id）
# 既有 GET（读取），也有 DELETE、POST（重建）、PATCH（更新）。
READONLY_KEYS = {"readonly-key-1"}
FULL_ACCESS_KEYS = {"secret-key-1", "secret-key-2"}

@app.post("/verify")
async def verify(request: Request):
    path = request.headers.get("X-Request-Path", "")
    method = request.headers.get("X-Request-Method", "").upper()

    # 提取凭证（Bearer 优先）
    key = None
    auth = request.headers.get("Authorization", "")
    if auth.startswith("Bearer "):
        key = auth.removeprefix("Bearer ").strip()
    else:
        key = request.headers.get("X-API-Key", "")

    if not key:
        return Response(status_code=401)

    if key in FULL_ACCESS_KEYS:
        return {}                           # 200 → 放行所有操作

    if key in READONLY_KEYS:
        if method in READ_METHODS:
            return {}                       # 200 → 允许读操作
        return Response(status_code=403)   # 拒绝写 / 删操作

    return Response(status_code=401)
必须同时校验路径「和」方法：同一路径上挂载了多个 HTTP 方法——例如 /templates/:id 同时处理 GET（读取）、POST（重建）、DELETE（删除）和 PATCH（更新）。如果回调仅按路径白名单授权，读权限可能被放大为删除或覆写操作：持有只读凭证的调用方发送 DELETE 请求时，路径匹配不会拦截它。请在回调中同时校验 X-Request-Path 和 X-Request-Method。

错误响应

场景HTTP 状态码
请求未携带凭证401 Unauthorized
回调返回非 200（含回调返回 403）401 Unauthorized
回调地址不可达500 Internal Server Error
回调服务可用性即鉴权可用性：回调地址不可达时，CubeAPI 采取「失败即拒绝」策略（请求被拒绝，返回 500）。请保证鉴权服务有足够可用性并保持低延迟，因为每个 API 请求都会等待它返回。
健康检查例外：启用 Auth Callback 后，除 GET /health 外的所有 API 请求都必须携带凭证。不要把健康探针也接到需要鉴权的路径上。

方案 A：绑定到内网网卡

若机器同时拥有公网与内网网卡，将管理类服务绑定到内网 IP，使其仅内网可达、公网接口不暴露：

# .env
CUBEMASTER_HTTP_BIND=10.0.0.11
CUBE_API_BIND=10.0.0.11:3000
CUBE_API_HEALTH_ADDR=10.0.0.11:3000
# Cubelet/config/config.toml
[http]
  address = "10.0.0.11:9998"
[grpc]
  tcp_address = "10.0.0.11:9999"

这样既保持多机通信正常（compute 节点经内网连接），又避免公网访问。对于单机一体化、无 compute 节点的场景，可以绑定到 127.0.0.1 实现最大限度收紧（注意下文各服务的相关限制）。

不要随手绑回环：如果有 compute 节点或使用 host 网络模式的 cube-proxy，请勿将 CUBEMASTER_HTTP_BIND 设为 127.0.0.1——它们需要通过节点的外网/内网 IP 访问 CubeMaster。同理，WebUI 容器通过 host.docker.internal 访问 CubeAPI，把 CubeAPI 绑到 127.0.0.1 会导致桥接模式 Docker 下的 WebUI 不可用。改 CUBE_API_BIND 时必须同步更新 CUBE_API_HEALTH_ADDR。

方案 B：防火墙源 IP 白名单

保持默认的 0.0.0.0 绑定，但通过防火墙规则只放通可信来源 IP（你的 compute 节点和管理机）。

使用 iptables：

# CubeMaster 只放通 compute 节点 + 管理机
sudo iptables -A INPUT -p tcp --dport 8089 -s 10.0.0.12 -j ACCEPT       # compute-1
sudo iptables -A INPUT -p tcp --dport 8089 -s 10.0.0.13 -j ACCEPT       # compute-2
sudo iptables -A INPUT -p tcp --dport 8089 -s 192.168.1.100 -j ACCEPT   # 管理机
sudo iptables -A INPUT -p tcp --dport 8089 -j DROP                      # 拒绝其余

# 对 9999、3000、12088 按需重复同样的规则

使用 ufw：

sudo ufw default deny incoming
sudo ufw allow from 10.0.0.0/24 to any port 8089 proto tcp   # CubeMaster
sudo ufw allow from 10.0.0.0/24 to any port 9999 proto tcp   # Cubelet
sudo ufw allow from 10.0.0.0/24 to any port 3000 proto tcp   # CubeAPI
sudo ufw allow from 10.0.0.0/24 to any port 12088 proto tcp  # WebUI
sudo ufw allow 22/tcp     # SSH
sudo ufw allow 80/tcp     # cube-proxy（如需公网）
sudo ufw allow 443/tcp    # cube-proxy TLS
sudo ufw allow 9090/tcp   # cube-proxy 明文 gRPC
sudo ufw enable
两者结合（推荐）：为实现纵深防御，同时绑定内网 IP 并设置防火墙规则。即使某一层配置失误，另一层仍能提供保护。

多机端口可达性要求

部署 compute 节点时，以下连通性必须保持开放。请确保你的绑定地址与防火墙规则不会阻断这些路径：

  • CubeMaster 与 CubeAPI 不做 TLS 终止。如需对外 TLS，请将其置于 cube-proxy 或独立反向代理之后。

8安全最佳实践与易错点

安全最佳实践清单

  • ✓ 所有 inject 规则显式写 scheme="https"，只在完全掌控的内网才用 http
  • ✓ 对 *.domain 通配放行时，额外用 host="domain" 的 deny 规则封住 apex 与不需要的嵌套子域

自测

1. 沙箱访问 https://example.com 被 403 拒绝，但访问 https://api.example.com:8443 却成功了。规则应如何解释？

很可能是先写了一条 deny host="example.com"（只命中 apex），又写了一条 allow host="*.example.com" 通配子域。由于 *.example.com 不命中 apex，而 apex 的 deny 先命中，所以 example.com 被拒；api.example.com 命中通配 allow，放行。若要放行 api.example.com:8443 这类自定义端口，记得 port 必须搭配 scheme，且更具体的 allow 规则要放在较宽的 host deny 之前。

2. 回调服务对只读凭证的 DELETE 请求返回了 403，但客户端收到的是 401。为什么？如何避免只读凭证被用来删除？

按官方文档，回调返回「非 200」时 CubeAPI 统一向客户端返回 401 Unauthorized（403 不会原样透传）。要避免只读凭证被放大为删除操作，回调里必须同时校验 X-Request-Path 与 X-Request-Method：只读凭证仅在 method ∈ {GET, HEAD} 时返回 200，其余返回非 200。仅按路径白名单授权会被 DELETE 绕过。

3. 你把 CUBEMASTER_HTTP_BIND 和 Cubelet 的 tcp_address 都设成了 127.0.0.1，结果多机集群直接不可用。正确做法是什么？

多机部署中，compute 节点需要经内网/外网 IP 访问控制节点的 CubeMaster（8089），控制节点需要经 tcp_address（9999）访问各 compute 节点的 Cubelet。绑 127.0.0.1 会切断这两条路径。应改为绑定内网 IP（如 10.0.0.11）并保留多机端口可达性；只有单机一体化、无 compute 节点时才可绑回环。同时改 CUBE_API_BIND 要同步改 CUBE_API_HEALTH_ADDR。
