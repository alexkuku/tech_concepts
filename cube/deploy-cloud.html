1三条路线怎么选

先判断你的「环境约束」是什么，再决定用哪条路线。三条路线共享同一套 CubeSandbox 组件，差别只在于谁来提供 KVM/PVM 算力与依赖哪种网络。

场景 A

腾讯云 Terraform 集群

需要一套高可用、可对外服务的沙箱集群，且接受按量计费。用发布包自带部署器一键拉起 TKE 控制面 + CVM PVM 计算节点。

场景 B

离线部署

目标机器在内网机房 / 隔离网段，没有公网，但能拿到安装包与容器镜像。按正常流程安装，只是产物靠人工搬运。

场景 C

本地 QEMU 开发环境

只有一台 Linux 笔记本 / 工作站 / WSL 2，想体验或直接改代码，又不愿污染宿主机。在一次性虚机里随便折腾。

3安全组与网络暴露

集群版的网络加固由腾讯云安全组完成：部署器按角色创建 4 个独立安全组，各自只放行该角色实际需要的入站端口。攻破任一角色都不会继承其他角色的入站面。计算节点与 TKE 节点无任何公网入站，计算节点不分配公网 IP。

四个安全组出站均默认放行全部（0.0.0.0/0 ALL）。数据库、TKE API Server 等均不开公网，仅限 VPC 内网访问。CLB 80 / 443 / 3000 的来源取决于 TENCENTCLOUD_ENABLE_PUBLIC_NETWORK：默认内网模式（false）来源为 VPC CIDR 10.0.0.0/16；开启公网模式（true）来源为 0.0.0.0/0。

公网服务加固建议

仅在开启公网模式（TENCENTCLOUD_ENABLE_PUBLIC_NETWORK=true）时适用。默认内网模式下三个服务均不对公网暴露，可跳过本节。开启后三个公网入口的安全模型不同，必须按服务分别加固：
  • WebUI（CLB 80）：控制台目前不带任何鉴权，任何能访问到它的人都能操作沙箱。强烈建议为 WebUI 的 CLB 单独创建一个安全组，配置严格的源 IP 白名单（仅放行办公网 / 管理机出口 IP）。
  • cube-api（CLB 3000）：默认对所有请求放行、不做凭证校验。对外暴露前务必启用 Auth Callback 鉴权，把决策委托给你自己的鉴权服务。
  • cube-proxy（CLB 80 / 443）：沙箱流量的公网入口，设计上即面向公网。若要限制对沙箱的公开访问，需启用每沙箱独立的入站 token 等机制。

4前置条件与快速开始

运行 create.sh 的机器无需预装 Terraform。先备好腾讯云 API 凭证与几个本地工具，再开通必要的云服务即可。

前置条件清单

  • 腾讯云 API 凭证：在访问管理控制台创建密钥对，导出 TENCENTCLOUD_SECRET_ID / TENCENTCLOUD_SECRET_KEY。
  • 本地工具：ssh、scp、nc，以及访问腾讯云 API 的网络。terraform 与 jq 缺失时会自动安装。
  • mkcert / openssl 无需本地安装——cube-proxy 证书在跳板机上生成。
  • 执行机：推荐 Linux；create.sh / destroy.sh 也支持 macOS（含 Bash 3.2）。Windows 请使用 WSL2。

Terraform Provider Init 加速（推荐）

国内网络下 tencentcloudstack/tencentcloud Provider 可能在下载时超时（典型报错 failed to retrieve authentication checksums、Client.Timeout exceeded）。在 Linux / macOS 上创建或更新当前用户的 ~/.terraformrc：

provider_installation {
  network_mirror {
    url = "https://mirrors.tencent.com/terraform/"
    include = ["registry.terraform.io/tencentcloudstack/*"]
  }

  direct {
    exclude = ["registry.terraform.io/tencentcloudstack/*"]
  }
}

部署前云服务开通与授权

  • 账号基础：注册腾讯云并完成实名认证；子账号需授予创建 VPC / CVM / TKE / CDB / Redis / CLB 等资源的权限（如关联 QcloudTKEFullAccess）。
  • TKE 服务角色授权（必须）：首次使用 TKE 前须完成服务角色授权，确认 TKE_QCSRole / IPAMDofTKE_QCSRole 等角色已授权，否则创建集群、CLB 型 Service 会失败。
  • Private DNS（按需）：USE_TCR=true 或 E2B SDK 访问 *.cube.app 时需开通；未开通时 API 可能返回 ResourceNotFound.ServiceNotSubscribed。
  • CFS（按需）：仅当 USE_CFS=true 且 cubemaster 多副本时需要，Terraform 会在 apply 阶段自动创建文件系统。

快速开始

部署器位于解压后发布包的顶层目录，解压后即可直接运行：

tar -xzf cube-sandbox-one-click-<version>.tar.gz
cd cube-sandbox-one-click-<version>

# 复制环境变量模板，填入凭证并按需编辑其余项
cp terraform/tencentcloud/env.example terraform/tencentcloud/.env
# $EDITOR terraform/tencentcloud/.env

./terraform/tencentcloud/create.sh

create.sh 会自动加载同目录下的 .env（仅填充未在当前 shell 中显式设置的变量）。凭证也可改用 export 注入，后者优先级更高、会覆盖 .env 中的同名值：

export TENCENTCLOUD_SECRET_ID="your-secret-id"
export TENCENTCLOUD_SECRET_KEY="your-secret-key"
create.sh 会自动完成：① 探测本地发布包作为离线源（设了 TENCENTCLOUD_LOCAL_BUNDLE 或探测到本地包则无需公网，否则回退在线安装）；② 生成 SSH 密钥对；③ 在跳板机用内置 mkcert 生成 cube-proxy 的 TLS 证书（cube.app / *.cube.app）；④ 默认模式拉取公网预置镜像；⑤ TCR 模式创建 TCR 并在跳板机构建、推送六个组件镜像。

成本估算

官方文档不内置具体价格——刊例价会随地域、规格档位、活动和时间变动。请用腾讯云官方价格计算器，按上面「默认配置创建的资源明细」中的规格自行测算：CVM（跳板机 / 计算节点 / TKE worker）、TKE 托管集群管理费、云数据库 MySQL / Redis、NAT 网关 / CLB / 弹性公网 IP、CFS / TCR。评估完成后立即 destroy.sh 释放即可避免空转计费；长期使用可手动改 main.tf 的计费字段为包年包月（PREPAID）。
包年包月注意事项：包年包月资源不会被 destroy.sh（terraform destroy）自动退费 / 释放，需要手动到期释放或在控制台退费；切换后执行 destroy.sh 可能报错或留下残留资源。建议仅在确认长期使用时才切换。

6部署阶段、重试与验证

资源按固定顺序创建，任一阶段失败即停止（快速失败）。理解阶段划分，才能在部分失败时精准重试而不是全都销毁重来。

阶段 1 · 网络：VPC / 子网 / NAT（USE_TCR=true 时附带 TCR）
↓
阶段 2 · CVM：跳板机 + 计算节点
↓
阶段 3 · 镜像（仅 TCR 模式）：跳板机构建并推送六个组件镜像
↓
阶段 4 · 数据库：云数据库 MySQL / Redis（USE_CFS=true 时附带 CFS 共享存储）
↓
阶段 5 · 集群：TKE 集群 + Kubernetes 插件
↓
阶段 6 · 收尾：健康检查 → 计算节点安装
Kubernetes provider 只在 TKE API Server 就绪后才接入。拆除时，若创建了 CFS，共享存储会先于其子网销毁（其 NFS 挂载点是该子网内的一个 ENI）。Terraform 状态保存在本地 terraform/tencentcloud/（*.tfstate，已被 gitignore，无远端后端），请妥善保留该目录与生成的 .env。

部分失败后的重试

若某阶段中途失败（如所选地域 / 可用区机型售罄、账号配额限制或瞬时 API 错误），无需全部销毁重来：

  • 修复原因——多数情况是调整配置：换一个 TENCENTCLOUD_AVAILABILITY_ZONE / TENCENTCLOUD_COMPUTE_INSTANCE_TYPE / TENCENTCLOUD_REGION、提升配额、设置密码等，然后直接重跑 ./terraform/tencentcloud/create.sh。
  • 重跑时 create.sh 会重新加载 .env 中的选择，将状态与云上已存在的资源对账（刷新并导入有状态资源，而非重建），并从中断处继续；已有计算节点会保留（绝不缩容）。
  • 可用性因地域和可用区而异——某可用区提供的机型在另一可用区可能不可用。交互式菜单按你的地域实时查询，最终选择在 apply 时校验。
  • 仅在确实要拆除部署时才运行 destroy.sh；普通重试之间无需运行它。

验证与拆除

部署完成后，create.sh 会执行健康检查并打印访问入口。你也可以通过跳板机进入 VPC 内网排查：

# create.sh 会输出形如下面的命令
ssh -i terraform/tencentcloud/.ssh/id_rsa -p 443 -o StrictHostKeyChecking=no root@<jumpserver_public_ip>
./terraform/tencentcloud/destroy.sh
避免意外计费：如果 destroy.sh 无法删除全部资源（例如 MySQL / Redis 卡在回收站 / 隔离状态，或 Terraform 已无法感知的残留），请登录腾讯云控制台手动删除剩余资源——VPC / 网络、MySQL 回收站、Redis 回收站、CFS 文件系统（若曾启用 USE_CFS=true）。当某个拆除步骤失败时，destroy.sh 也会打印这些链接。

7E2B 与 cube.app 域名解析

单机 one-click 安装会通过 CoreDNS + split DNS 在宿主机上解析 *.cube.app；Terraform 集群版默认不包含这套 DNS 配置。若要通过 E2B 官方 SDK 创建 / 访问 sandbox，需要额外配置域名解析。

背景：cube-proxy 为 cube.app / *.cube.app 终结 TLS（证书由 create.sh 在跳板机用 mkcert 生成，或通过 BYO 证书替换）；E2B SDK 访问 sandbox 时使用形如 https://<sandbox-id>.cube.app 的 URL；默认 TENCENTCLOUD_ENABLE_PUBLIC_NETWORK=false 时，cube-proxy CLB 是 VPC 内网 VIP，只有 VPC 内（或经跳板机 / VPN）才能访问。

部署完成后，在 terraform/tencentcloud/ 目录获取 CLB 地址：

cd terraform/tencentcloud
terraform output tke_cube_proxy_clb_ip    # cube-proxy
terraform output tke_cube_api_clb_ip      # cube-api（E2B_API_URL）
terraform output tke_cube_webui_clb_ip    # WebUI
terraform output tke_cubemaster_clb_ip    # cube-master（VPC 内网）
terraform output jumpserver_ssh_command   # 跳板机 SSH 命令

三种解析方案

方案一 · 推荐

Private DNS

客户端在 VPC 内、或经跳板机 / VPN 接入 VPC。创建私有域 cube.app，加 * A 记录指向 cube-proxy 内网 VIP，并关联到部署所在 VPC。

方案二 · 仅测试

/etc/hosts

在运行 E2B SDK 的机器上手动绑定若干 sandbox 域名。泛域名无法完整覆盖所有 sandbox ID，不适合多 sandbox 并发测试。

方案三 · 公网

公网 CLB + 公网 DNS

设 TENCENTCLOUD_ENABLE_PUBLIC_NETWORK=true 重建 CLB，把 cube.app / *.cube.app 解析到公网 VIP，并换成公网 CA 证书。

方案一（Private DNS）步骤：① 登录 DNSPod 内网解析，创建私有域 cube.app；② 添加 A 记录，主机记录 *，记录值填 terraform output tke_cube_proxy_clb_ip 的内网 VIP（可选再给 @ 加同一 VIP）；③ 将该私有域关联到部署所在 VPC；④ 在 VPC 内的跳板机或计算节点上验证：

dig +short test.cube.app
curl -k https://test.cube.app/   # 自签名证书需 -k 或信任 mkcert CA
能力单机 one-clickTerraform 集群版
*.cube.app 解析自动（CoreDNS + split DNS）需手动配置 Private DNS / hosts / 公网 DNS
TLS 证书宿主机 mkcert跳板机 mkcert → K8s Secret 挂载
cube-api 地址http://<host>:3000cube-api CLB 内网 / 公网 VIP

E2B SDK 环境变量

export E2B_API_URL=http://<cube-api-clb-vip>:3000
export E2B_API_KEY=e2b_000000
E2B SDK 访问 sandbox 本身走 *.cube.app → cube-proxy，因此 cube.app 域名解析与 TLS 证书是必须项，仅配置 E2B_API_URL 不够。
自带 TLS 证书：cube-proxy 的 nginx 配置硬编码了证书路径 …/certs/cube.app+3.pem 与 …/certs/cube.app+3-key.pem。运行 create.sh 前把 PEM 证书 + 私钥放入 terraform/tencentcloud/cubeproxy-certs/，文件名必须是这两个，并覆盖 cube.app 与 *.cube.app 两个 SAN。轮换时替换文件并重跑 create.sh 即可刷新 Secret 并重启 cube-proxy。

8离线部署：五步流程

目标机器没有公网（内网机房、隔离网段、受限环境），但接入内网并配有内网软件源。离线部署完全可行：一键安装脚本原生支持离线——预载容器镜像直接生效，部署包自带全部版本锁定产物，真正需要公网的只有三件事：下载安装包、安装缺失软件包、拉取容器镜像。

步骤 1 · 下载安装产物：在有公网的机器下载一键部署包（必要时加 PVM 宿主内核包），拷贝到目标节点
↓
步骤 2 · 系统软件包：有内网源可跳过；无源则提前装好 Docker、Compose 等
↓
步骤 3 · 预载容器镜像（核心）：docker pull → docker save → 目标节点 docker load，或推内网仓库
↓
步骤 4 · 安装：解压部署包，./install.sh，与正常部署相同
↓
步骤 5（可选）· 模板源镜像入内网仓库：安装完成后把模板源镜像推入内网仓库，创建模板时直接引用
适用范围：覆盖一键部署（单机、裸金属、多机集群）。两种部署方式不适用——腾讯云 Terraform 部署器（需访问腾讯云 API 创建云资源）与 Kubernetes（Helm）部署（集群必须能访问存放组件镜像的仓库；若已有内网仓库如 Harbor，按 Kubernetes 部署指南把 chart 指向该仓库即可）。

开始之前：确认宿主机条件

  • x86_64 或 aarch64 Linux，glibc ≥ 2.31，root 权限
  • 内存至少 8 GB（安装器硬性检查，不足会直接终止安装）
  • /data/cubelet 使用 XFS，至少 50 GB
  • KVM 可用：裸金属原生支持；x86_64 云服务器可先安装 PVM 内核（见步骤 1，不支持 aarch64——ARM 机器必须本身已有 KVM）

步骤 1：下载安装产物

在有公网的机器上下载下列产物，拷贝到目标节点（内网若已有制品中转站或 Release 镜像，直接走内网获取）：

  • 一键部署包：cube-sandbox-one-click-<version>-<arch>.tar.gz，<arch> 与目标节点架构一致（amd64 / arm64）。
  • PVM 宿主内核包（rpm/deb）：仅当目标是无 /dev/kvm 的云服务器时需要，从最新的 kernel-release-* release 下载，安装并重启后再继续。

步骤 2：提前安装系统软件包（无内网源时）

已配置内网软件源？直接跳到步骤 3。没有内网源的机器才需要本步。跳过前先确认内网源里收录了 Docker 和 Compose——不少内网源不带它们。

  • Docker Engine 和 Compose：只要 docker 和 docker compose version（或 docker-compose）都能运行，install.sh 就跳过联网安装。不支持 snap Docker（读不到 /usr/local/services），请用软件包方式安装 docker-ce / docker.io。
  • 基础命令：tar、ss、ip（iproute2）、bash、curl、grep、sed、pgrep（procps）、awk、date、openssl
  • e2fsprogs + util-linux：默认存储后端 cubecow 依赖 mkfs.ext4、mount、umount、losetup
  • 按需安装：dnsmasq（宿主机无 systemd-resolved / resolvectl 时必装）、s3fs + jq（S3 卷挂载，务必提前装好）、python3 / nvme-cli / libaio / libnuma / libuuid（仅启用 CubeS3lvol 时）、logrotate（最小化系统镜像若未自带请补装）

验证 Docker 就绪：

docker version && docker compose version   # 或：docker-compose --version

9离线部署：镜像清单与运维

容器镜像是离线部署的核心。两种搬运方式任选其一：逐台搬运（有公网、同架构机器 docker pull → docker save → 目标节点 docker load），或走内网镜像仓库（多节点推荐，推到 Harbor 后用覆盖变量指向它）。

步骤 4：安装（与正常部署相同）

所有命令必须以 root 身份执行，先切换到 root，解压部署包后安装：

控制台地址是 http://<目标主机>:12088，E2B 兼容 API 在 3000 端口。

离线安装的日志长什么样？registry 不可达时，三个组件镜像各打一行 WARN: pull failed but local image exists; using cached copy 后改用预载镜像，其余服务静默使用预载镜像——都是预期行为，不是错误。只有出现 pull failed … and no local copy is cached 才说明某个镜像没 load，回步骤 3 检查。

步骤 5（安装后，可选）：把模板源镜像推入内网仓库

想在离线环境创建模板，就把模板源镜像推送到内网镜像仓库，创建模板时直接引用内网仓库地址。原理：CubeMaster 构建模板时从 registry 拉取源镜像——内网仓库可达即可，不需要公网；多机集群无需额外处理，CubeMaster 通过内网分发构建产物，计算节点不拉源镜像。

# 有公网的机器
docker pull cube-sandbox-int.tencentcloudcr.com/cube-sandbox/sandbox-code:latest
docker save -o sandbox-code.tar cube-sandbox-int.tencentcloudcr.com/cube-sandbox/sandbox-code:latest

# 能访问内网仓库的机器
docker load -i sandbox-code.tar
docker tag cube-sandbox-int.tencentcloudcr.com/cube-sandbox/sandbox-code:latest \
  <内网仓库>/cube/sandbox-code:latest
docker push <内网仓库>/cube/sandbox-code:latest
cubemastercli tpl create-from-image \
  --image <内网仓库>/cube/sandbox-code:latest \
  --writable-layer-size 1G \
  --expose-port 49999 \
  --expose-port 49983 \
  --probe 49999
  • 内网仓库需要认证时，加 --registry-username / --registry-password。
  • 内网仓库走 HTTP（无 TLS）时，引用必须带 http:// 前缀，例如 http://harbor.internal:5000/ns/app:tag。

升级、模板构建与卸载

  • 升级 = 新部署包 + 新镜像（tag 会随版本变化）：重新执行步骤 1 和步骤 3，然后 ./install.sh --mode=upgrade。
  • 离线构建自定义模板镜像：Dockerfile 构建通常要访问 apt / pip，把软件源指向内网镜像，或提前在有公网环境构建好完整镜像再按步骤 5 推入内网仓库。
  • 卸载流程不变：/usr/local/services/cubetoolbox/scripts/one-click/uninstall.sh。

10开发环境：QEMU 虚机

手头只有一台本地机器（Linux 笔记本 / 工作站 / WSL 2），没有独立云服务器，但仍想体验或直接上手改代码？dev-env/ 会在本机起一台一次性的 OpenCloudOS 9 虚机，把 Cube Sandbox 装在虚机里跑，宿主机保持干净。

不是生产部署方式。dev-env/ 是单机、密码认证、用完即弃的开发 / 体验环境。生产部署请走快速开始或多机集群部署，在 bare-metal 机器上执行。

三条命令上手

cd CubeSandbox/dev-env
./create_vm.sh    # ① 创建虚机（仅首次，约 10 分钟）
./run_vm.sh       # ② 在终端 A 启动虚机
./login.sh        # ③ 在终端 B 登录，拿到 root shell
  • create_vm.sh 会下载官方 OpenCloudOS 9 qcow2（约 800 MB）、把磁盘扩到 100 GB、启动一次完成初始化后干净关机。只需跑一次；想重建干净虚机，删掉 dev-env/.workdir/ 重跑即可。
  • run_vm.sh 把 QEMU 串口控制台挂在终端 A，默认只转发 SSH（127.0.0.1:10022）。
  • login.sh 密码由脚本自动处理，登录后直接是 root shell。
关机千万别用 Ctrl+a 然后 x。那相当于硬断电，可能损坏虚机状态。请在另一个终端用 ./login.sh 登录后，在虚机内执行 poweroff；虚机正常关机后，run_vm.sh 自己会退出。

guest 就是一台普通的 OpenCloudOS 9 机器，dnf、curl、docker 都能直接用。在虚机内执行官方一键安装：

curl -sL https://github.com/tencentcloud/CubeSandbox/raw/master/deploy/one-click/online-install.sh | bash
# 国内环境建议走腾讯云镜像
curl -sL https://cnb.cool/CubeSandbox/CubeSandbox/-/git/raw/master/deploy/one-click/online-install.sh | MIRROR=cn bash

端口映射：宿主机 ↔ 虚机

默认只转发 SSH。要把虚机内的 Cube API（3000）与 CubeProxy HTTPS（443）暴露到宿主机，用 EXTRA_FORWARDS：

宿主机 127.0.0.1
:10022SSH
:13000Cube API
:11443CubeProxy HTTPS
↓ QEMU user networking（-netdev user）
OpenCloudOS 9 虚机（guest）
:22sshd

:443cube-proxy
宿主机虚机用途

# 启动时按需转发（推荐，长期使用），统一绑定在宿主机 127.0.0.1
EXTRA_FORWARDS="13000:3000 11443:443" ./run_vm.sh
# 临时开一条隧道（不改启动参数）

条目格式是空格分隔的 宿主机端口:虚机端口；格式非法时脚本会在 QEMU 启动前直接报错退出。

传文件（宿主机 ↔ 虚机）

SSH 已转发到 127.0.0.1:10022 且允许密码登录（用户 / 密码默认 opencloudos），宿主机上直接用 scp / rsync / ssh 即可。

# 宿主机 → 虚机
scp -P 10022 ./local-file opencloudos@127.0.0.1:/tmp/
scp -P 10022 -r ./local-dir opencloudos@127.0.0.1:/tmp/
rsync -avz -e 'ssh -p 10022' ./_output/bin/ opencloudos@127.0.0.1:/tmp/bin/
scp 登录的是普通用户 opencloudos，写不了 /usr/local/bin 这类系统目录，需先落到 /tmp 再用 sudo 安装： 
scp -P 10022 ./cubelet opencloudos@127.0.0.1:/tmp/
ssh -p 10022 opencloudos@127.0.0.1 \
  'sudo install -m 0755 /tmp/cubelet /usr/local/bin/cubelet'
# 虚机 → 宿主机
scp -P 10022 opencloudos@127.0.0.1:/data/log/cubelet.log ./
scp -P 10022 -r opencloudos@127.0.0.1:/data/log ./guest-logs/
ssh -p 10022 opencloudos@127.0.0.1 'sudo journalctl -u cubelet --no-pager' > cubelet-journal.log

./login.sh 连不上虚机还没启动，或宿主机 10022 端口被占确认 ./run_vm.sh 还在运行，或通过 SSH_PORT 换端口

df -h / 仍然很小虚机内扩容没走完看 .workdir/qemu-serial.log，再 scp 进 grow_rootfs.sh 手动跑一次
EXTRA_FORWARDS 的端口被占宿主机上已有服务占用该端口换一个宿主机端口，例如 EXTRA_FORWARDS="23000:3000"

11下载与 Release

CubeSandbox 的所有发布物都在同一个 Releases 页面上。先按场景对号入座，再照做即可——照着快速开始部署的话，你不需要本页，在线安装脚本会自动下载一键部署包并解析全部产物。

你的场景需要手动下载什么常规获取方式
标准部署（快速开始、裸金属）什么都不用在线安装脚本自动解析
PVM 部署（云服务器无 /dev/kvm）宿主机内核包（rpm/deb）kernel-release-* Release
离线部署安装包、容器镜像、系统软件包见第 8、9 节
自建发布包 / 替换内核或镜像guest 内核、guest 镜像kernel-release-* / guest-image-*

需要手动下载整包（cube-sandbox-one-click-<版本>-<架构>.tar.gz，架构为 amd64 / arm64）：

wget https://cnb.cool/CubeSandbox/CubeSandbox/-/releases/download/v0.6.0/cube-sandbox-one-click-v0.6.0-amd64.tar.gz

PVM 部署：下载宿主机内核包

PVM 部署中唯一需要手动下载的就是宿主机内核包——装上它、重启进入 PVM 内核即可获得 KVM 能力。PVM 的 guest 内核（vmlinux-pvm）已内置于一键部署包，安装时设 CUBE_PVM_ENABLE=1 即自动激活。内核包发布在专属的 kernel-release-* Release 上：

  • RPM 系（OpenCloudOS、RHEL、CentOS、TencentOS、Fedora）：kernel-*opencloudos9.cubesandbox.pvm.host*.x86_64.rpm
  • DEB 系（Ubuntu、Debian）：linux-image-*opencloudos9.cubesandbox.pvm.host*_amd64.deb

资产列表中的 kernel-headers-*、-dbg 等为可选包，无需下载。OpenCloudOS 9 用户可直接用官方 yum 仓库 dnf install 一行直装，无需手动下载 rpm。

自建部署：下载 guest 内核与镜像

只有在自行构建发布包或替换组件时才需要下载这些（一键部署包已全部自带）：

# guest 内核（发布在 kernel-release-* 下，文件名固定）
wget "https://cnb.cool/CubeSandbox/CubeSandbox/-/releases/download/kernel-release-260812-1/vmlinux-amd64"       # 裸金属/KVM，aarch64 用 vmlinux-arm64
wget "https://cnb.cool/CubeSandbox/CubeSandbox/-/releases/download/kernel-release-260812-1/vmlinux-pvm-amd64"    # PVM guest 内核（仅 x86_64）

# guest 镜像（发布在 guest-image-* 下，内含 cube-guest-image-cpu.img）
wget https://cnb.cool/CubeSandbox/CubeSandbox/-/releases/download/guest-image-260820-1/cube-guest-image-amd64.tar.gz
tar -xzf cube-guest-image-amd64.tar.gz

URL 中的 tag 会随发布递增（文件名固定，换 tag 即可）；最新 tag 可在 Releases 页面过滤 kernel-release / guest-image 查看。自建时把 vmlinux 放入 deploy/one-click/assets/kernel-artifacts/ 即可。

URL 规律、最新 tag 与版本 pin

所有资产两个渠道完全一致，把域名换掉即可切换：

渠道URL 规律
CNB 镜像（国内推荐）https://cnb.cool/CubeSandbox/CubeSandbox/-/releases/download/<tag>/<资产名>
GitHub（权威源，境外推荐）https://github.com/TencentCloud/CubeSandbox/releases/download/<tag>/<资产名>
 
# 列出最新的 kernel-release tag
gh release list --repo TencentCloud/CubeSandbox --limit 30 | grep kernel-release

# 按通配下载（<tag> 替换为上面查到的最新 tag，无需知道精确文件名）
gh release download <tag> --repo TencentCloud/CubeSandbox \
  --pattern 'kernel-6*.x86_64.rpm'   # 或：--pattern 'linux-image-6*_amd64.deb'
版本 pin：每个 v* 产品版本在 deploy/release-assets.yaml 中记录打包所用的 kernel / guest-image tag（也写在包内 release-manifest.json），据此可查「我手里的包用的是哪个内核」。专属 tag 的发布节奏独立于产品版本，pin 可能落后于最新 tag——PVM 宿主机内核建议始终用最新 kernel-release-*（含内核安全修复），无需与产品版本对齐。

13自测题

合上页面，先自己回答，再展开对照。

自测

1. 默认配置下，为什么从公网访问不到 cube-webui？如果要临时切到公网，需要改哪个变量、注意什么？

因为默认 TENCENTCLOUD_ENABLE_PUBLIC_NETWORK=false，cube-api / cube-proxy / cube-webui 关联的是 VPC 内网 CLB（来源 10.0.0.0/16），只有 VPC 内（经跳板机 / VPN）可访问。设为 true 会重建 CLB 并放行 0.0.0.0/0。注意 WebUI 目前不带任何鉴权，cube-api 默认也不校验凭证，开启公网前必须做源 IP 白名单 / Auth Callback 等加固。

2. 离线部署时安装器报 pull failed … and no local copy is cached，如何定位？

说明某个镜像没 load 进来，或 load 的引用（tag / 仓库）与安装器解析出的不一致。用 docker images 对照部署包默认引用（env.example，或 grep -rhE '_IMAGE.*_DEFAULT="' scripts/ 查），再检查 MIRROR 是否与拉取的 -cn / -int 引用一致。注意 WARN: pull failed but local image exists; using cached copy 是预期行为，不是错误。

3. 在 dev-env 里想用宿主机 13000 访问虚机里的 Cube API（3000 端口），怎么起虚机？

用 EXTRA_FORWARDS 启动：EXTRA_FORWARDS="13000:3000 11443:443" ./run_vm.sh，条目统一绑定在宿主机 127.0.0.1。若端口被占可换一个（如 23000:3000）；也可以不改启动参数、临时开隧道：ssh -N -L 13000:127.0.0.1:3000 -p 10022 opencloudos@127.0.0.1。
