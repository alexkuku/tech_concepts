1运维工具全景

CubeSandbox 的运维工具按“离用户多远”分成四层：给人看的 WebUI、集群级的 cubemastercli、节点管理专用的 cubeopscli、单节点排障的 cubecli，以及进入 guest MVM 的 cube-runtime。选错工具最常见的后果是：在错误的机器上执行命令、看到的是本节点视图而不是集群视图。

看集群

WebUI（:12088）

用浏览器看指标、创建沙箱、管理模板与 API Key。适合人眼观察和点选操作。

集群级

cubemastercli（:8089）

查所有 sandbox、模板元数据、模板 redo / merge、销毁 sandbox。跨节点操作优先用它。

节点管理

cubeopscli（:3010）

节点列表、隔离 / 取消隔离、删除节点、机型与标签。节点注册由 Cubelet 自动完成。

单节点

cubecli

在计算节点本地查 sandbox、进容器、看日志、清孤儿存储、看 tap 状态。

Guest 内

cube-runtime login

通过 hybrid-vsock 进 guest debug console，排查 guest 内核、网络、agent 与挂载。

2WebUI 控制台

Dashboard 是一个静态前端，由控制节点上的 nginx 容器托管。它本质上只是 CubeAPI 的一个轻量客户端：每个页面背后都是一次 /cubeapi/v1/* 请求，和 E2B SDK、curl 调的是同一个 E2B 兼容 REST API。

检查集群是否健康

打开 Overview（/），应看到几张偏绿色的 KPI 卡片：

  • Running Sandboxes：当前活跃的 micro-VM 数量；
  • CPU / Memory Utilization：整集群的压力；
  • Healthy Nodes：N/M 个节点处于 Ready 状态。

如果哪项数字飘红，点进 Nodes 看是哪个宿主出了问题。

创建一个沙箱

  1. 点左侧栏的 Sandboxes，再点右上角 + New sandbox。
  2. 在网格里挑一个模板。优先选 READY；如果模板标了“需重建”，先打开详情点“重建模板”，再建沙箱。其它 READY 模板在节点升级后仍可直接创建。
  3. （可选）填几对 meta 键值对作为标签。
  4. 点 Create。几秒内会跳转到该沙箱的详情页，能看到日志实时滚动。

要停掉一个沙箱，去 Sandboxes 列表，找到对应行，点最右边的暂停 / 销毁按钮。

配置 API Key（仅在开启鉴权时需要）

  1. 点左侧栏的 API Keys。
  2. 把 Key（形如 sk-cube-…）粘进输入框。
  3. 点 Save。Key 会保存在浏览器的 localStorage.cube.apiKey，之后每次请求自动带上 X-API-Key 请求头。

常见问题

为什么还要单独做个 Dashboard，不能直接用 curl 吗？

绝大多数操作（从镜像创建模板、看版本矩阵、排查节点）在 UI 里更容易发现和理解。Dashboard 只是 CubeAPI 的轻量客户端，每个页面背后都是一次 /cubeapi/v1/* 请求。

Dashboard 会保存我的数据吗？

只会在浏览器里保存 localStorage.cube.apiKey。其他所有状态（模板、沙箱、日志）都在集群上。

能改端口或关掉 Dashboard 吗？

改端口：在 .env 里设 WEB_UI_HOST_PORT，重跑 install.sh，下次启动 cube-sandbox-webui.service 时生效。关掉：把 WEB_UI_ENABLE 设成 0（或不设），集群照常运行，只是不再提供 WebUI，3000 端口的 API 不受影响。

Dashboard 是开源的吗？

是。它在仓库的 web/ 目录里，用 Vite + React + TypeScript + Tailwind 构建。

3CLI 工具速查

四个 CLI 的分工很清晰：cubemastercli 面向集群、cubeopscli 面向节点管理、cubecli 面向单节点运行时、cube-runtime 面向 guest MVM。下面命令中的 <...> 都是占位符，复制后替换成真实值。

cubemastercli：集群级管理

# 确认地址与版本
cubemastercli --address <cubemaster-host> --port 8089 --help
cubemastercli --address <cubemaster-host> --port 8089 version

# 查看所有 sandbox / 单个 sandbox
cubemastercli --address <cubemaster-host> --port 8089 list --all
cubemastercli --address <cubemaster-host> --port 8089 info --sandboxid <sandbox-id>

# 模板列表与元数据（含各节点副本状态）
cubemastercli --address <cubemaster-host> --port 8089 tpl ls
cubemastercli --address <cubemaster-host> --port 8089 tpl info <template-id>

# 新增节点后，在指定节点重新构建 / 分发模板
cubemastercli --address <cubemaster-host> --port 8089 tpl redo \
  --template-id <template-id> \
  --node <node-id-or-host>

# 从 OCI 镜像创建模板
cubemastercli --address <cubemaster-host> --port 8089 tpl create-from-image \
  --image <registry>/<repo>:<tag> \
  --writable-layer-size 1G \
  --expose-port 49983 \
  --probe 49983

# 把 READY 模板的 rootfs artifact 迁入 TC 存储（API: /cube/template/migrate）
cubemastercli --address <cubemaster-host> --port 8089 tpl merge <template-id>

# 只提交 migrate job，不等待结束
cubemastercli --address <cubemaster-host> --port 8089 tpl merge <template-id> --detach

# 破坏性操作：通过控制面删除 sandbox
cubemastercli --address <cubemaster-host> --port 8089 cubebox destroy <sandbox-id>
merge 与 redo 的口径：tpl merge 解决历史 artifact 的存储收敛问题（本地盘 → S3 托管存储），tpl redo 解决节点侧的重新分发 / 必要时重建问题。两者独立：同一次运维既要迁存储又要重新覆盖节点时，先 merge 再 redo。

cubeopscli：节点管理

# 节点列表 / 单节点查询
cubeopscli --address <cubeops-host> --port 3010 node list
cubeopscli --address <cubeops-host> --port 3010 node list --hostid <node_id>

# 隔离 / 取消隔离 / 删除
cubeopscli --address <cubeops-host> --port 3010 node isolate <node-id>
cubeopscli --address <cubeops-host> --port 3010 node unisolate <node-id>
cubeopscli --address <cubeops-host> --port 3010 node delete <node-id>
cubeopscli --address <cubeops-host> --port 3010 node rm --force <node-id>

# 版本信息
cubeopscli --version
cubeopscli version
cubeopscli version --versiononly

delete 的别名是 rm。删除节点要求节点已隔离且无沙箱；批量删除时单个节点失败不会中断后续节点，命令最终返回非零退出码。--force 可在无法校验沙箱清单时强制删除，但仍要求先隔离。

cubecli：计算节点本地工具

cubecli --help
cubecli version

# 本机 Cubelet 上的 sandbox（可按 ID 过滤）
cubecli cubebox ls
cubecli cubebox ls --sandbox <sandbox-id>

# containerd 容器元数据 / sandbox 或模板日志
cubecli container info <container-id>
cubecli logs <sandbox-id>
cubecli logs --stderr <sandbox-id>

# 本地 volume 与孤儿存储清理（先 dry-run）
cubecli storage ls
cubecli storage cleanup --dry-run

# Cubelet network runtime 的 tap 状态（需要 toolbox 配置，并会提示确认）
cubecli network ls

# 进入 sandbox 容器 / rootfs 视角
cubecli exec -it <sandbox-id> bash
unsafe 命令是运维变更：cubecli unsafe ... 只应在明确理解本地节点影响范围时使用。例如 cubecli unsafe rm --all 会删除当前节点上的所有本地 sandbox。在多节点集群中，cubecli 只覆盖命令所在节点，集群级操作请优先使用 cubemastercli。

cube-runtime：进入 guest MVM

cube-runtime --help
cube-runtime login --help

# 登录 sandbox MVM（默认 debug console 端口 1026，连接超时 10s）
cube-runtime login <sandbox-id>
cube-runtime login <sandbox-id> --port 1026 --timeout 10

login 会连接 sandbox 的本地 hybrid-vsock 路径，再进入 debug console 端口。当需要 guest VM 视角时使用它，例如排查 guest 内核状态、guest 网络接口、agent 状态、挂载点或 MVM 级 pause / resume 行为。cube-runtime snapshot 是底层 snapshot 工作流使用的命令，通常由 Cubelet / CubeMaster 的上层流程调用；除非排查运行时内部问题，否则应优先使用 cubemastercli 的模板和快照操作。

4节点身份与动态 IP 跟随

CubeSandbox 把计算节点的稳定身份（node_id / InstanceID）与可拨号地址（HostIP / Endpoint IP）解耦，使节点 IP 变更后控制面与数据面链路仍能自动跟随新 IP。理解这套规则，是安全做节点换 IP、滚动升级和回滚的前提。

node_id 与 Endpoint IP 的解析优先级

cubelet 启动时按以下优先级解析自身身份（见 Cubelet/pkg/utils/cloud.go）：

环境变量 / 来源解析对象优先级与说明
CUBE_SANDBOX_NODE_IDnode_id最高优先级，可为任意稳定标识。Kubernetes Helm 部署中 Chart 通过 Downward API 默认注入 spec.nodeName，同一宿主机上 cube-node Pod 重启或重建后 node_id 保持不变。
CUBE_SANDBOX_NODE_IPnode_id未设置 NODE_ID 时使用。一键安装 / systemd / Terraform 物理机部署默认走此路径，节点静态 IP 直接作为 node_id。
自动探测主网卡非回环 IPv4node_id兜底：默认路由网卡 → 出站探测 IPv4 → 首个非回环 IPv4。
CUBE_SANDBOX_ENDPOINT_IPEndpoint IPKubernetes Helm 部署中 Chart 通过 Downward API 默认注入 status.podIP。
node_id 本身是合法非回环 IPv4Endpoint IP未设置 ENDPOINT_IP 时直接复用 node_id。
自动探测主网卡非回环 IPv4Endpoint IP以上都不满足时的兜底。
动态 IP 跟随的前提：node_id 在 IP 变更前后必须保持稳定（显式配置 CUBE_SANDBOX_NODE_ID，或使用 Kubernetes Helm Chart 默认注入的 spec.nodeName）。若未设置 CUBE_SANDBOX_NODE_ID 而由 IP 兜底作为 node_id，IP 变化会被视为一个新节点。

控制面与数据面如何跟随节点 IP 变更

当计算节点以相同 node_id、新 HostIP 重新注册时：

CubeOps
更新 HostIP写入共享 Redis Hash节点删除时同步移除
CubeMaster
同时保存 HostID / HostIP按 node_id 动态解析关闭旧 IP 的 gRPC 连接池
CubeProxy
本地路由缓存保存 HostID10s 刷新 TTL单飞合并 / 1s 错误退避
  • CubeOps：更新节点注册信息中的 HostIP，并在注册与每次心跳时将 node_id -> host_ip 同步写入共享 Redis Hash cube:v1:shared:node:endpoint（节点删除时同步移除）；后续心跳保持最新注册的 HostIP 不被旧值覆盖。
  • CubeMaster：在沙箱代理路由、本地缓存、暂停快照、异步任务和状态对账器中同时保存 HostID 与 HostIP，向 cubelet 发起调用前按 node_id 动态解析最新 HostIP；检测到节点 IP 变更时自动关闭旧 IP 对应的 gRPC 连接池。
  • CubeProxy：在本地路由缓存中保存 HostID，通过 cube:v1:shared:node:endpoint 解析节点实时上游 IP（本地缓存 10s 刷新 TTL，并发刷新单飞合并，Redis 异常时优先回退到最近一次查到的实时 IP 并启用 1s 错误退避，无需清理存量沙箱路由缓存）。

滚动升级与回滚

  • 兼容性：存量不含 HostID 的 sandbox:proxy:{sandboxID} 路由，在 CubeMaster 和 CubeProxy 中都会自动降级使用静态 HostIP，无需数据迁移。
  • 推荐滚动升级顺序：先升级 CubeOps（节点心跳约 10s 内自动补齐 cube:v1:shared:node:endpoint），再升级 CubeProxy 和 CubeMaster（先升级 CubeMaster 再升级 CubeProxy 同样安全，旧版 CubeProxy 会忽略 HostID 并继续使用静态 HostIP）。
  • 多副本 CubeMaster：在所有副本完成升级前，避免执行跨节点 Resume。新旧版本混跑期间，旧版只改写 HostIP 而不清除新版写入的 HostID，可能导致沙箱继续解析到旧节点。
  • 回滚：若将 CubeMaster 从新版回滚到旧版，Redis 中已写入的 HostID 不会被旧版清理；回滚时请先回滚 CubeProxy，或清理受影响 sandbox:proxy:{sandboxID} 中的 HostID 字段。
  • CubeProxy 平滑重载：升级后通过 nginx 平滑重载保留的旧路由缓存项不含 HostID，首次命中时会集中从 Redis 重新加载一次。

5节点分组、机型与标签

沙箱的跨机恢复要求源节点和目标节点的 CPU 与 Kernel 完全一致。三个概念容易混淆，先记住一句话：节点分组是“自动识别出的同类机器”，机型是“人为声明可以互相恢复的一组节点”，标签是“自由格式的记录”。

节点分组

系统按 CPU 与内核特征自动归类节点。查看集群的节点类别及每组成员：

cubeopscli node groups

输出示例（默认精简显示：组名、CPU 信息、成员数量和成员列表）：

type-2   AMD            AMD EPYC 7B13 ...     2      node-4,node-5(cordoned)
  • 同组节点之间可以互相跨机恢复内存快照，不同组之间不可以。
  • 构建共享存储后端的模板、执行跨机恢复、规划宿主内核滚动升级之前，都可以先用该命令确认集群里混用了几种节点类型。
标记含义

机型配置

机型用于声明一组可以互相恢复内存快照的节点。默认规则要求源、目标节点 CPU 相同且宿主内核版本完全一致；宿主内核滚动升级之后，同一批机器的内核小版本常常不一致，本可以互相恢复的机器因此被挡在门外。把这组机器绑定到同一个机型，即可豁免内核一致性要求：

  • 在 WebUI 的“节点 → 机型管理”或用 cubeopscli machine-type 创建机型，并把节点绑定到机型上；
  • 绑定后的节点会带上标签 cube.cubesandbox.io/machine-type=<机型名>，没有该标签就是未绑定；
  • 机型只放宽内核比较，CPU 仍必须相同。
源节点目标节点须满足
未绑定机型cpuid_hash 和 host_kernel_release 都相等（不变）

cubeopscli machine-type create intel-oc9-k66 \
  --display-name "Intel OC9" \

6节点扩容、隔离与删除

节点没有单独的 node add 命令：计算节点服务启动后会自动完成注册。真正需要人工介入的是扩容后的模板分发、隔离、清空与删除。先看完整生命周期：

未注册 → Ready → cordoned 隔离 → 已删除

其中“Ready → cordoned”可逆（unisolate 回到 Ready）；“cordoned → 已删除”不可逆，但也不是永久禁止注册——如果 Cubelet 仍在运行或再次启动，它可以使用相同节点 ID 重新注册为新节点记录。

增加节点

  1. 将控制节点使用的同一份发布包复制到计算节点并解压。
  2. 复制环境配置模板，然后设置计算节点角色、节点 IP 和控制面地址： 
    cp env.example .env

ONE_CLICK_DEPLOY_ROLE=compute
CUBE_SANDBOX_NODE_IP=<当前节点IP>
ONE_CLICK_CONTROL_PLANE_IP=<控制面IP>
  3. （可选但强烈建议）从控制节点复制 CUBE_S3_* 到本机 .env： 
    # 在控制节点执行，把输出拷贝到计算节点 .env
grep '^CUBE_S3_' /usr/local/services/cubetoolbox/.one-click.env
    也可指向其他共享的 S3 兼容存储。缺失时仅告警并继续安装，但 S3 卷插件不可用，安装结束时会再次提醒。
  4. 安装计算节点：sudo ./install-compute.sh
  5. 检查本地服务：sudo ./quickcheck.sh
  6. 在控制节点确认新节点已注册并处于健康状态：cubeopscli node list

隔离与取消隔离

隔离会临时阻止 CubeMaster 向指定计算节点调度新沙箱，行为类似 Kubernetes cordon：节点仍保持健康，已有沙箱继续运行；后续新沙箱不再选择该节点，如果没有其他可调度节点，创建会失败。已有沙箱不会自动销毁或迁移。

# 隔离单个 / 多个节点（幂等）
cubeopscli node isolate <node_id>
cubeopscli node isolate <node_id_1> <node_id_2>

# 确认 SCHEDULING_DISABLED 为 true
cubeopscli node list

# 维护完成，允许节点重新接收新沙箱
cubeopscli node unisolate <node_id>

自动化场景可以使用带 JWT 的 CubeOps API：

# 隔离
curl -X PUT "http://127.0.0.1:3010/api/v1/nodes/<node_id>/isolation" \
  -H "Authorization: Bearer $TOKEN"

# 取消隔离
curl -X DELETE "http://127.0.0.1:3010/api/v1/nodes/<node_id>/isolation" \
  -H "Authorization: Bearer $TOKEN"
隔离不等于清空节点：隔离不会驱逐已有沙箱。执行会中断进程或网络的维护操作前，需要先隔离节点，再主动销毁该节点上的沙箱。进行破坏性维护前，建议至少等待 60 秒，让正在进行的调度和创建窗口结束。

删除节点

删除节点会从 CubeOps 移除节点注册信息、状态、组件版本元数据和指标缓存。它不会停止节点进程、销毁沙箱、删除磁盘或删除 Kubernetes Node 对象。CubeOps 只允许删除已经隔离且没有沙箱的节点；删除操作本身不会隔离节点，也不会销毁节点上的负载。

重启服务

场景 A：改了配置，想让单个服务生效

最常见的两种配置入口：顶层环境 /usr/local/services/cubetoolbox/.one-click.env，以及组件原生配置 Cubelet/config/config.toml、Cubelet/dynamicconf/conf.yaml、CubeMaster/conf.yaml、cubeproxy/global.conf、coredns/Corefile.template。改完之后，重启直接读这份配置的那个服务：

sudo systemctl restart cube-sandbox-cubelet.service
sudo systemctl restart cube-sandbox-cubemaster.service
sudo systemctl restart cube-sandbox-cube-api.service
sudo systemctl restart cube-sandbox-cube-proxy.service
sudo systemctl restart cube-sandbox-coredns.service
CoreDNS：改模板，而不是渲染产物 Corefile。coredns/Corefile 是渲染产物：cube-sandbox-coredns.service 每次启动都会从 coredns/Corefile.template 重新渲染（coredns-prepare.sh → coredns-start.sh → render_template_atomic）。直接改渲染文件会在下次重启时被静默覆盖，请修改模板文件再重启服务。
改了 systemd unit 文件本身：如果直接动了 /etc/systemd/system/cube-sandbox-*.service 文件本身，需要先 sudo systemctl daemon-reload 再 restart。但如果你只是改了 helper 脚本（/usr/local/services/cubetoolbox/scripts/systemd/*.sh），不需要 daemon-reload，下一次 restart 就会重新拉起脚本生效。

场景 B：服务挂了 / 反复重启

每个 service 都配了 Restart=on-failure，进程崩一次会自动重启。但如果反复 fail，需要先看清楚原因再重启：

# 1. 当前状态：Active、Restart Counter、最近 10 条 journal
sudo systemctl status cube-sandbox-cube-proxy.service --no-pager

# 2. 启动期日志：脚本、ExecStart、拉镜像、健康检查超时
sudo journalctl -u cube-sandbox-cube-proxy.service -n 200 --no-pager

# 3. 业务日志在 /data/log/，不在 journal
sudo tail -200 /data/log/Cubelet/Cubelet-req.log
sudo tail -200 /data/log/CubeMaster/cubemaster-req.log
sudo tail -200 /data/log/CubeAPI/cube-api-$(date +%F).log

# 4. 重置 failed 计数后再启
sudo systemctl reset-failed cube-sandbox-cube-proxy.service
sudo systemctl restart cube-sandbox-cube-proxy.service

场景 C：整套重启 / 整机维护后复位

# 控制节点
sudo systemctl restart cube-sandbox-control.target

# 计算节点
sudo systemctl restart cube-sandbox-compute.target

# 或者发布包目录下
sudo ./down.sh
sudo systemctl start cube-sandbox-control.target
target 本身没有进程，restart target 时 systemd 会顺序重启所有 PartOf=cube-sandbox-control.target 的 service。这条命令是替代“逐个写一长串 service 名”的快捷方式。

场景 D：完整下线（停止整套服务）

# 推荐：用发布包内的脚本（自动按角色走）
sudo /root/cube-sandbox-one-click-<version>/down.sh

# 等价命令
sudo systemctl stop cube-sandbox-control.target   # 控制节点
sudo systemctl stop cube-sandbox-compute.target   # 计算节点

轮转：按小时 rename + create

CubeShim 和 VMM 运行期间会保持日志文件打开。CubeShim 通过内部每 30 分钟轮转事件 reopen；VMM 控制线程自己持有 monotonic timerfd，每小时发出已有的 LOG_CTRL_REOPEN 控制记录。reopen 由固定周期驱动：宿主机执行“rename + create”后，会在下一次计划中的 reopen 时切换到新文件。因此宿主机侧仍应按小时执行轮转，并使用“rename + create”方式，不要使用 copytruncate。

一键部署会安装 /etc/cube-sandbox/logrotate.d/cubesandbox，并启用每小时的 cube-sandbox-logrotate.timer。Kubernetes / Helm 仍需手工安装：把下面的示例保存为 /etc/logrotate.d/cubesandbox，并确保宿主机每小时执行一次 logrotate；发行版默认的每日任务只能按天轮转。

/data/log/CubeVmm/vmm.log /data/log/CubeShim/*.log {
    su root root
    hourly
    rotate 24
    missingok
    notifempty
    compress
    delaycompress
    create 0640 root root
}
rotate 24 约保留 24 小时日志，可按实际保留周期调整。delaycompress 会将最新的轮转文件延迟一个周期压缩，因为 writer 在下一次计划中的 reopen 之前可能仍使用旧 fd。不需要 postrotate 信号或重启服务；该策略保证宿主机侧 retention 有界，但不承诺对任意手工轮转立即响应，也不支持 copytruncate。示例使用 root root，因为随附的一键部署 systemd 服务以 root 运行；如果 CubeShim 或 VMM 使用其他账号运行，请把 su 和 create 的 user/group 都改成对应账号。

哪份配置在生效

CubeMaster 按下面的优先级决定调度策略：

分支 1：配置了 scheduler.profiles → 使用这些 Profile，按标签或实例类型路由
↓ 否则
分支 2：配置了 legacy filter / score / postscore → 编译为兼容的 default Profile
↓ 否则
分支 3：全为空 → 注入出厂 Profile，启动时输出告警
  • 配了 profiles：按配置顺序做路由，第一个命中请求标签或实例类型的 Profile 生效，都没命中走标记为 default: true 的那个。
  • 只配了 legacy 块：编译成一个兼容的 default Profile，容错语义和 priority_select_num、least_select_name 的行为都保持不变。
  • 全为空：注入出厂 Profile（burst_balance、template_reuse、mixed_binpack），零配置也能按真实策略调度。因为放置行为和旧版的随机选点不同，注入时会打一条告警；想保持旧行为就设 scheduler.disable_factory_profiles: true。
内置 Score 的因子开关不在 Profile 里：real_time_weighted_average、image_score、multi_factor_weighted_average 始终读全局的 scheduler.score 树。Profile 引用了它们但缺这块配置，会在启动或热更新时报编译错误。出厂 Profile 自带这块配置，所以零配置部署不受影响；自己写 Profile 引用内置 Score 时要记得保留。

推荐配置

小集群（POC、功能验证、低并发）

新建集群可以直接用，已有集群按需合并，不要整体覆盖：

scheduler:
  priority_select_num: 3
  metric_update_timeout: 300s
  local_metric_update_timeout: 300s
  filter:
    enable_filters:
      - cpu
      - mem
      - template_locality
      - realtime_create_num
  score:
    enable_scorers:
      - real_time_weighted_average
    resource_weights:
      mvm_num: 2
      local_create_num: 3
      quota_cpu_usage: 1
      quota_mem_usage: 1
    plugin_conf:
      real_time_weighted_average:
        weight: 1.0
        enable_weight_factors:
          - mvm_num
          - local_create_num
          - quota_cpu_usage
          - quota_mem_usage

要点：至少 2 台计算节点；priority_select_num 从 3 开始，节点不够 3 台就设成节点数；Cubelet 上报周期和超时保持默认；配额用推导值即可，压测前再显式检查。

生产集群

  • 用 host.scheduler_label 把不同用途的节点分成节点池（通用、内存型、压测等），避免互相挤占；
  • 大小规格混部时，给不同 instance_type 单独设 node_max_mvm_num_conf，不要共用一组上限；
  • priority_select_num 调到健康节点数的一小部分即可，大到接近全量就退化成完全随机；
  • template_locality 过滤器保持开启；
  • 给 host.quota.creation_concurrent_num 设明确上限，防止单节点被突发创建打满；
  • 控制面同步扩容（TKE 节点数、控制面副本数），别让 CubeMaster 或 cube-api 先成为瓶颈。

调度流程

一次创建请求进来后，CubeMaster 做四步：

1. 解析请求约束：实例类型、CPU / 内存、模板、标签亲和
↓
2. 过滤节点：排除不健康、指标过期、超出 MVM 上限、缺模板副本、创建并发到顶、不满足亲和性的节点
↓
3. 打分：基于 MVM 数、实时创建数、CPU / 内存配额使用率加权
↓
4. 从高分节点中选一个：legacy 配置下由 priority_select_num 控制候选范围，Profile 模式下对应 selection.method 与 selection.top_n
没配评分时仍然会过滤：但选点会偏向候选列表的前几个节点，表现为新沙箱集中到少数机器，直到资源过滤器把流量推走。
字段作用
priority_select_num最终选点从评分前 N 名里做。多节点建议大于 1，小集群从 3 开始。
metric_update_timeout节点指标超过此时长视为过期、不可调度。应远大于上报周期。
local_metric_update_timeout本地指标超时字段。当前预过滤对两类指标的新鲜度检查都用 metric_update_timeout。
filter.enable_filters启用过滤器，常见有 CPU、内存、模板本地性、实时创建并发。
score.enable_scorers启用评分器。多机部署通常启用 real_time_weighted_average，且必须配好对应的 plugin_conf，否则该评分器不生效（有 Warn 日志）。

disk_usage_max_percent磁盘水位阈值，超过的节点被排除。

扩容后的 template redo

新节点注册成功不代表模板已经在它上面可用——template_locality 过滤器要求目标节点有模板副本，否则创建会失败或继续落到旧节点。镜像构建的模板需要在扩容后执行一次 redo：

cubemastercli tpl redo --template-id <tpl-id> --node <node-ip>

升级时的行为变化

从 v0.7.3 及更早版本升级、且不修改调度配置的集群，受两处影响：

  • 零调度配置会激活出厂 Profile：完全没配调度策略的集群，选点从“预过滤候选里随机挑”变为“强制 Guards + 出厂 Score 按 spread 选点”，放置会不同（注入时打一条告警）。想保持旧行为，设 scheduler.disable_factory_profiles: true，或配置任一 legacy 块；已配置过调度策略的集群不受影响。
  • 模板亲和打分：持有模板的节点得满分，其余 0 分。受影响的只有显式启用 image_score 的部署（含出厂 template_reuse Profile 和 legacy enable_scorers: [image_score] 集群）——默认配置、推荐配置和一键部署都不启用它，升级无感知。落点变化不符合预期时：想完全恢复升级前的放置，从 score.plugin_conf.image_score.enable_weight_factors 移除 template_id，或把 score.resource_weights.template_id 置 0；想保留模板亲和、但让负载能压过它，调低 image_score 权重。JFS 等共享存储后端不要为此启用模板亲和——模板所有节点都能直接读取，没有“避免拉取”的收益。

出厂 Profile

二进制内置三条 Profile（scheduler_factory.yaml）：

Profile路由条件行为
burst_balancelabel workload=burst_balance高并发同规格请求按资源水位与在途创建打散
template_reuselabel workload=template_reuse优先落在已持有模板本地副本的节点
mixed_binpack默认紧凑放置，保留整空节点

系统只在没有任何调度配置时注入这套出厂策略；显式配置了 profiles 或任一 legacy 块，整套出厂策略就不生效（legacy 块编译为兼容的 default Profile，行为不变）。

配置 Profile

scheduler:
  profile_route_label_keys: [workload]
  profiles:
    - name: burst
      route:
        labels: {workload: burst}
      filters:
        - name: skip-high-create
          type: expr
          expr: "node.creating < 8"
      scores:
        - name: prefer-idle
          type: expr
          expr: "node.cpu_util < 60.0 ? 80.0 : 20.0"
          weight: 2
      selection: {top_n: 5, method: spread}
      failure:
        filter: fail-closed
        score: default-score
        no_candidate: fail
  • 只有 profile_route_label_keys 列出的请求 label 能参与路由，也才会传给外部插件。
  • 路由按配置顺序匹配，第一个命中的 Profile 生效；非默认 Profile 必须带 instance type 或 label 条件（instance_type 当前统一为 cubebox，实际区分流量用 label 即可）。
  • selection.method 从打分结果里选最终节点：highest 取最高分；spread 在前 top_n 里选当前运行沙箱数最少的（把放置摊开）；random（缺省）按分数加权随机。top_n: -1 表示全部通过过滤的节点。
  • 每个 Profile 固定跑 node_safety、cpu、mem、disk、template_locality、realtime_create_num 这六个 Guards，配置关不掉。

失败语义

Guards 永远 fail-closed。Filter 默认 fail-closed，显式配 fail-open 会打风险告警。Score 默认 default-score，单个插件失败后用它的 default_score 继续，也可以配成 fail-closed。no_candidate 支持 fail 和 backoff，backoff 时会重新执行整条管线。配置在启动或热更新时整体编译——插件名、路由、表达式、权重、选点或失败策略任何一处无效，新配置都不生效，调度器继续用上一份。

准入与预留

跨副本准入是建议性的：每个副本按本地节点快照做准入，指标按上报窗口独立传播，所以窗口内多个 Master 可能对同一份可见容量重复准入，短暂超发。节点实际装不下时，创建第一次尝试就直接失败，不会转移到其他节点重试——建议配额贴近节点实际容量，并在客户端处理好创建失败。

Redis 是必选依赖：节点指标读取和创建后的路由元数据写入都要走它，Redis 故障会打断创建链路。滚动升级时混合版本不具备完整跨副本协调；旧版本还在服务时不要删旧版本的 reservation key，全部升级完后这些 key 就没人用了。

插件开发者：三种插件与 Score 契约

  • go（默认）：编译进 CubeMaster，实现 filter.Selector 或 score.Selector 接口，在包初始化时调 plugin.RegisterGoFilter / plugin.RegisterGoScore 注册。新增插件后要重新编译；重名在启动时被拒。
  • expr：启动时编译 CEL。Filter 返回 bool，Score 返回 0—100。CEL 拿到的是强类型只读的 node 和 request 对象；未知字段、类型错误、返回类型不对在 Profile 激活时被拒；Score 数值超出 0—100 在请求时才会报错并触发 score 失败策略。常用节点字段有 cpu_util、quota_cpu、allocated_cpu、creating、mvm_num、labels、template_local、snapshot_storage_writable 等；请求字段有 instance_type、cpu_millis、memory_bytes、template_id、labels。
  • grpc：独立进程。启动时完成一次握手，之后批量调 Filter 或 Score；CubeMaster 校验超时、熔断、快照版本和返回值。协议在 pkgs/proto/services/schedulerplugin/v1/plugin.proto。每个请求都带完整冻结快照，所以插件服务端可以无状态，并发请求共享一条连接即可；生产环境建议 Unix Domain Socket。
      filters:
        - name: company-policy
          type: grpc
          socket_path: /run/cube/company-scheduler.sock
          timeout: 100ms
          circuit_breaker_failures: 3
          circuit_breaker_cooldown: 30s
Score 插件契约：评分维度对当前请求不适用时，返回 score.ErrNotApplicable 显式跳过——不计分、不计权重，也不算失败（即使在 fail-closed 下）。返回空评分列表加 nil 错误是违反契约，会触发配置的失败策略。内置 scorer 在 legacy 因子配置缺失、被禁用或权重全为零时也返回 ErrNotApplicable。可运行示例在 examples/scheduler-plugin：SOCKET=/tmp/cube-scheduler-example.sock go run .。

验证

所有调度指标都带 profile 标签。最常用的三个：

  • scheduler_attempts_total{profile=...}：哪个 Profile 在承接流量；
  • scheduler_plugin_duration_seconds{profile,kind,plugin}：逐插件耗时，调权重时用；
  • sandbox_create_duration_seconds{profile,result}：按 Profile 的端到端创建延迟。

11软删除墓碑清理

CubeSandbox 在很多表上使用 GORM 的软删除：删除一行时只是把它的 deleted_at 列置位，GORM 随后在普通查询里把它隐藏起来。此前没有任何机制回收这些“墓碑”行，于是表会无限增长，过期的墓碑还会一直占用唯一键（即软删除 + 唯一键陷阱）。墓碑清理器（tombstone purger）就是解决这个问题的定时“看门人”。

它做什么

一个共享包 pkgs/cubedb/tombstone 同时运行在共享数据库的两个二进制里：

  • CubeMaster：清理 t_cube_* 软删除表；
  • CubeOps：清理 t_agenthub_* 软删除表。

每个组件在启动时注册清理器。它按固定间隔获取一个集群级咨询锁（保证每个 tick 内只有一个 HA 副本干活），然后对每张配置的表，硬删除 deleted_at 早于保留窗口的行。单次 pass 是有上限的（max_per_pass），大的积压会分摊到很多个 tick 里慢慢清，而不是一次长事务把锁占满。硬删除是跨方言的，并且对复活竞态安全——DELETE 会重新校验墓碑谓词，因此应用层 UPSERT 复活（deleted_at = NULL）的行在 select 与 delete 之间不会被硬删。

配置

soft_delete_purge:
  enable: false       # 默认关闭：清理不可逆，需显式开启
  dry_run: false      # 只 select 并打印计数，不真正 DELETE（用于安全的首轮观察）
  retention: 168h     # deleted_at 早于 now-retention 的行会被清理。
                      #   <=0 -> 7 天默认值；(0, 1h) 之间的值会上调到 1h。
  interval: 1h        # 两次 pass 之间的间隔。
                      #   <=0 -> 1h 默认值；(0, 1m) 之间的值会上调到 1m。

max_per_pass（5000）和批次大小 batch size（500）是包级常量，不可配置。所有字段都是可选的；默认值是安全的，且特性默认关闭（需显式开启），因为清理不可逆。

运维注意事项

默认关闭，先 dry-run：清理不可逆，需显式开启（soft_delete_purge.enable: true）；升级不应静默硬删此前一直保留的墓碑。开启后首次 pass 会按 max_per_pass 分批回收已积压的墓碑。面对大的历史积压，可先把 dry_run: true 设一个间隔，观察“将要清理”的计数，再开启真正删除。
  • 带外 DDL：设置了 CUBE_AUTO_MIGRATION=false 的部署，必须带外应用迁移 20260731120000 中的 deleted_at 索引；否则清理会是全表扫描。
  • PostgreSQL：迁移中的普通 CREATE INDEX 在构建每个索引期间会持有 ACCESS EXCLUSIVE 锁（阻塞写入）——对当前以 PG 为非主力的较小部署可接受；较大的 PostgreSQL 部署请在低峰期或维护窗口执行迁移。一次大规模回收 pass 之后，相关表会出现短暂的 autovacuum 高峰（大规模 DELETE 的正常现象）。

12组件多版本

节点上同时留着好几个版本的组件。建沙箱、恢复沙箱都按模板绑定的版本来取；本地没有，就去 CubeOps 仓库拉一份下来。这样节点把组件升到新版后，用老版本建的沙箱照样能恢复、老模板照样能调度，不会被升级连累。

组件是什么
cube-shim容器运行时 shim 和 cube-runtime
cube-image客户机根文件系统镜像
cube-agent客户机里的 agent
cube-kernel-scf客户机内核

背景：为什么要多版本

以前节点上只有一份组件（当前工具箱），升级器一升，版本就跟着变。模板是按特定版本建的：节点把 cube-image 从 v1 升到 v2 后，用 v1 建好的沙箱恢复时只能取到 v2，版本对不上，恢复直接失败；用 v1 的老模板副本被判成不兼容（STALE），没法调度。想救回来只能把老模板重做、重新给节点装组件，新老模板没法在一台节点上并存。

有了多版本：每个版本各留一份。v1 还在节点上存着，老沙箱恢复照样取 v1，老模板照样调度，节点升到 v2 一点都不影响它。新老模板能在一台节点上并存，升级不再伤筋动骨。一句话：缺版本不会拿当前工具箱凑合，而是去仓库下。所以当前工具箱随便升，都不影响已经绑定老版本的副本——这就是稳定恢复（stable restore）。新模板会把四个组件的版本都绑上；只有从老版本迁过来的历史副本可能只绑了两件，不享受稳定恢复。

“缺了自动拉”依赖两条网络：节点 → CubeOps（领下载地址、上报本地版本清单；不通就退回“只用已有的版本”，缺了直接失败）和节点 → 对象存储（数据真正下载的地方，组件包统一放在独立的 cube-ops 桶）。CubeOps 的地址三种部署方式都会自动配给节点（需要时用 CUBE_OPS_ADDR 覆盖），差别只在对象存储这一侧：

13Redis Cluster 部署与迁移

CubeSandbox 支持用外部原生 Redis Cluster 作为 Redis 后端。单机和 Sentinel 模式不受影响。Cluster 模式下不部署内置 Redis；Master 和 TemplateCenter 的配置变更会滚动其 Pod。

前置要求

  • 仅支持 DB 0：启用前先把数据迁出非零数据库；
  • 仅支持密码认证：不支持 TLS 和 ACL 用户名；
  • 仅支持 IPv4：IPv6 集群的重定向地址各客户端处理不一致；
  • 每个通告地址都必须从客户端网络直连可达：单个负载均衡入口通常不够。

Helm：在 values 里提供种子节点列表，密码走现有私有配置；Cluster 模式不部署内置 Redis。

  db: 0

  • 从客户端网络确认所有通告地址可达；
  • 跑一遍完整沙箱生命周期：创建、路由、暂停、恢复、删除；
  • 确认节点快照覆盖多个主节点上的节点。

运行行为与限制

  • key 名称不变。热点 key（生命周期状态、事件流、代理注册表）仍是单 key，分片拆不开；
  • 单 key 锁、解锁脚本和 WATCH 事务在所属主节点上仍然原子；
  • 跨槽位的批量读取是近似视图，不是全局一致快照；
  • 多 key 删除可能部分成功，失败后重试幂等清理即可；
  • Proxy pipeline 逐条独立路由，保序执行，不重放已成功的命令；
  • Master、Ops、Proxy 只重试服务器明确返回的重定向（MOVED / ASK / TRYAGAIN）。切主后收到 READONLY 会刷新路由并重试一次；传输错误一律返回调用方，不重放。Master 的 max_retry 在 Cluster 下不生效；
  • 生命周期管理器保留 go-redis 的重定向和断连重试。EXEC 响应丢失时 WATCH 回调可能重复执行，不重放保证不适用于生命周期写入；
  • 升级本 Chart 会一次性滚动重启全部控制面组件，即使不启用 Cluster。请预留容量。

14易错点与最佳实践

这一章的命令多、路径多，下面九条是运维现场最容易踩的坑。做任何破坏性操作前，先对照一遍。

易错点 1：把 12088 当成 3000。3000 是 E2B 兼容 REST API，12088 才是 WebUI。打开 Dashboard 用 12088，不需要额外暴露 3000。
易错点 2：去 journalctl 找业务日志。请求、调度、审计、VMM 创建过程都在 /data/log/<Module>/；journalctl 只覆盖启动期 stdout/stderr。
易错点 3：把“隔离”当成“清空”。隔离只阻止新调度，不会驱逐已有沙箱。维护前要先隔离，再主动销毁该节点上的沙箱，并等待至少 60 秒让在途调度结束。
易错点 4：以为删除节点会停进程。删除只移除 CubeOps 中的注册信息、状态、版本元数据和指标缓存；不停止进程、不销毁沙箱、不删磁盘。Cubelet 再启动会用相同 ID 重新注册。
易错点 5：IP 变了但 node_id 没配。未设置 CUBE_SANDBOX_NODE_ID 而由 IP 兜底时，IP 变化会被视为新节点。要动态跟随，必须显式配置稳定的 node_id。
易错点 6：扩容后不 redo 模板。新节点注册成功不代表模板可用，template_locality 会把缺副本的节点排除。标准顺序是装节点 → 健康检查 → redo → 等成功 → 放流量。
易错点 7：用关闭 template_locality 绕过模板问题。这会把模板副本缺失变成隐性故障。正确姿势是对新增节点执行 redo，并确认模板 job 状态。
易错点 8：直接打开软删除清理。清理不可逆且默认关闭。先用 dry_run: true 观察计数，并确认 disable_hard_delete 是否符合保留审计记录的预期。
易错点 9：Redis Cluster 用了非 0 库或 TLS。Cluster 仅支持 DB 0、密码认证与 IPv4；每个通告地址都必须从客户端网络直连可达。升级 Chart 会滚动重启全部控制面组件，请预留容量。

最佳实践清单

  • 先用 cubeopscli node list 和 cubeopscli node groups 确认节点状态与机型分布，再做任何维护。
  • 多节点排障先 cubemastercli info --sandboxid <id> 定位节点，再登录该节点用 cubecli / cube-runtime。
  • 改配置只重启直接读该配置的服务；改 CoreDNS 只改 Corefile.template；改 unit 文件先 daemon-reload。
  • 提 issue 前用 collect-logs.sh 打包，先脱敏再分享。
  • 生产集群保持 template_locality 开启，priority_select_num 取健康节点数的一小部分，并给 creation_concurrent_num 设上限。

自测

1. 为什么删除计算节点前必须先隔离并清空？删除操作到底做了什么、没做什么？

CubeOps 只允许删除已经隔离且没有沙箱的节点；删除本身不会隔离节点，也不会销毁负载。删除只移除节点注册信息、状态、组件版本元数据和指标缓存，不会停止节点进程、销毁沙箱、删除磁盘或删除 Kubernetes Node 对象。正确顺序是：隔离 → 等至少 60 秒 → 销毁全部沙箱 → 停止或退役 Cubelet → 删除 → 确认消失。

2. 新沙箱总是集中创建到少数几个节点，应按什么顺序排查？

先确认 score.enable_scorers 是否启用、enable_weight_factors 是否包含预期因子，以及 priority_select_num 是否大于 1（等于 1 或接近全量都会退化）。再检查各节点的模板副本是否都可用——template_locality 会把缺副本的节点排除出候选集。若刚扩容，先对新节点执行 cubemastercli tpl redo。

3. 组件多版本场景下，创建沙箱报 component version not in warehouse 或 component version missing on node，分别怎么处理？

component version missing on node 表示节点没配 cubeops_addr，且本地版本库没有该版本——给节点配置可访问的 CubeOps :3010 地址。component version not in warehouse 表示地址配了，但仓库里没有这个版本——去控制台导入对应的 cube-sandbox-one-click-<tag>-{amd64,arm64}.tar.gz 一键包，再到“任务”页确认导入成功。体积大的组件建议提前“预装”，避免首次创建卡在下载超时。
