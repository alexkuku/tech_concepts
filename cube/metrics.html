指标与性能基准

本页把 CubeSandbox 的三类指标串成一张可观测地图：CubeProxy 请求指标回答「请求进出是否正常」，沙箱资源指标回答「沙箱吃了多少 CPU 与内存」，沙箱网络指标回答「流量是否被转发、Session 与 SNAT 端口是否吃紧」。读完你应能配置抓取任务、写出正确的 PromQL、并用这些指标把性能与容量问题定位到具体组件。

1指标全景：三类指标与采集视角

CubeSandbox 的指标由三个互相独立、各自拥有端点的导出器提供。它们从不同视角描述同一条「请求 → 沙箱 → 网络 → 宿主机」的链路，因此不能彼此相加，也不能互相替代。

指标族导出组件默认端点回答的问题
请求指标CubeProxyhttp://127.0.0.1:18082/metrics请求流量、并发、成功率、失败率、沙箱响应延迟
资源指标Cubelethttp://<cubelet-node>:9998/v1/metrics/resource沙箱消耗多少 CPU、多少内存、是否触发限流/内存限制失败
网络指标Cubelet（读取 CubeVS 状态）http://<cubelet-node>:9998/v1/metrics/network沙箱 ingress/egress 流量、Session 数、SNAT 端口压力与分配失败

下图把三者的位置放进同一条链路：请求从 CubeProxy 进入，路由到沙箱；沙箱的资源由 Cubelet 从宿主机与 Guest 两侧采集；沙箱收发流量经过 CubeVS 数据面，由 Cubelet 读取 CubeVS 状态导出；最终全部汇总到 Prometheus。

采集视角 · 请求 → 沙箱 → 网络 → 宿主机
CubeProxy请求指标 :18082/metrics
↓ 路由到沙箱 / 统计请求生命周期
Cubelet资源导出器
host_sandbox宿主机 cgroup 记账
guest_workloadGuest 内 cgroup
↓ 沙箱 TAP / veth 收发报文
CubeVS eBPF每沙箱流量 Counter
session reaperSession / SNAT 快照
网络导出器:9998/v1/metrics/network
↓ 三类来源统一抓取
Prometheus抓取 · 存储 · PromQL 查询
三个独立端点，不要混淆。CubeProxy 的 /metrics 在 18082；资源指标在 9998/v1/metrics/resource；网络指标在 9998/v1/metrics/network。三者都独立于 Cubelet 通用指标端点 /v1/metrics，且都需要各自配置独立的 Prometheus 抓取任务。

2CubeProxy 请求指标

CubeProxy 为选定的沙箱数据面路由提供 Prometheus 格式的请求指标，用于观测请求流量、并发请求、成功率、失败率和请求延迟。指标保存在 Nginx 内存共享字典中，CubeProxy 重启后 Counter、Gauge、Histogram 全部重置。

2.1 启用与禁用：默认关闭（opt-in）

请求指标默认关闭，需将环境变量 CUBE_PROXY_METRICS_ENABLE 设为真值（1、on、true 或 yes）才启用：

# 启用请求指标
CUBE_PROXY_METRICS_ENABLE=1

设为其他任意值、空值或不设置时指标保持关闭。禁用时 CubeProxy 不记录任何请求样本，数据面请求阶段完全跳过指标采集，不创建指标监听器、不监听任何端口——此时 CUBE_PROXY_METRICS_LISTEN 的取值会被忽略。

部署方式开关配置项（均默认关闭）监听地址配置项（可选）
one-click（docker compose）在 .env 设 CUBE_PROXY_METRICS_ENABLE=1CUBE_PROXY_METRICS_LISTEN
Helm chart在 values 设 cubeProxy.metrics.enabled=truecubeProxy.metrics.listen
Terraform（TKE）在 tfvars 设 cube_proxy_metrics_enabled = truecube_proxy_metrics_listen

2.2 指标监听器

监听器由 CUBE_PROXY_METRICS_LISTEN 配置，默认值为 127.0.0.1:18082。若 Prometheus 从其他主机抓取，需改成 Prometheus 网络可访问的地址：

# 允许其他主机抓取
CUBE_PROXY_METRICS_LISTEN=0.0.0.0:18082

监听器只提供精确的 GET /metrics 端点，其他路径返回 HTTP 404。该端点既不使用 CubeProxy 的普通数据面路由，也不使用管理服务器。

网络访问风险：指标监听器本身不提供鉴权或 TLS。不要将其暴露在不可信网络中，应将监听地址绑定到可信管理地址，并通过防火墙或安全组限制访问来源。

2.3 Prometheus 抓取配置

prometheus · cube-proxy 
scrape_configs:
  - job_name: cubesandbox-cube-proxy
    metrics_path: /metrics
    scrape_interval: 30s
    scrape_timeout: 10s
    static_configs:
      - targets:
          - <cube-proxy-host>:18082

将目标地址替换为 Prometheus 可以访问的 CubeProxy 内部地址。若保持默认监听 127.0.0.1:18082，Prometheus 必须与 CubeProxy 在同一主机，或使用本地抓取代理。

2.4 指标族

指标类型标签含义
cube_proxy_request_totalCounterroute、method、result已完成且被统计的请求次数
cube_proxy_inflight_requestsGaugeroute已开始但尚未完成的被统计请求数
cube_proxy_upstream_response_secondsHistogramroute、method、result沙箱开始响应所需时间（秒）

关键语义：

  • result 判定：HTTP 状态码 200 至 399 记 success，其他记 fail。它只反映 CubeProxy 看到的结果，不代表沙箱内最终是否成功。
  • 流式调用：process.Process/Start 和 Connect 流一建立 CubeProxy 就收到 HTTP 200，此后流中的错误仍记为 success；用户命令以非 0 退出码结束也记为 success（调用本身已正常完成）。
  • Histogram 衡量服务延迟：从 CubeProxy 把请求转发给沙箱，到收到沙箱响应头为止，不是请求总耗时。bucket 当前从 0.001 秒到 8.192 秒，并包含 +Inf。
Histogram 边界语义：对 process.Process/Start 与 Connect 统计路由和启动/接入进程的时间，不含命令运行时长；文件下载统计沙箱开始发送文件之前的时间；文件上传因 CubeProxy 先收完整请求体再转发，不含客户端上传时间，但包含发送给沙箱及沙箱写盘时间。没有到达沙箱的请求（如 CubeProxy 自身返回的错误）计入 cube_proxy_request_total，但不会记录到该 Histogram。

2.5 当前采集范围

当前实现只记录以下两类归一化路由，其他 URI 不计入这些指标。路由标签经过归一化，不会因为每个沙箱的 ID 和容器端口不同而创建独立时间序列。

route 标签URI 形式典型用途
sandbox_exec/process.Process/*、/sandbox/<sandbox-id>/<container-port>/process.Process/*沙箱进程执行和连接请求
sandbox_files/files、/sandbox/<sandbox-id>/<container-port>/files沙箱文件请求

2.6 请求生命周期

rewrite 阶段：开始统计请求，将对应路由的 in-flight Gauge 加 1，并把归一化后的 route 写入请求变量。
↓
转发与等待响应：CubeProxy 把请求转发给沙箱，并开始计时「沙箱开始响应」的耗时。
↓
请求结束：读取 method、最终状态码，以及沙箱开始响应所需的时间。
↓
落账：更新 Counter 与 Histogram，并将 in-flight Gauge 减 1。
  • 计入的请求：只要 CubeProxy 能确定目标沙箱就计入，包括因沙箱不存在（404）、无权访问（403）、已删除（410）、暂不可用（503）以及无可用后端（503）而直接返回的错误。每个请求只计一次。
  • 不计入的请求：无法识别目标沙箱时（Host 与 E2b-Sandbox-* 头都没有路由信息，或 /sandbox/<sandbox-id>/<container-port> 路径格式不正确），CubeProxy 直接返回 HTTP 400，这类客户端错误不计入指标。

2.7 验证指标端点

curl -fsS http://127.0.0.1:18082/metrics

CubeProxy 刚启动时可能只有 HELP 和 TYPE 元数据，或暂时没有请求样本。完成一次被统计的沙箱执行或文件请求后，再检查对应的 Counter 与 Histogram 样本。

2.9 故障排查

现象检查项
curl 无法连接确认 CubeProxy 正常运行，检查 CUBE_PROXY_METRICS_LISTEN，并确认监听地址与防火墙允许请求
Prometheus 无法访问端点默认只绑定回环地址；将 CUBE_PROXY_METRICS_LISTEN 设为 Prometheus 可访问的内部地址后重启 CubeProxy
metrics listener 返回 HTTP 404必须使用精确路径 /metrics，其他路径按设计返回 404
HTTP 200 但没有请求样本完成一次被统计的 sandbox_exec 或 sandbox_files 请求后再抓取；首次抓取前可能只有元数据
期望的路由没有指标当前只统计 sandbox_exec 与 sandbox_files 两类路由，其他路由不在采集范围
重启后 Counter 清零指标保存在内存中，CubeProxy 重启会创建新的共享字典；Prometheus 应视为普通 Counter/Gauge reset
Prometheus 报鉴权错误监听器没有内置鉴权，应检查外围防火墙、安全组、代理或网络策略

3沙箱资源指标：host_sandbox 与 guest_workload

Cubelet 为运行中的 Cube 沙箱提供 CPU 与内存指标。一键安装默认启用，端点为 http://<cubelet-node>:9998/v1/metrics/resource。Cubelet 在后台定期采集所选统计视角的数据并缓存在内存中，Prometheus 抓取时只读缓存——抓取不会同步访问所有沙箱，也不会触发与沙箱数量成比例的运行时 RPC；但响应体大小与序列化开销仍随时间序列数量增长。

3.1 使用前提

  • 仅面向运行中的 Cube 沙箱。暂停、终止或删除后，对应指标停止导出。
  • 当前面向单容器沙箱，主工作负载使用 container_id == sandbox_id，暂不提供多容器级别拆分。
  • guest_workload 要求沙箱内 cube-agent 支持资源指标能力版本 1，并使用 cgroup v2 统一层级。
  • host_sandbox 只依赖宿主机上的沙箱 cgroup，兼容范围更广，是默认采集与导出的视角。

3.2 两种统计视角

统计视角统计范围适用场景
host_sandbox宿主机内核统计的沙箱 cgroup，包含 CubeShim、VMM 及其他宿主机侧资源占用宿主机侧沙箱资源记账和基础运维观测
guest_workload沙箱内核统计的工作负载容器 cgroup，不含 cube-agent 等管理进程用户代码的 CPU、内存使用率与内存限制观测
all同时导出以上两组指标同时分析工作负载使用量与运行时开销
两组指标不应直接相加。它们来自不同的资源记账范围。尤其 host_sandbox 的内存值是宿主机 cgroup 记账值，受共享快照页与写时复制（COW）影响，并不等于沙箱内看到的逻辑工作集或按比例分摊的物理内存。由于 VMM 开销、共享页与私有 COW 页等因素，两者的内存值通常不会相等。
如何选择：只需节点侧基础观测时用默认的 host_sandbox；要判断沙箱内工作负载的资源使用率或内存压力时用 guest_workload；需要对比工作负载与运行时开销时用 all。

3.3 工作原理

所有采集都由宿主机上的 Cubelet 主动发起，沙箱不会主动推送指标。两条路径的差异如下图所示：

资源采集 · 两条独立路径
Cubeletresource-metrics 插件 · :9998/v1/metrics/resource
↓ 两种视角分别采集
host_sandbox直接读宿主机 sandbox cgroup
containerd Task.Stats→ CubeShim
guest_workload 继续下沉 ↓
cube-agent StatsContainer读取工作负载容器 cgroup
↓ 缓存最新样本
Prometheus抓取缓存，不进入 RPC 同步路径
  • host_sandbox：Cubelet 直接读宿主机沙箱 cgroup。不依赖模板中 cube-agent 版本，也不涉及沙箱内统计周期；沿用节点自身的 cgroup 层级，保留现有 cgroup v1/v2 兼容逻辑。
  • guest_workload：Cubelet → containerd Task.Stats → CubeShim → 沙箱内 cube-agent StatsContainer → 读取工作负载容器 cgroup。依赖：cgroup v2 统一层级、cube-agent 声明能力版本 1、CubeShim 能通过 Task.Stats 返回完整统计、Cubelet 能按沙箱生命周期维护统计周期与计数器基线。
  • CubeShim 在启动沙箱时通过 agent.unified_cgroup_hierarchy=true 为 cube-agent 启用 cgroup v2 统一层级。旧模板的 cube-agent 可能不支持，这类沙箱不导出 guest_workload，但仍可导出 host_sandbox。

3.4 Cubelet 配置

一键安装部署后配置文件位于 /usr/local/services/cubetoolbox/Cubelet/config/config.toml，资源指标插件默认配置如下：

toml · cubelet resource-metrics 
[plugins."io.cubelet.internal.v1.resource-metrics"]
  enabled = true
  collection_interval = "5s"
  request_timeout = "2s"
  max_concurrent_requests = 8
  stale_after = "15s"
  export_scopes = ["host_sandbox"]
配置项说明
enabled是否启动资源指标采集，默认启用。设为 false 后端点仍返回 HTTP 200，但不导出沙箱资源指标
collection_intervalCubelet 更新内存缓存的目标间隔；决定 Task.Stats RPC 与宿主机 cgroup 的读取频率，与 Prometheus 抓取间隔相互独立
request_timeout单次 Task.Stats 请求或宿主机 cgroup 读取的超时时间
max_concurrent_requests单个采集器的最大并发请求数；guest_workload 与 host_sandbox 各自独立
stale_after最近一次成功样本超过该时长后停止导出对应视角；不得小于 collection_interval，并应为调度与短暂采集失败预留余量
export_scopes控制采集与导出视角，可设 ["host_sandbox"]、["guest_workload"] 或 ["all"]，默认 ["host_sandbox"]；未选中的采集器不会启动

发生短暂采集失败时，Cubelet 会继续导出最近一次成功样本；只有样本年龄超过 stale_after 后，对应视角才停止导出。配置校验失败会导致 Cubelet 启动失败（例如 stale_after 小于 collection_interval，或 export_scopes 含不支持的值）。修改配置后重启：

sudo systemctl restart cube-sandbox-cubelet.service

3.5 Prometheus 抓取配置

建议为资源指标配置独立抓取任务，以便单独调整间隔、超时与 relabel，而不影响 Cubelet 通用指标：

prometheus · resource 
scrape_configs:
  - job_name: cubesandbox-resource
    scrape_interval: 30s
    scrape_timeout: 10s
    metrics_path: /v1/metrics/resource
    static_configs:
      - targets:
          - <compute-node-ip>:9998

也可用 one-click 安装器的 scrape-job 模式生成该任务（只输出文件，不安装任何组件）：

# 当前节点，取自 CUBE_SANDBOX_NODE_IP 或默认路由
CUBE_OBSERVABILITY_CLUSTER_ID=cubesandbox \
  ./deploy/one-click/observability/install.sh prometheus scrape-job

# 或每行一个目标地址，'#' 开头为注释
CUBE_METRICS_NODE_LIST=./nodes.txt \
CUBE_METRICS_PROM_CONFIG=./cubesandbox-prometheus-scrape.yml \
  ./deploy/one-click/observability/install.sh prometheus scrape-job
资源指标端点最多同时处理两个抓取请求，超过上限返回 HTTP 503，以避免多个大响应同时占用 Cubelet 的 CPU 与内存。正常的单个 Prometheus 任务不会触发；若出现 503，应检查是否有多个 Prometheus 实例或手工请求并发抓取同一节点。

3.6 验证指标端点

sudo systemctl is-active cube-sandbox-cubelet.service
/usr/local/services/cubetoolbox/Cubelet/bin/cubecli cubebox ls -a --no-trunc

# 等待至少一个采集周期后执行
curl -fsS http://127.0.0.1:9998/v1/metrics/resource | \
  grep '^cubesandbox_'

默认配置会导出 cubesandbox_host_sandbox_* 指标。需要 guest_workload 时：将 export_scopes 设为 ["guest_workload"] 或 ["all"]；重启 Cubelet；确认沙箱内 cube-agent 兼容能力版本 1。端点返回 HTTP 200 但无逐沙箱序列不一定表示故障——节点上没有可采样的运行中沙箱、插件已禁用、或 Cubelet 尚未完成首次采样，都可能只剩节点聚合 Gauge 或空结果。

3.7 基础指标族

Cubelet 仅导出 Counter 与 Gauge 基础指标；CPU 使用核数以及 CPU、内存使用率等派生值由 Prometheus 查询计算。CPU 与内存上限只在 cgroup 配置了有限值时导出——未配置上限时不会用 0 或极大值代替；当前内存用量不受此限制，只要视角可用就导出。

节点聚合指标（启用 host_sandbox 时始终导出，含值为 0）

指标类型单位与说明
cubesandbox_node_sandbox_countGaugeHostSandbox 采样器当前清单中的沙箱总数
cubesandbox_node_sandbox_available_countGauge状态为 HostSandboxAvailable、资源样本可用的沙箱数

采集系统可在抓取时附加 cluster、node 标签用于聚合。available_count 是资源采样可用性口径，不是完整业务状态的 running 实例数（受暂停、采集错误、stale_after 影响）；两者都不含沙箱 ID 列表，不能替代控制面或 CubeBox Store inventory。

host_sandbox 指标（仅含 sandbox_id 标签）

累计指标只包含当前沙箱占用宿主机 cgroup 期间的使用量，不包含可复用 cgroup 槽位中上一个沙箱的历史。

指标类型单位与说明
cubesandbox_host_sandbox_cpu_usage_seconds_totalCounter沙箱在宿主机上累计使用的 CPU 秒数
cubesandbox_host_sandbox_cpu_user_seconds_totalCounter累计用户态 CPU 秒数
cubesandbox_host_sandbox_cpu_system_seconds_totalCounter累计内核态 CPU 秒数
cubesandbox_host_sandbox_cpu_throttled_seconds_totalCounter累计受到 CPU 限流的秒数
cubesandbox_host_sandbox_cpu_periods_totalCounter累计 CPU 调度周期数
cubesandbox_host_sandbox_cpu_throttled_periods_totalCounter累计发生限流的 CPU 调度周期数
cubesandbox_host_sandbox_cpu_limit_coresGauge宿主机沙箱 cgroup 的有限 CPU 上限（核数）
cubesandbox_host_sandbox_memory_current_bytesGauge当前计入宿主机沙箱 cgroup 的内存字节数
cubesandbox_host_sandbox_memory_limit_bytesGauge宿主机沙箱 cgroup 的有限内存上限（字节）

3.9 生命周期语义

为什么需要统计周期（epoch）

CPU 使用时间与内存限制失败次数来自 cgroup 累计计数器。制作模板/快照时这些计数器会随沙箱状态一起保存；从模板或快照创建新沙箱会继承已有计数；执行回滚时原始计数器还可能退回到快照时的值。若直接按 sandbox_id 导出原始计数，会出现：

  • 模板制作阶段产生的 CPU 与内存限制失败历史被计入新沙箱；
  • 回滚后同一指标出现无法区分原因的数值倒退。

为此，Cubelet 为每个新的 guest_workload 状态建立统计周期，并把首次成功采样作为基线：

导出的累计值 = 当前原始值 - 当前统计周期基线

这样可排除继承历史，并将回滚后的数据表示为新的统计窗口。当前内存用量是瞬时值，不做基线扣减。

guest_workload 生命周期

生命周期事件指标行为
新建沙箱、从模板/快照创建、克隆、重建工作负载创建新统计周期，首次成功采样排除继承的累计历史
创建快照或提交模板保持当前统计周期
回滚回滚期间停止导出；完成后创建新周期，累计指标从 0 开始。若运行时恢复请求发出后失败，新周期保持准备状态，guest_workload 继续不可用，直到后续回滚成功或删除并重建沙箱
暂停保持当前统计周期，但停止导出指标，而不是导出 0
恢复运行创建新周期，累计指标从 0 开始；在首次成功采样建立新基线前保持不可用
删除删除缓存与对应指标序列
Cubelet 重启从持久化状态恢复统计周期与基线，不重新计算已有窗口
累计指标只在一个统计周期内有效。从暂停恢复时即使还原了沙箱内存，也会创建新周期，因此这些计数不是沙箱生命周期总量。统计周期序号在恢复后可能回退（如从 2 回退到 1），应使用 cubesandbox_guest_workload_metrics_epoch_start_time_seconds 识别窗口，不要按序号排序。Prometheus 不理解 epoch 语义，只有累计值实际下降时 rate()/increase() 才按计数器重置处理，查询应覆盖所需时间范围并用 epoch 指标标注重置点。当前版本不导出按统计周期精确计算的内存峰值。

host_sandbox 生命周期

host_sandbox 不使用统计周期，而是按宿主机 cgroup 的分配关系统计：

  • 新沙箱被分配到可复用的宿主机 cgroup 池槽位时，Cubelet 在挂载沙箱进程前读取并持久化本次分配的基线。升级 Cubelet 时已存在的沙箱可能没有该持久化字段，会在升级后首次成功采样中建立兼容基线。
  • Cubelet 会在挂载进程前重试瞬时的分配计数器读取失败；若多次仍失败，沙箱仍正常创建，但该沙箱的 host_sandbox 保持不可用（不导出缺失初始使用量的累计窗口）。修复持续存在的 cgroup 读取问题后，需要重新创建沙箱。
  • 新沙箱不会继承同一槽位中上一个沙箱的 CPU 或内存限制失败历史。
  • 创建快照与执行回滚不会重置基线（不更换宿主机沙箱进程，也不改变 cgroup 分配关系）。
  • 暂停时停止导出，恢复运行后继续此前的累计值；删除沙箱后移除对应指标序列。
采集与抓取调优：collection_interval 控制 Task.Stats RPC 与宿主机 cgroup 读取频率，Prometheus 的 scrape_interval 控制 HTTP 抓取与样本写入频率。节点沙箱较多或抓取间隔较长时，可同时增大 collection_interval 与 stale_after。端点只保存最新样本、不保存历史，两次抓取间的短时内存峰值不会被保留；CPU 速率查询窗口内应包含多个成功写入的样本。两个间隔都不会减少活跃时间序列数（export_scopes = ["all"] 时单容器沙箱最多 22 条序列，节点另固定 2 条聚合 Gauge）。

3.10 升级旧模板与快照

快照模板会捕获沙箱内的进程与内存状态。仅升级节点上的 Cubelet、CubeShim 或沙箱虚拟机镜像文件，不会替换旧模板内存快照中的 cube-agent。旧模板的 cube-agent 可能不具备 cgroup v2 统计语义，也不会声明能力版本 1，这类沙箱不导出 guest_workload，但仍可导出 host_sandbox。

  • 镜像构建的模板：执行模板 redo，它用节点当前的沙箱虚拟机镜像与 cube-agent 为同一模板 ID 重做副本，完成后新建沙箱即可导出 guest_workload。节点升级后，Dashboard 标「需重建」的模板要先点「重建模板」再建沙箱；其它模板可直接创建。
  • 用户快照与已有沙箱：从运行中沙箱创建的用户快照，应先用兼容的新模板创建沙箱再重做快照；已运行或暂停的旧沙箱保留内存中的旧 cube-agent，需删除并重建才能完成升级。
  • 运行时 CubeShim 还会校验 StatsContainer 返回的能力版本，避免把旧版本 guest_workload 数据识别为有效指标。

4沙箱网络指标：流量 / Session / SNAT

4.1 背景与设计目标

沙箱网络由节点上的 CubeVS 数据面统一转发。CPU、内存等资源指标能说明沙箱消耗了多少计算资源，却无法回答这些网络问题：

  • 某沙箱是否实际产生了 ingress/egress 流量，当前吞吐和报文量是多少；
  • 流量是在 CubeVS 中正常转发，还是因策略、NAT、报文改写被丢弃；
  • 每个沙箱的各类 session 数量；SNAT IP 的 30000-65535 源端口范围是否正在承受压力；
  • 是否已出现真实的 SNAT 源端口分配失败。

因此网络指标的直接目标有三个：按 sandbox_ip 提供 ingress/egress 报文、字节、丢包与 SNAT 分配失败的 Counter；按 sandbox_ip 与 packet_class 提供存活 session 数；按 snat_ip 提供物理源端口占用量与容量 Gauge。

设计目标做法
无需 guest 配合归属流量eBPF 数据面把转发与丢包归属到具体沙箱，不依赖 guest VM
指标身份稳定用户态维护 map entry 所有权，使指标身份与 TAP、IP 所有权严格一致
抓取零侵入Prometheus 抓取不进入报文处理路径，也不触发 guest RPC
受控基数只用沙箱 IP、固定 packet class 集合与 SNAT IP 控制标签基数，不引入目的地址、端口、协议、单 session、策略规则等高基数维度
复用扫描复用已有 session reaper 结果计算 session 数与 SNAT 占用，不增加第二次完整 session map 扫描
局部失败可观测任一来源暂不可用时，仍保留另一来源的可观测性

4.4 Session 与 SNAT 快照

Session 与 SNAT Gauge 复用已有 session reaper 的扫描结果，不会在每次抓取时重扫 session map：

① reaper 每 5 秒扫描一次 egress_sessions，用安全延迟删除遍历移除过期 session。
↓
② 所有存活 session 按 (sandbox_ip, packet_class) 统计；只有普通 SNAT 与 hairpin session 纳入物理 SNAT 端口占用。
↓
③ 使用 (snat_ip, source_port) 对源端口去重。
↓
④ 完成整个扫描后，原子发布一份不可变快照供抓取读取。
快照会失效。任意一次 5 秒扫描失败时，上一份快照立即失效：下一次抓取不再导出 Session 与 SNAT Gauge，并返回 exporter_up{source="session"} == 0 与 exporter_up{source="snat"} == 0，而不是展示陈旧状态；超过 10 秒的快照也会被判过期并拒绝导出。后续扫描成功后指标恢复。源端口范围 30000 到 65535（含两端，共 35536 个）；同一源端口可在不同目的地址/协议 tuple 间复用，所以 session 数与不同物理源端口数是两个不同指标。

4.5 抓取路径与局部失败

Cubelet handler 使用独立 Prometheus registry。每次抓取 collector 依次：① 遍历并排序 sandbox_metrics；② 读取最新 session/SNAT 快照与已配置的 snat_iplist；③ 对同一 SNAT IP 的重复 allocator shard 去重；④ 生成 Prometheus 常量样本；⑤ 分别导出三个来源的健康状态。

三个来源相互独立。即使 sandbox map 读取失败，只要 session/SNAT 快照健康，对应指标仍会正常导出，仅 exporter_up{source="sandbox"} 变为 0。抓取不会扫描运行中沙箱、不会调用 CubeShim 或 guest、也不会向数据面增加报文；sandbox map 遍历成本与活跃 entry 数成正比，session map 扫描由后台 reaper 承担。

metadata upsert 或修复ensure 成功时清零；失败时保持原有 map 状态下一次快照前保持不变
网络策略更新计数继续；被新策略拒绝的报文进入 drop 计数被淘汰的 session 在后续快照中消失
保持同一网络分配的沙箱回滚计数继续，不跟随快照回滚陈旧 session 被删除，后续快照收敛
删除沙箱TAP 清理后移除时间序列session 删除或回收后消失
沙箱 IP 复用注册前用全零 value 覆盖 entry；失败时残留 Counter 可能进入新生命周期session 使用独立生命周期
CubeVS/Cubelet 网络初始化pinned map 与 Counter 在 Init 后保留；恢复 ensure 成功时清零，失败时留下原 Counter进程内 cache 初始为空，再由 reaper 发布

这些 Counter 的范围是 pinned sandbox_metrics 与当前沙箱 IP 分配，CubeVS 进程重启本身不会清零。Prometheus 应把一次成功的恢复 ensure、metadata upsert 或 IP 重新分配视为 Counter reset 边界。label 使用 sandbox_ip 而非 sandbox_id，因为数据面稳定且随时可用的所有权 key 是沙箱 IPv4；需要沙箱 ID 时，应在该端点之外与控制面 inventory 做关联。

4.8 基数与性能

每个 sandbox map entry 导出 9 条流量序列与最多 4 条 session 序列。map 硬上限 8192，因此单节点最多 106496 条；最多 4 个逻辑 SNAT IP 额外产生 8 条 Gauge，再加 3 条 exporter 健康指标。实际部署沙箱上限通常更低，但 Prometheus 仍需处理所有导出的指标族；若不需要同时保留 packet、byte 与 drop，可用 metric_relabel_configs 丢弃。该端点最多同时处理两个抓取请求，更多并发返回 HTTP 503，以避免多个大响应同时消耗过多 Cubelet CPU 与内存。

6用指标做性能基准与 SLO

这三份官方页面只定义指标语义，不提供具体基准数字。要做性能基准，应先用上面的指标把「请求面 → 资源面 → 网络面」串成可复现的观测口径，再据此定义 SLO。官方性能基准数据见「可观测性」章节中的性能基准页面。

6.1 建立最小可复现基准的三个口径

⏱️

请求面口径

用 cube_proxy_upstream_response_seconds 的 P95/P99 衡量「沙箱开始响应」的服务延迟，用 cube_proxy_inflight_requests 衡量并发水位。注意它不含命令运行时长与文件传输时长，比较时必须固定同一 route。

🧮

资源面口径

用 rate(...cpu_usage_seconds_total[5m]) 衡量实际使用核数，用 memory_current_bytes / memory_limit_bytes 衡量内存压力。host_sandbox 含 VMM 开销，guest_workload 更贴近用户代码，两者需分别报告。

🌐

网络面口径

用 8 * rate(egress_bytes_total[5m]) 衡量吞吐（bit/s），用丢包比例与 snat_alloc_failures_total 增长衡量数据面健康，用 SNAT 占用率观察物理端口整体趋势。

易错点正确做法
把 host_sandbox 与 guest_workload 内存相加当「沙箱内存」两者来自不同记账范围，分别报告；前者含 VMM/CubeShim 与 COW 影响，通常不相等
按 sandbox_id 直接导出 guest cgroup 原始计数使用统计周期基线扣减后的值，用 metrics_epoch_start_time_seconds 标识窗口，不要按 epoch 序号排序
把「没有网络指标序列」当成「零流量」无序列表示 key 不存在（数据缺失），必须结合 ensure 告警与活跃 TAP/IP 列表判断
用 端口容量 - session 数 推导剩余端口源端口可跨目的地址/协议 tuple 复用；判断真实耗尽看 snat_alloc_failures_total 正增长

未配置有限上限却期待使用率指标无上限时 *_limit_* 不导出，只能查实际使用量，无法算有明确分母的使用率

自测（点击展开答案）

1. 为什么 guest_workload 需要统计周期（epoch）？直接按 sandbox_id 导出原始 cgroup 累计值会有什么问题？

CPU 使用时间与内存限制失败次数来自 cgroup 累计计数器，制作模板/快照时会被保存，从模板或快照创建新沙箱会继承已有计数，回滚还可能让计数退回快照值。直接导出会导致：模板制作阶段的历史被计入新沙箱；回滚后出现无法区分原因的数值倒退。Cubelet 为每个新的 guest_workload 状态建立统计周期，以首次成功采样为基线，导出「当前原始值 − 基线」，从而排除继承历史并把回滚表示成新窗口。当前内存用量是瞬时值，不做基线扣减。

2. 为什么不能把 host_sandbox 与 guest_workload 的内存值相加得到「沙箱内存」？

两者来自不同的资源记账范围。host_sandbox 是宿主机 cgroup 的记账值，包含 VMM、CubeShim 等宿主机侧开销，并受共享快照页与写时复制（COW）影响；guest_workload 是沙箱内工作负载容器 cgroup 的值，不含 cube-agent 等管理进程。由于 VMM 开销、共享页与私有 COW 页等因素，两者通常不相等，直接相加会重复计算或错配口径，应分别报告。

3. 某沙箱在 Prometheus 中完全没有 sandbox_ip 时间序列，是否等于「该沙箱没有网络流量」？为什么？

不等于。eBPF 数据面只做 lookup，key 不存在时立即返回，不会自动创建 entry；entry 由用户态在 TAP 生命周期中 ensure 创建。如果 ensure 失败（如 map 打开失败、map 已满、UpdateAny 失败），该沙箱会缺少时间序列，但网络转发可能仍然正常。因此「无序列」表示 map 中不存在这个 key（数据缺失），必须结合 Cubelet 的 metrics ensure 告警以及活跃 TAP/IP 列表与 Prometheus 的 sandbox_ip 集合对比来判断覆盖情况。
