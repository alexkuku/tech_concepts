1产品定位：CubeSandbox 是什么

CubeSandbox 是专为 AI Agent 打造的开源 MicroVM 沙箱基础设施——既能安全执行不可信代码，也能托管长驻 Agent 进程与有状态服务。它基于 RustVMM + KVM 构建，每个沙箱都是一个具备独立内核的硬件隔离 MicroVM。

一句话记住三个硬指标：冷启动不到 60ms、单实例 VMM 额外内存消耗不足 5MB、原生同时支持 x86_64 与 ARM64 双架构。核心系统在开源前已在腾讯云生产环境规模化验证。

它解决什么问题

  • 不可信代码执行：LLM 生成的代码、Shell 命令、第三方工具需要强隔离环境，不能让一次逃逸污染宿主。
  • 长驻 Agent 与有状态服务：不止「跑一段代码」，还要托管 Redis、MySQL、浏览器、桌面乃至常驻 Agent 进程。
  • 规模化并发：评测、RL Rollout、海量会话需要高密度驻留与毫秒级启停，容器与重型 VM 都难以兼顾。

与 E2B / Docker / VM 的关系

CubeSandbox 在技术谱系中的位置
对比 Docker不是容器：每个沙箱独立内核，无共享内核逃逸风险
对比传统 VM更轻更快：亚 60ms 冷启动，VMM 内存不足 5MB
对比 E2BSDK 级兼容：替换环境变量即切换，业务零改动

更准确地说，CubeSandbox 把自己定位为 E2B 的可私有化替代：对外暴露 E2B 兼容的 REST API，对内用 MicroVM 提供硬件级隔离。因此既复用了 Docker 生态的镜像与编排习惯，又拿到了接近虚拟机的隔离强度。

55 行代码接入 E2B

如果你已有 E2B 项目，无需修改业务代码——只要把 SDK 请求指向你的 CubeSandbox 服务，就能切到私有化硬件隔离沙箱。迁移路径只有一步：改环境变量。

现有 E2B 代码业务逻辑保持不动
→
修改环境变量E2B_API_URL / E2B_API_KEY
→
CubeSandbox私有化 MicroVM 沙箱

Shell · 指向本地 CubeSandbox 服务

export E2B_API_URL="http://127.0.0.1:3000"
export E2B_API_KEY="e2b_000000"

Python · 直接沿用 E2B SDK

from e2b_code_interpreter import Sandbox  # 直接沿用 E2B SDK

with Sandbox.create(template="<你的模板ID>") as sandbox:
    result = sandbox.run_code("print('Hello from CubeSandbox!')")
    print(result)
核心结论：接入成本 = 两个环境变量。E2B 的 Sandbox.create、run_code 等调用完全不变，CubeSandbox 在协议层接管全部请求。

第一步：安装 PVM 宿主机内核

到 Releases 页面下载 kernel-release 内核主包（RPM 系 *.x86_64.rpm，DEB 系 *_amd64.deb）。以 RPM 系为例：

# 安装内核包（--oldpackage 跳过版本号比较）
rpm -ivh --oldpackage kernel-*.rpm

# 查看已安装内核，找到 PVM 内核序号
grubby --info=ALL | grep -E "^kernel|^index"

# 将 <index> 替换为 PVM 内核对应数字并设为默认启动项
grubby --set-default-index=<index>
grubby --default-kernel

# 配置内核启动参数
curl -sL https://cnb.cool/CubeSandbox/CubeSandbox/-/git/raw/master/deploy/pvm/grub/host_grub_config.sh | bash

重启后验证并加载 KVM 模块：

reboot

uname -r                 # 期望包含 opencloudos9.cubesandbox.pvm.host
modprobe kvm_pvm
lsmod | grep kvm         # 期望包含 kvm_pvm
echo 'kvm_pvm' > /etc/modules-load.d/kvm-pvm.conf  # 开机自动加载

第二步：一键安装

以 root 身份执行在线安装脚本（CUBE_PVM_ENABLE=1 启用 PVM 模式，MIRROR=cn 使用国内镜像）：

curl -sL https://cnb.cool/CubeSandbox/CubeSandbox/-/git/raw/master/deploy/one-click/online-install.sh | CUBE_PVM_ENABLE=1 MIRROR=cn bash

第三步：制作模板

安装完成后，用预构建镜像创建代码解释器模板，并监控构建进度直到状态变为 READY，记录输出中的 template_id：

cubemastercli tpl create-from-image \
  --image cube-sandbox-cn.tencentcloudcr.com/cube-sandbox/sandbox-code:latest \
  --writable-layer-size 1G \
  --expose-port 49999 \
  --expose-port 49983 \
  --probe 49999

# 监控构建进度（替换为实际 job_id）
cubemastercli tpl watch --job-id <job_id>
镜像仓库：国内优先 cube-sandbox-cn.tencentcloudcr.com/...，境外推荐 cube-sandbox-int.tencentcloudcr.com/...。目前仅 sandbox-code:latest 已发布为 Multi-Arch（同时支持 x86_64 与 ARM64）。

    result = sandbox.run_code("print('Hello from Cube Sandbox, safely isolated!')")

9易错点、记忆卡片与自测

易错点与最佳实践

架构别搞混：PVM 宿主机内核只支持 x86_64。ARM64 主机不要走快速开始的 PVM 路线，应直接使用物理机 / 裸金属部署。
文件系统必须是 XFS：CubeSandbox 依赖 XFS reflink 实现 Copy-on-Write 快照。Ubuntu / Debian / WSL 默认 ext4，需把 XFS 挂到 /data/cubelet，否则模板与快照会异常。
磁盘别卡在 50G：50 GB 只是下限；要制作多个模板或自定义镜像，建议 200 GB 及以上，避免构建中途空间不足。
glibc 版本是硬门槛：二进制基于 glibc 2.31 构建，系统 glibc < 2.31 时二进制直接无法运行，装前先 ldd --version 确认。
生产环境先加固：把服务暴露到不可信网络前，务必先按「网络加固」指南完成安全配置；E2B_API_KEY 本地可填任意值，但对外务必启用 API 鉴权。

自测

自测：3 道题检验掌握度

1. 为什么说 CubeSandbox「与 Docker 不同」，核心差异是什么？

Docker 容器共享宿主机内核（靠 Namespace 隔离），隔离级别低、存在容器逃逸风险；CubeSandbox 每个沙箱是独立 Guest OS 内核的 MicroVM，由 KVM + eBPF 构成硬件与内核级双重边界，因此能安全执行不可信的 LLM 生成代码。

2. 已有 E2B 项目接入 CubeSandbox，最少需要做哪些改动？

无需改业务代码，只需设置 E2B_API_URL（指向本地 CubeSandbox，如 http://127.0.0.1:3000）与 E2B_API_KEY（本地填任意非空值）。完整示例还需 CUBE_TEMPLATE_ID 与 SSL_CERT_FILE。

3. 快速开始四步中，哪个环节容易被系统环境卡住？为什么？

最易卡住的是 PVM 内核与文件系统：PVM 仅支持 x86_64，且要求系统 glibc ≥ 2.31；同时 /data/cubelet 必须是 XFS（依赖 reflink 做 CoW），磁盘至少 50 GB（建议 200 GB+）。ARM64 主机应改走裸金属 / 物理机部署，而非 PVM。
